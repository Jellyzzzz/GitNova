用户已确认：刚开始重构，完成内容主要是CommandType、AgentCommand及少量协议类型，没有大量新实现。因此撤销原“Agent仅剩14–20小时”的快速前提。**42–60小时是本次可投入预算，不是本次全部范围可完成的预测。** 文档仍覆盖所有已同意功能，不删安全、幂等、同步或后端功能来迎合预算。

以下为本次审计给出的规划假设，不是实测工时：旧代码纯逻辑可迁移、基础设施无重大障碍、前端由Codex生成而你负责验收时，当前全范围可先预留104–166有效小时。早期学习/真实恢复联调偏差很大，完成两个切片后必须重估。它不是由“文件数×几分钟”推导，也不是承诺上限。旧Agent86–142小时估算已包含旧PR，不与新PR重复相加；本表重新分组，A明确不含B/C。

## 3. 当前42–60小时怎么用

它是一段集中实现窗口，不按“第60小时一定全部交付”安排。按依赖推进：H0→Agent本地可靠闭环→HTTP/SSE/实例安装→平台初始Workline/发布与恢复→通用PR→同步→用户关系→异步投影。实际提前完成即可进入下一段；超预算不拿Fake代替实现。

最初2小时只做文档导入/现有类与测试清点/Java与环境探针。随后以每个2–4小时的小块完成一个可观察行为：先日志两条重开→错误写入不确认→结果对象→脚本模型read/tool/STOP→取消→本地Worker。读API、写测试与修失败都计入有效工时。

在累计H6记录Core/日志实际到达的行为，不以“还没达某个任意节点”为能力评价。H12检查两条本地Task及取消是否已能重复演示；H24检查真实Sandbox与模型代理是否已接通；H42/H60按唯一验收清单记录已完成/未完成和下一个最短路径。这些是重估窗口，不是允许跳过上一段的死线。

PR依赖仓库树/CAS和Outbox的事务写入端；不等待通知消费者全部实现。同步依赖RECOVERY安装器及三方合并器；不在协议阶段先构造完整同步框架。社会关系代码可以与前端分工，但核心手写者的时间不能被重复算成两人并行。

## 4. 如何取得可信剩余估计

做完两个垂直切片后，逐卡填写估时：理解需求/查API、实现、功能内测试、接入回归四项。将已经暴露的实际阻塞单列。剩余预测=未完成卡实测估时之和+已知阻塞+最后8–12h跨模块验收；新证据可以缩短或拉长，不为维护旧承诺篡改测试标准。

验收文件内“参考编译通过”“模型规格实验通过”不计作产品PASS。只有你实际代码的commit、运行命令和输出对应到用例才勾选。时间不足时可明确改变投递/展示日期，功能范围的调整必须由用户另行决定，不默认拆成缩水版本。
