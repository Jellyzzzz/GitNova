## 开始前：三条写代码的方式

### 当前实际施工顺序：先Core，再托管衔接

| 顺序 | 阶段目标（完整放行条件见对应步骤） | 打开哪些部分 | 此阶段边界 |
|---|---|---|---|
| 1 | 用户原文成为USER Message，脚本模型调用一次读工具，再STOP返回原文 | 步骤3；按需声明SessionLog/ResultStore及其事件值对象；接口测试实现放test | 不要求COMMAND_ACCEPTED，不做HTTP、不先写全部日志恢复/历史索引 |
| 2 | 同一个Core在本地目录真实读写，模型可调用，事实有真实日志 | 步骤2的日志/结果存储、步骤4的本地工具；迁移步骤12中的纯Gateway部分，开发连接不经过平台 | 不宣称已实现云端恢复；Linux进程取消在Linux测 |
| 3 | 同一会话第二个Task能利用第一轮历史，Context策略可用 | 步骤5；复用已实现的摘要/外置算法，不重新调参 | 不先加Memory/RAG或平台功能 |
| 4 | 相同Core由Worker接收命令、返回回执和事件 | 步骤1剩余协议及步骤6—8 | 不在Core里重做命令幂等与Binding校验 |
| 5 | 同一Worker放进Sandbox并接GitNova平台 | 步骤9—12 | 未实现能力不注册、不用Fake冒充成功 |
| 6 | 回答展示、显式发布和约定恢复链实际可用 | 步骤13—16及对应后端施工章节 | 自然STOP、发布、RECOVERY分别验收，不互相代替 |
| 7 | 新执行链完成替换，整套Harness验收通过 | 步骤17—18、03验收矩阵 | 保留旧历史；未执行项不能算完成 |

已完成的AgentCommand/ProtocolJson保留给Worker。**接下来实现步骤3的ModelTypes.Message与AgentEngine执行链，包括工具分发、自然结束、取消、预算及错误处理。** 可先实现业务再写验证；第一条循环的测试用本地executionId和空平台来源，不伪造HTTP受理，其余分支按步骤3逐项完成。

本地驱动与Worker都传原文/Message、只读SessionRuntime、Control和本次Writer；Worker额外绑定平台身份，Core不用TaskInput。真实本地使用前必须接好实际日志与资源关闭，测试中的内存Log不能冒充崩溃恢复。当前默认先用shell调用系统程序，不以手写LocalReadTool为前置。

**先说明一个可观察行为，再实现它。** 例如写出“同一命令POST两次只启动一次”的输入与预期结果。可以先写业务代码再写JUnit，不要求测试先行；但正常/失败验收不能留到所有模块写完才补。

**按责任拆类，不按每个动作拆 Service。** 本地日志一个写入者、Worker 一个任务执行器、平台一个窄的 WorkerClient，足以表达多数行为。不要每个字段再包一层 provider。

**核心实现由你写。** 可让模型解释代码或指出反例；完整输入、输出、失败条件以本文为依据。改动后要能回答：为何这个位置需要持久化？什么已经发生？重试会不会重复？

### 每步先看数据流，再看文件卡

本次补充只覆盖Harness及其必须的平台接线，不展开通用PR/社交/通知。步骤15与协作后端单独排期；步骤16的原线恢复不依赖完成跨工作线sync。每步的“行为与数据流”给调用入口、必要类型、来源与去向、锁/落盘位置、失败停点和首个验收，文件卡才回答具体落在哪个类。字段完整规则统一查05，不再让你从变量名猜。

#### 1.3 ProtocolJson：这是待手写的类，不是reference里已有接口

生产文件：`agent-runtime/agent-protocol/src/main/java/com/gitnova/agent/protocol/json/ProtocolJson.java`。**reference没有ProtocolJson的Java实现**，现已补入[四个方法的详细施工说明](reference/agent-protocol/src/main/java/com/gitnova/agent/protocol/json/ProtocolJson.md)：按输入→处理→输出展开，并包含旧代码复用和待实现测试。本卡决定施工顺序，05第1节决定字节格式；详细说明不另排一套顺序。

先读已有[CanonicalJsonCodec](../../src/main/java/com/gitnova/service/agent/persistence/CanonicalJsonCodec.java)的递归排序与hash逻辑。仅提取纯算法，不引入Spring Bean、不修改旧持久化摘要；新协议的UTF-8字段排序与旧Java自然排序不完全相同，具体反例见详细说明。

先实现以下四个静态方法，不增加Validator/helper类：

```java
static ObjectMapper mapper();
static AgentCommand readCommand(byte[] body) throws IOException;
static byte[] canonicalBytes(Object value) throws IOException;
static String sha256(Object value) throws IOException;
```

- `mapper()`：类初始化时固定私有ObjectMapper，注册JavaTimeModule、统一日期编码，拒绝未知字段、重复键、尾随JSON；不启用default typing。对外返回已配置副本，调用方构造时取一次并复用；内部编码/摘要不受副本修改影响。它只处理JSON，不查询数据库。
- `readCommand(body)`：读单个JSON对象；检查外层必需键恰好为schemaVersion、commandId、sessionId、worklineId、runnerEpoch、type、taskId、attemptId、payload；拒绝未知/缺失键。明确检查整数/字符串/null类型，避免字符串转数字或缺失primitive变成0。按八种type选择对应内部Payload record解码；Payload也检查必需键、类型和未知键，然后用明确提取的公共字段new AgentCommand。不得直接让Jackson猜sealed Payload子类。
- `canonicalBytes(value)`：转换为JSON树，对所有对象字段递归按字段名的UTF-8无符号字节排序，数组保持原序；可在同一类写一个私有递归方法，不另建helper类。日期/数字使用固定配置，最终输出UTF-8字节；保留显式null，不trim用户正文，不做Unicode改写。字符串是字符串值，不自动二次解析为JSON。
- `sha256(value)`：仅对canonicalBytes的结果计算SHA-256，输出小写hex；不是对toString或任意原始JSON排版计算摘要。

语法/解码失败由IOException族传播，值对象违反约束由IllegalArgumentException表达；HTTP错误码转换是步骤6的HttpJson职责。本步只处理有界fixture，HTTP实际请求大小/深度限制不得因此省略。

**依赖只有：** CommandType、AgentCommand、Jackson及JDK。不等Receipt、Event、SessionLog或Worker写完。

## 步骤 2：本地日志与完整结果存储

### 行为与数据流：返回一次append究竟确认了什么

**入口/前置：** 【本步实现】FileSessionLog(stateRoot,streamId,FileLock)；宿主先持目录进程锁。它提供只读SessionLog和每次执行的SessionLog.Writer，签名/StoredEntry完整定义见05第2.3。

```text
宿主：bind(executionId, immutable origin) → 本次Writer
Core：writer.append(type,payload)
  → 追加锁 → 固定Entry/来源 → 分配sequence/eventId
  → 完整编码/写满/force → 发布Boundary/索引 → 返回Entry
ResultStore.capture → finish返回Ref → writer.append(TOOL_RESULT引用)
  → eventId作为resultId → HistoryIndex → read/search
```

**数据与所有者：** 序号、完整字节尾部、偏移索引和失败标志只在FileSessionLog。Boundary(Position(streamId,sequence),byteOffset)不暴露未确认字节。Worker从StoredEntry.origin生成平台AgentEvent；Core history只返回Entry，不反查Task。history与Writer读写同一库，不增加另一条内存权威历史。

**动手顺序：** SessionLog中的Entry/Position/Writer→FileSessionLog bind/append/read/close重开→boundary/awaitAfter→尾部恢复；再ResultStore→FileResultStore→HistoryIndex。先给本地executionId和空origin追加两条，不需AgentCommand、Worker或云端身份。

**锁和失败：** FileLock防另一个进程打开同一写环境；ReentrantLock防本进程线程交错分配/追加，两者不能互相替代。force失败不更新可读尾部，实例停止确认新写入。写了半行且无成功确认时，重开只允许修复末尾不完整记录；完整中间记录损坏拒绝恢复并保留证据。force成功后返回丢失属于“可能已提交”，重开按日志事实核对。

**对象与限额：** 捕获超限继续排空输入但停止保存，Ref.captureTruncated=true；预览省略不是捕获丢失。对象发布后日志失败只留下孤儿，不把它当可检索事实；引用对象缺失/坏hash明确报错。此步不实现在线GC。

**验收：** append A/B→close→reopen→read仍是A/B→下一条序号继续；然后故障注入短写、force失败、半行尾部、并发追加和等待通知竞态。这里只证明正常重开和明确故障模型，不能承诺宿主盘损坏也无损。

FileSessionLog固定streamId，bind的Writer固定executionId/origin；不能读取可变currentTask补身份。云端streamId为Q:E，旧段和旧resultId保留；本地段由本地创建，不需平台。历史按保存的段顺序读取，不对不透明streamId字典排序。Worker全进程锁仍由WorkerApplication持有；关闭单次Writer不关共享日志，关闭日志不释放外部进程锁。


> **动手提示：** 先分清：日志记录已发生的事实；ResultStore存事实引用的字节。你要定义append成功的含义，而不是先背NIO。 最先验证：顺序append两条、close/reopen后读回同一内容；再增加短写/force失败/尾行损坏测试。 逻辑与检索目标见[09步骤2](09_文档修正与开发导航.md#step-2)。

### 目标

离开MySQL以后，实际使用的Agent仍有可靠可查的本地事实。步骤3的第一条控制流可先用测试Log；此步是接入真实本地运行前的耐久实现，不是写Engine业务方法的先决关卡。

### 新建责任

`FileSessionLog`：一个日志写入者、分配序号、读历史、恢复尾部。  
`FileResultStore`：完整命令输出/大结果保存、摘要、稳定资源身份。  
`FileSessionLog/HistoryIndex（本步仅落盘与索引；完整恢复见步骤 16）`：从日志和最近摘要构造会话状态。

### 写入算法

`append(eventType,payload)` 在短写入锁内确定 sequence，编码一条完整 JSONL，写入 FileChannel。需要耐久确认的记录完成 force 后，才返回 eventId 并通知事件订阅者。失败不能继续假装该响应已经记录。

事件分配和磁盘追加由同一个写入者负责；不要多个线程各自 `sequence++` 再抢着写。

大结果先写唯一临时文件，计算摘要并关闭/force，再原子改名为最终对象，然后在日志中追加引用。实际返回路径的映射以不可变 resultId 为主，不以当前容器路径为长期身份。

### 崩溃处理

启动逐行检查。只允许最后一条不完整记录被隔离/截断；完整行中部校验失败或序号断裂要返回恢复错误。先保存坏文件证据。

看到 `TOOL_STARTED` 没有对应结果时，标为结果未知；不能据此重跑工具，也不能编造一个 exitCode。

同一环境重开继续原stream/sequence；从快照恢复新环境分配新stream，旧段只读保留。云端由平台新epoch映射为新streamId，本地不申请云端epoch。

### 测试

`SessionLogTest` 覆盖并发追加仍有序、写失败不确认、尾行截断可识别、中间损坏拒绝恢复、重复 eventId 内容不同报错。

`FileResultStoreTest` 覆盖小结果和大结果均有稳定身份、写文件后日志前崩溃只留下孤儿、结果缺失明确报错、摘要不匹配拒绝读取。

### 为什么这不是重 Workspace

这里管理的是 Agent 自己的历史事实，不是每次文件修改的数据库镜像。它可以直接在容器内读写，不请求平台批准每个工具。

## 步骤 3：抽出 AgentEngine，用假模型证明执行边界

### 行为与数据流：同一个请求如何从模型变成工具、再变成回答

**入口：** 【本步实现】AgentEngine.run(Message,SessionRuntime,ExecutionControl,SessionLog.Writer)。String重载在Core入口逐字包装USER Message。SessionRuntime只有共享目录、只读history和ResultStore；本次executionId来自Writer，Task/Attempt只存在于Worker固定绑定。

```text
校验USER Message → writer.append(EXECUTION_STARTED / USER_MESSAGE_RECEIVED)
  → Control检查 / 工具与模型预算 / 应用已接纳Steer
  → context.prepare(session,control,writer,tools.definitions()) : Request
  → writer.append(MODEL_CALL_STARTED) → gateway.complete : Response
  → writer.append(MODEL_RESPONSE) → context.observeResponse
      TOOL_CALLS → Context(executionId,toolCallId,session,control)
                 → TOOL_STARTED → tools.execute → ResultStore / TOOL_RESULT
      STOP → Control原子保存ANSWER_DELIVERED并关闭输入 → AgentOutcome
宿主 finally：确认进程/输出收尾，撤销该Writer；Worker再按原绑定写TASK_FINISHED
```

**生成与复用：** Context为每次请求分配modelCallId，Engine不重新生成。toolCallId检查非空、当前execution内唯一及配对；普通工具不传Task/Attempt、不直接写TOOL_RESULT。Entry.eventId为稳定证据引用，模型文本中不夹带平台命令或身份。

**消息入口：** Worker把已受理Submit原文传给String入口；本地CLI做同样调用。也允许受信调用者构造USER Message使用主入口。Engine不反查COMMAND_ACCEPTED，不修改原文。当前输入及已应用补充按executionId/源事件引用保护；Context不得再无条件追加一次input。

**动手顺序：** 迁移已有model消息/usage/thinking和自然STOP；声明Message、SessionLog.Entry/Writer、Control、SessionRuntime/Outcome、Map工具分发。最先用脚本Gateway、内存日志Writer和一个测试工具跑通循环，再换真实存储/Shell。具体类照后面的卡片写，测试替身不进入生产装配。

**必须明确的分支：** 非空正常STOP、无toolCalls且无待应用Steer才交付；reasoning-only、LENGTH、坏协议不当回答。工具参数错误可成为已保存observation；日志/结果写失败不能伪装为INVALID_ARGUMENT。取消/过期/预算用明确终止原因，不继续下一次调用。供应商错误分类可迁移旧Gateway，不为此新造第二套retry框架。

**竞态：** 接收Steer与确认STOP共用Control锁；Steer先成立则本次STOP不得交付，Engine取出指示后再决策；STOP先成立则拒绝新的Steer。取消回调在锁外关闭当前HTTP/进程，注册时处理“此前已取消”；Engine不持Control锁等待网络。主模型usage在保存后更新，摘要usage不覆盖它。

**验收：** 脚本模型read→tool结果→STOP；断言请求含配对toolCallId、日志有唯一原响应、answer逐字等于STOP正文。随后加入空STOP、重复callId、取消与存储失败。做到这里即可脱离Server运行一个Agent，不等后端协作功能。

> **动手提示：** 把模型当会按脚本返回的外部函数。输入Message+本地SessionRuntime+本次Writer/Control，输出AgentOutcome；先不联公网模型。 最先验证：假模型按read→tool结果→STOP返回；最终answer必须引用那一条已保存响应。 逻辑与检索目标见[09步骤3](09_文档修正与开发导航.md#step-3)。

### 目标

不启动Server、MySQL、Redis、MQ，给目录和模型入口就能完成一次任务。

### 可复用与必须改造

可从当前模型结构迁移 `ModelRequest/Response/Message`、tool call、usage、thinking、预算和终止原因。当前 ModelGateway 与 Context 类带 Spring 装配与持久化依赖，需要构造器注入纯配置/接口，不能原目录整包复制。[G04][G08]

本地最新自然 STOP 路径优先迁移，不从旧 `AgentCompletionOutcome/finishTask` 反推新的结束语义。[U01]

### 建议的核心接口

```java
public interface AgentEngine {
    AgentOutcome run(ModelTypes.Message input, SessionRuntime session,
                     ExecutionControl control, SessionLog.Writer events);
}

// ToolRuntime 是本地Map分发类，完整签名见 reference 中同名文件。
```

SessionRuntime持本地sessionId/目录/只读history/ResultStore；写入只能通过本次SessionLog.Writer。底层仍是一份日志，Writer是固定身份的写入视图，不是新事实库。Core不import AgentCommand、AgentEvent或PlatformOperation，平台类型留Worker适配。

### 完整循环顺序

1. 检查取消、deadline、model/tool预算；应用已受理的后续指示。
2. 通过 ContextCoordinator 构造请求。
3. 保存 MODEL_CALL_STARTED；调用 ModelGateway。
4. 保存完整 MODEL_RESPONSE，再更新内存消息。
5. TOOL_CALLS：逐个执行与保存结果，正确配对 toolCallId；再循环。
6. STOP：验证非空正文、无工具调用、无待应用指示；记录 ANSWER_DELIVERED，引用原始响应。
7. LENGTH/协议错误/网络错误：保留已经发生的轨迹，返回相应终止原因，不冒充回答。

工具异常如何返回模型与系统持久化失败如何停止运行，必须分开。不能把本地日志写失败包装成“模型换个参数再试”。

### 假模型测试

`ScriptedModelGateway` 预设：先返回 read，再 edit，再 shell，最后 STOP。测试实际文件被修改、工具 ID 对应、最终回答文字不被二次总结。

再模拟 STOP 为空、STOP 带工具、LENGTH、重复 toolCallId、取消、工具结果保存失败。新工具定义中找不到 `finishTask`。

### 完成标准

## 步骤 4：先接Shell与Linux原生命令，再按需迁移专用文件工具

### 行为与数据流：参数、文件字节与进程事实分别归谁

**入口：** `AgentTool.execute(argumentsJson, ToolTypes.Context): ToolTypes.Result`；definition只暴露模型业务参数，真实workRoot、取消句柄和scope来自Context。复用旧Edit/读取/参数错误表达的纯逻辑，去掉Workspace permit与Mapper依赖。

```text
可选read_file：解析路径/行区间 → SafePaths → 有界读取 → 原行号/继续参数
edit_file：解析操作 → 读取同一原文件 → 定位/校验全部替换与expectedSha
           → 单文件临时写/原子替换 → changed/前后hash
shell：解析action → Spec(processId,argv,cwd,白名单env,timeout,captureLimit)
       → ProcessSupervisor.run/start/poll/stop → Exit/Background/有界增量输出
       → ToolTypes.Result → Engine统一记录TOOL_RESULT
```

**数据与身份：** processId由Harness为一次实际启动分配，不接受用户任意PID/PGID；POLL/STOP只使用本Session已登记的processId。stdout/stderr的Ref由ResultStore生成；exitCode在仍运行/无法确认时可null，不能默认0。`stoppedConfirmed`和`timedOut/cancelled`不同：触发超时不等于已经杀干净子进程。

**动手顺序：** 【本步实现】SafePaths（先满足cwd校验）→ProcessSupervisor/Linux实现→LocalShellTool；先让模型经shell执行cat/sed/rg，再复用LocalEditTool。LocalReadTool是可选适配，不阻塞本地闭环。参数先解析为工具内部Args；路径/冲突错误由工具返回精确字段位置，I/O/存储失败按05异常表处理。Linux启动/进程组测试在Colima或目标Linux中进行，Mac文件工具测试不假装证明Linux取消。

**并发/输出：** Engine顺序调用工具；后台START产生的潜在写进程另由Supervisor登记，冻结/收尾前必须处理，不能用“工具串行”推导目录一定静止。stdout/stderr同时排空到有界捕获，waitFor不能阻塞两路Reader；控制请求有独立线程。超限继续消费并标截断；非零退出如实返回，不在Harness推断语义任务失败。

**验收：** 中文/CRLF原文、重叠替换拒绝、旧hash冲突、路径逃逸/符号链接；shell同时大输出、exit3、timeout、取消父子进程、POLL前进和重复STOP。无法确认停止则BLOCKED，不能继续编辑/封存或对用户说环境已清理。

> **动手提示：** 先区分工具协议错误、文件冲突、命令非零退出。它们不是同一种“失败”。 最先验证：命令同时输出大量stdout/stderr仍能退出；错误cwd不能越界；取消检查实际子进程。 逻辑与检索目标见[09步骤4](09_文档修正与开发导航.md#step-4)。

### 目标

工具直接操作本地目录，功能不再绕平台 Workspace；错误和取消仍然正确。

### 文件工具

不要求为了读取文件先手写LocalReadTool。shell可以执行`sed -n '1,120p' src/Foo.java`、`rg -n 'keyword' src`；正文仍是模型选择工具后给出的script，绝不直接执行用户Task原文。镜像负责安装并验证bash/coreutils/sed/findutils/ripgrep。需要稳定行号、分页或独立只读授权时再迁移LocalReadTool；LocalEditTool则可保留已有精确匹配/替换收益，不强制一切都用shell重写。

最初只有shell实现时，实际allowedTools只配置`["shell"]`，先证明一条读取/搜索链，再按实现加入edit_file/history工具。examples/runtime-config.json是完整能力示例，不是当前施工阶段必须照抄的授权清单；未实现read_file/平台工具时不要授权，也不要悄悄忽略配置错误。

Linux程序不是模型可直接调用的协议：LocalShellTool仍负责输入解析、可信cwd/环境、启动、超时/取消、stdout/stderr捕获、退出事实与结果包装。shell能改文件和执行网络操作，不能用工具名或字符串黑名单证明只读；真正的读写/网络限制来自运行用户、挂载与Sandbox策略。SafePaths只保护专用工具路径及shell的cwd参数，不约束脚本内任意路径。

路径解析：允许工作根内的相对路径，拒绝越界；访问前检查符号链接/实际路径。创建文件检查父目录；替换可写临时文件后在本地锁内改名。别用 `startsWith` 字符串前缀替代路径关系检查。

精确替换要求原文存在且匹配数量符合预期；“没找到”不是“追加到末尾”。创建模式不能悄悄覆盖已有文件。删除明确记录被删除对象的来源摘要。

保留 bytes 原样，文本工具不负责二进制编辑。二进制文件可以由模型生成的脚本在受限环境内处理，出版通过 byte hash 验证。

### Shell 工具

`LocalShellTool` 解析 `{script,cwd,timeoutSeconds}`，交给 `ProcessSupervisor`。不要让 Server 的 `/tasks` handler 直接执行脚本，更不能把 Task.message 当 script。

ProcessSupervisor 内部：

1. 校验 cwd、超时、参数长度和环境白名单。
2. 创建独立命令身份和输出文件；TOOL_STARTED由Engine在dispatch前统一记录，Supervisor不重复追加。processId作为本地进程登记身份与当前toolCall关联。
3. 用 ProcessBuilder 在工作目录启动 Linux 进程组。
4. 两个独立读取任务同时消费 stdout/stderr；完整落盘与有界预览分离。
5. 等待退出/超时/取消，记录真实退出状态。
6. 返回工具事实，而不把“命令退出1”直接认定为工具协议失败。

可以用镜像中的 `setsid` 建立进程组，通过受控代码取得并核对 pgid；取消时 TERM→宽限→KILL。核对 pgid>1 且不是 Worker 的进程组。不要假设启动器进程PID永远等于实际进程组ID；要在 Linux 测试中验证启动器是否 fork。

Java 的一次 `destroy()` 只针对一个 Process，不能保证派生/脱离的所有子进程结束。无法确认停止时，拒绝继续编辑或封存，并向平台报告 `EXECUTION_ENVIRONMENT_UNSAFE` 请求停止整个实例。

构建工具输出可能填满管道，必须边运行边读，而不是 `waitFor()` 完才读。输出Reader、控制handler不能和单线程Agent执行器共用同一条阻塞线程。

### 原生命令边界

目录/关键词搜索使用 `rg --files`、`find`、`rg`。镜像没有这些命令时返回环境错误，不把每次缺命令交给模型猜安装。

同一Sandbox不保证两个shell调用共享cd；每次传入cwd。后台服务登记句柄与进程组，可查询/停止；封存前处理仍可能写入代码的后台任务。

## 步骤 5：迁移 Context 与历史回查，不重新调参

### 行为与数据流：共享Session历史怎样变成这一次Request

**入口/输出：** `ContextCoordinator.prepare(SessionRuntime,ExecutionControl,SessionLog.Writer,definitions)`最终返回`ModelTypes.Request`。数据源是本地SessionLog/ResultStore，不是上一次Run的内存messages；Summary只是可替换投影。

```text
SessionLog固定Boundary → HistoryIndex + SessionHistoryReader.load
  → HistorySnapshot(Group集合、Summary、through)
  → 当前system/工具定义 + 当前Task原文/已应用Steer + 环境事实 + 历史投影
  → TokenEstimator/主usage校准 → 预算内增量保留
  → 超触发点：保留近期闭合组、摘要旧前缀 → 校验 → 追加摘要事件
  → 重新估计，必要时同摘要能力做强压缩 → 完整Request或明确预算错误
```

**结构的来源：** Position是日志位置；Group由已提交assistant及其所有工具结果形成，不把一轮多工具拆散；Summary的coveredThrough来自被替换源组。ResultRef来自原结果事件，历史读取副本带historyReadback；读取源是原事实，不是摘要里的猜测。Request.messages是本次模型视图，不回写覆盖原日志。字段口径见05第2.4—2.6节。

**迁移与顺序：** 【已有迁移】ContextAssembler.assemble/selectWindow、ContextSummarizer.summarize、TokenEstimator.estimateRequest、ToolObservationPreview.preview及SessionContextService的配对算法；【本步实现】SessionHistoryReader将Mapper读取换SessionLog→Projector→DefaultContextCoordinator→history_read/search。不要整包复制旧Service和RunJournalScope进Core。

**最新结果先保存：** Engine提交TOOL_RESULT后，Projector才能用返回的sourceEvent.eventId生成小结果来源或大结果预览/读入口；不能把未落盘临时ID发给模型。SessionHistoryReader通过Projector重建消息，不要求Engine再维护一份独立可变transcript。observeResponse只更新计量状态，不自己重复append响应。

**预算/失败：** 当前用户prompt计入动态容量；系统/工具与输出保留不能重复扣除。摘要请求有独立ID/purpose/预算，候选未成功持久化不替换旧摘要。一次prepare设置有界处理次数，不能对同一坏响应无限摘要。强压缩后仍超硬预算明确报错；旧验证/旧工作线结果只能作为历史来源，不能提升为当前验证。

**验收：** 同Session连续两Task可见先前事实；强制摘要后仍能按resultId读最初小结果；多tool消息闭合；捕获丢失与预览省略可区分；分页固定through不吞新增历史。先跑固定参数回归，不同时修改模型/阈值掩盖迁移问题。

## 步骤 6：建立常驻 Worker 的 HTTP 受理入口

### 行为与数据流：202、后台执行与控制请求怎么分开

**入口/前置：** AgentWorkerMain读取WorkerConfig→WorkerAssembly.build得到控制壳→AgentWorkerServer注册路由。BOOTING时运行句柄为空，只能初始化/健康检查；`INITIALIZE`走WorkerResources与安装回执，不调用尚不存在的TaskInbox。步骤8装配成功后，普通命令才交给Inbox。

```text
POST /commands → 校验workerToken/有限body → HttpJson.readCommand
  → 静态构造校验 → 验证Q/L/E属于当前实例
  → TaskInbox.accept：短受理锁内核对commandId/digest及taskId+attemptId
       重复：返回原受理身份/sequence，不重做执行
       新Submit：检查IDLE/config/head/deadline → append COMMAND_ACCEPTED
                 → 保存executionId → 建固定Execution(Control/Writer/获授工具) → 保留活动槽
                 → taskExecutor提交Engine.run + finally安全收尾
  → CommandReceipt（首次202；重复可200）
```

**映射表：** AgentCommand完整保留在WorkerSession.Execution，Task/Attempt/Q/L/E不再映射进Core DTO。Worker冻结本地executionId，用origin绑定Writer并装配该次平台工具；deadline进入Control；必要环境消息先记为该次RUNTIME_CONTEXT，再将Submit.message原文交Core。SessionRuntime共享目录/history/ResultStore，不能每Task重建工作树或清历史。

**线程与生命周期：** TaskInbox的receipt/digest索引可从COMMAND_ACCEPTED重建；单任务执行器只跑Engine/Finalizer。控制HTTP、进程Reader、SSE分别有受限资源，不使用一个共享单线程池。单任务队列不是允许同Session积压多个已受理Task，第二个新Task在受理锁内BUSY。多个Session的Worker各自执行，可并行；不需要全平台串行锁。

**Steer/Cancel：** 先核对目标task/attempt。Steer由Control.acceptSteer在同一控制锁下持久受理再入有界队列；Engine消费并记STEER_APPLIED。Cancel可靠记录请求后设置取消，回调在Control锁外打断HTTP/进程，不排进taskExecutor。STOP通过同一Control锁确认没有已受理未应用的Steer，避免“刚接收用户补充却交付旧答案”。

**失败停点：** 受理记录失败则不调度；记录成功而executor拒绝时保留原身份，通过本地失败收尾记录原因。HTTP响应丢失查原commandId；重启发现未完成attempt进入中断处理，不自动重跑Shell。初始化未完成503，状态冲突409，解析错误400/413；安全映射见05第1.1.3节。

**动手顺序：** 【本步实现】WorkerConfig/WorkerSession→TaskInbox.accept及查询→HttpJson/路由→WorkerAssembly生命周期句柄；【仅测试替身】WorkerResources/TaskFinalizer的测试实现。构造器与嵌套WorkerApplication/RuntimeServices见component-methods第1/9节。正式Main在步骤8依赖闭合前不能用Fake返回READY。

**验收：** 同命令发两次只有一次Engine进入；换commandId但同attempt也不能重复启动；慢模型中Cancel仍能返回并触发中断；任务结束后第二Task看见同一目录。这里不等待Server或MySQL即可测试受理行为。

> **动手提示：** 先区分“命令被接受”和“任务已完成”，再区分启动壳与初始化后的RuntimeServices。 最先验证：同commandId发两次只启动一次；慢模型不阻塞cancel；未初始化Submit返回不可执行。 逻辑与检索目标见[09步骤6](09_文档修正与开发导航.md#step-6)。

### 目标

普通 HTTP POST 可以让容器内Agent开始执行；接口不阻塞到任务结束。

### 新建类与职责

`AgentWorkerMain` 装配配置、日志、模型、工具、Engine。  
`AgentWorkerServer` 注册接口。  
`TaskInbox` 做短锁受理、幂等、单活跃任务。

### 启动过程

Worker从配置读取sessionId、worklineId、epoch、workRoot、stateRoot、模型代理地址和受控身份。缺少必要配置退出并记录启动错误；未完成 INITIALIZE 时只开放 live/初始化，不声称 ready。

应用监听0.0.0.0:8081；`/health/ready` 返回实际 Session/Workline/epoch，不能只返回字符串“ok”。平台要验证连到的不是另一个会话。

### SUBMIT受理流程

在HTTP认证及Q/L/E核对后，TaskInbox短锁中：查commandId→核对内容/重复attempt→确认已绑定配置、HEAD、deadline和IDLE→持久COMMAND_ACCEPTED→设置currentTask→提交内部执行器。完成后返回202。重复同内容请求在可变状态检查前返回原事实，不能因当前已RUNNING就把网络重试判为新任务BUSY。

若刚记录受理却执行器拒绝提交，应落明确错误并保留该任务身份，不能回滚日志后假装没受理。重启检测到受理未完成也不自动重复Shell。

以下是`TaskInbox.accept(AgentCommand)`的处理步骤，不是要求创建同名helper：

```text
输入：已解析AgentCommand；前置：认证成功且与Worker固定scope一致
计算canonical command摘要
在受理锁中：
    若commandId已记录：比对原digest，相同返回原receipt，不同拒绝
    核对taskId/attemptId没有被另一命令启动
    核对运行配置、已发布HEAD、deadline和可接收状态
    分配本次executionId（SUBMIT首次受理才生成；STEER/CANCEL查目标Execution）
    event = store.appendHost(COMMAND_ACCEPTED, executionId, 固定origin, 原命令与摘要)
    SUBMIT绑定Writer/Control/工具，把Submit.message原文交Core，保留固定Execution活动槽
    尝试提交执行器；拒绝也不能撤销event，记录明确失败
输出：关联event.sequence的CommandReceipt；HTTP层负责202/错误映射
```

### 控制请求

CANCEL在handler中立即设置线程安全取消信号，不排在长任务后面。STEER先持久确认再排入有界队列，Engine在安全边界应用。

`CHECKPOINT_SESSION/ACK_CHECKPOINT/STOP_WORKER`仅用于后台回收；Task结束不调用这条链。report_progress/create_pull_request走独立平台能力通道。

### 本地联调

实现后启动Worker，再调用本包样例。示例URL仅用于本机联调；云端要使用OpenSandbox解析的端点与headers。

```bash
curl -i -X POST 'http://127.0.0.1:8081/commands' \
  -H 'Content-Type: application/json' \
```

样例包含合成ID/HEAD，须与测试启动配置一致；时间示例不是生产deadline。真正平台请求由Server生成，不让用户手填内部身份。

## 步骤 7：事件流、回答关联与可重连通信

### 行为与数据流：断线续读的是事实，不是重新触发执行

**入口：** `EventStreamHandler.handle(HttpExchange)`读取授权的epoch/after；`QueryHandlers`查询receipt/TaskView。只有初始化后的RuntimeServices提供SessionLog，Boot查询不得伪造空任务执行史。

```text
FileSessionLog.readStored(after, through, limit) → Worker按固定origin投影AgentEvent批次 → SSE完整帧/flush
  → 当前epoch到尾：history.awaitAfter(Position(streamId,最后序号)) → 再readStored
  → 【后续步骤11】Server保存原事件/投影/cursor事务 → 公共事件/Task查询
Task终态 → answerEventId → ANSWER_DELIVERED.responseEventId
         → 原MODEL_RESPONSE.text → TaskView.Answer
```

**游标含义：** Worker是(epoch,sequence)，Server页面是archiveOffset，不互相代替。心跳没有业务序号。旧epoch作为有限历史读到固定末尾后结束，不在当前epoch的Condition上等待旧历史变动。客户端提供未来/非法游标要报错；不能跳过缺失事件后声称连续。

**丢唤醒与慢消费者：** read到尾后，awaitAfter必须在同一追加锁下重查sequence，再条件循环等待。signal只是提醒重读，数据仍在日志。写SSE前不持append锁；每个连接限额与超时，单个用户断网只释放该订阅，不能取消Task或堵住Engine。

**回答区分：** 模型响应已保存不代表已交付，必须有有效ANSWER_DELIVERED引用；被Steer否决的STOP不能展示为answer。已有交付记录而Finalizer尚未成功时，不把任务状态提前改成COMPLETED。reasoning与原始私有事件不直接转发浏览器。

**动手/验收：** 先append两事件再订阅，核对id/data/空行；随后从中间游标重连得到同一原事件；再拆UTF-8字节与SSE行验证解析。查询正文逐字一致、错误scope拒绝、慢连接不挡Cancel。ModelGateway非流式时只展示阶段事件，不伪造逐token数据。

> **动手提示：** 把SSE当日志的读者，而不是事实的唯一存放处。游标表示已确认读到哪里，不是最后看见的字符。 最先验证：事件先产生后订阅也能收到；在read/await交界追加不丢；中文跨字节分片。 逻辑与检索目标见[09步骤7](09_文档修正与开发导航.md#step-7)。

### 目标

断线不丢可恢复事件，不重复执行；前端不靠终端日志猜最终回答。

### Worker SSE实现

`GET /events?epoch=1&after=40` 从本地事实日志读取>40的记录，写成SSE；读到尾部后等待追加通知，再从当前游标读。整个迭代只以日志为事实，不靠一次性的内存广播。

每个event写完空行并flush。心跳使用注释行。单个订阅者慢/断连只释放该连接；有界订阅数防止耗尽线程。不要让Engine同步等待所有订阅客户端写完。

逐token或命令片段可以用于显示，但最终必须追加完整MODEL_RESPONSE/TOOL_RESULT。现有ModelGateway若是非流式complete，就先显示模型阶段与工具阶段事件，不伪造字符流；在本次通信接线里实现经测试的流式适配时，原始最终响应仍是唯一回答事实，不允许删掉它。

### 自然回答关联

依次记录 MODEL_RESPONSE → ANSWER_DELIVERED → TASK_FINISHED。ANSWER/TASK事件引用原始响应eventId/modelCallId。持久查询只沿这个引用取文本。

Worker若在完整响应保存后、终态前崩溃，这条响应不能自动成为最终回答：要依据已经提交的终态决定，未决定则中断。

### 测试

`EventReplayIT`：订阅在事件产生之后建立仍能收到；重连从cursor续；同一记录重复传输不改变其身份；慢订阅不阻塞Agent；append和订阅注册交界不丢帧。

`AnswerReferenceTest`：工具调用前文字不是最终回答；被steer推迟的STOP不是最终回答；正文空或reasoning-only拒绝；页面刷新取到完全同一正文。

SSE协议依照WHATWG格式，实现自己的Java/前端解析器时必须测试分帧和UTF-8边界。[S07]

## 步骤 8：分离本地Task收尾、恢复快照与显式平台工具

### 行为与数据流：本步有四个入口，不能塞进同一个finish方法

**前置：** 本地日志/工具/Context可用；步骤6/7只验证过接口时，在这里替换测试Resources/Finalizer。生产装配只在真实目录安装成功后激活，实例锁始终在待替换state之外。

| 入口与返回 | 需要的数据 | 调用链与持久化位置 |
|---|---|---|
| INITIALIZE → 安装回执/ready | 固定bootstrapId/hash、Q/L/E、配置digest | receiveBootstrap→BundleCodec验证staging→PREPARED安装意图→完整安装→INSTALLED→打开Log/ResultStore→装配→记录WORKER_READY→发布运行句柄 |
| `TaskFinalizer.finish(acceptedCommand,outcome)` → 本地结束 | AgentOutcome及本attempt进程 | closeInput/FINALIZING→stopAllAndConfirm→TASK_FINISHED→IDLE；不生成ZIP或Commit |
| `report_progress` → CallResult | 本toolCall、固定operationId、expectedHead、树/说明 | 记平台操作意图→sealProgress→固定PROGRESS export→平台发送/查询→已确认结果→安装该export对应baseline |
| CHECKPOINT/ACK/STOP → 后台回执 | 真空闲实例、RECOVERY、连续事件覆盖、archiveId | QUIESCING→固定树/日志/基准→RECOVERY_CHECKPOINT_READY→平台保存后ACK→CHECKPOINT_STORED/PARKED→STOP |

**数据结构：** ExportManifest说明scope/purpose/条目/throughSequence/digest；ObjectFile是私有导出句柄(path不进模型)；ResultStore.Ref是字节引用，不等于Manifest。BOOTSTRAP/RECOVERY包含STATE+BASELINE，PROGRESS只包含固定TREE。install.json是当前实例安装控制记录，不是复用旧实例控制权的恢复材料。

**初始化重试：** 相同command/bootstrap/hash返回已保存结果；INSTALLED后不能再次从原包覆盖已经修改的工作树。PREPARED崩溃只按同一输入恢复未激活安装。多目录移动不是单个事务，以安装意图/校验核对进度；旧epoch/目录与新epoch不能同时写。WORKER_READY先落日志再向HTTP发布完整RuntimeServices，发布前不能有handler拿到半装配组件。

**封存与外部未知：** Sealer取得写入屏障，确认后台写进程、固定文件集合和日志Boundary再复制；不能假定慢ZIP期间目录没有变化。外部调用前operationId及输入已持久，网络超时只核对原ID；新平台副作用/回收被阻止，但原任务可如实回答。baseline只按被确认的固定树更新，不能用稍后活动目录替代。

**动手顺序：** BundleCodec/ExportStore→LocalWorkerResources安装→LocalTaskFinalizer→Sealer的RECOVERY/PROGRESS→Worker侧PlatformCapabilities接口/HttpPlatformCapabilities及平台Tools。create_pull_request先保留端口/参数契约，实际通用PR实现留后端阶段；平台未接通则不授予该工具。显式发布在步骤14接真实平台，测试Fake只验证协议和故障，不计产品成功。

**验收：** 本地空壳PUT包→INITIALIZE→两Task；重复初始化不清草稿；自然STOP零次发布；RECOVERY下载/ACK/STOP可恢复同一树；PROGRESS不能恢复Session；归档失败保留唯一副本。详细安装算法仍在09第3节，封存/平台路径在08，不再创造另一套文件树恢复器。

> **动手提示：** 先用本地目录证明空壳可导入bootstrap并跑两条Task，再测显式发布与RECOVERY；不要从Sealer接Task终态。 最先验证：打开日志之前完成安装；重复INITIALIZE不覆盖已修改文件；零次report_progress产生零次发布。 逻辑与检索目标见[09步骤8](09_文档修正与开发导航.md#step-8)。

### 目标

完成Worker生产装配：自然结束不等待网络发布；有能力显式发布和创建PR；后台可保存完整恢复状态。真实平台网络在步骤14/15接，当前用独立Fake平台测试，不交付假实现。

### 实现顺序

先BundleCodec/ExportStore区分BOOTSTRAP、RECOVERY、PROGRESS；再SessionSealer实现sealProgress与checkpoint；再HttpPlatformCapabilities连接PlatformOperationClient；然后注册ReportProgressTool/CreatePullRequestTool。最后LocalTaskFinalizer只做本地安全收尾，WorkerResources暴露后台checkpoint/ack/stop，不依赖TaskFinalizer做这些事。

完整方法体算法在08第5—8节，方法签名在contracts/component-methods.md。封存固定文件集合、日志边界、路径hash和原始字节；导出区不进入自身归档。PROGRESS不打包Agent历史，更不能更新latestRecoveryArchive；RECOVERY必须含状态和已确认baseline。

### 异常处理

PROGRESS封存失败只返回当前工具失败，安全确认后允许后续本地任务，不引入Task级WAITING状态。发生未知平台响应保存operationId，禁止新的平台副作用和回收；实际结果通过GET同id核对。

后台checkpoint失败续期/保留环境；不可确认停止的子进程则BLOCKED并请求平台停止实例。Task取消不撤销已发布Commit。具体故障不能用一个统一“模型失败”掩盖。

## 步骤 9：把独立 Worker 放进 Linux 镜像并接 OpenSandbox

### 行为与数据流：同一个Worker换宿主，不换执行语义

**入口：** 【本步实现】`SandboxControl.create(LaunchSpec): Binding`与`endpoint(Binding): WorkerEndpoint`；实际方法以component-methods第3节为准。Core/Worker不import SDK，SDK只在Server适配器。环境探针可先验证，正式验收必须使用步骤8的真实Worker。

```text
固定LaunchSpec(Q/L/E, createOperationId, image/volume, 配置与受限token)
  → OpenSandboxControlAdapter → 真实实例Binding
  → resolve WorkerEndpoint(baseUri + routingHeaders)
  → live → 上传BOOTSTRAP → INITIALIZE → ready(Q/L/E/config/head)
  → 连续Task/SSE → renew → destroyAndConfirm
```

**谁赋值：** 平台分配Q/L/E与createOperationId；供应商返回sandboxId/端点；Worker从环境读取相同身份。Worker不生成worklineId，endpoint不进用户页面。把两个方向分开：Server到Worker的管理通信，Worker到ModelProxy/平台能力的出站通信。

**动手顺序：** 先在Mac完成Java，本机Linux或Windows Linux执行宿主准备镜像→独立控制探针→真实Worker初始化→两Task+SSE→卷/续期/销毁。每次记录实际镜像架构与digest，Mac ARM镜像不默认可在Intel执行。每条shell直接在常驻沙箱内运行，不再每工具创建一个Docker容器。

**失败/验收：** 创建响应丢失按createOperationId/metadata查原实例，不无限重复create；ready scope不符拒绝绑定；destroy超时保留UNKNOWN而不是删除记录。SDK close仅关client。断开SSE不结束Task，同卷不并挂双写者；跨机地址和代理headers按06实测，不能拿localhost猜。

> **动手提示：** 供应商只负责提供可访问的环境。先记录SDK实际端点及headers，再接你已经本地跑通的Worker。 最先验证：跨两机先跑独立探针；readiness不能在INITIALIZE之前要求IDLE；控制流与模型回连分别验证。 逻辑与检索目标见[09步骤9](09_文档修正与开发导航.md#step-9)。

### 目标

证明供应商只负责环境，Worker本身不依赖OpenSandbox SDK。

## 步骤 10：平台 Session 初始化与工作分支创建

### 行为与数据流：固定Commit怎么变成Worker的初始目录

**本步仅接Harness必要平台边界。** 复用已有RepositoryAccessService、RepositoryRevisionService、ObjectStorage/GNOV codec；不在这里实现通用PR、同步或通知消费者。数据行/SQL仍依05/16，生产迁移先核对真实库，不直接运行目标DDL。

```text
公共创建请求 + actor/幂等键
  → RepositoryAccessService鉴权 → TX-S1固定Commit A与Session/初始Workline/Binding意图
  → 事务外CommitTreeService.load(repoKey,A)得到完整path→blob映射
  → 逐Blob读取 → RepositoryBootstrapService构造BOOTSTRAP + 固定manifest/hash
  → SandboxControl.create + uploadBootstrap + INITIALIZE
  → ready事实核对Q/L/E/A/config
  → TX-S2建指向A的受管分支并激活Binding → 公共Session结果
```

**来源与去向：** repoKey由仓库鉴权结果给出；A首次准备后固定，main后来推进不改变本次树。worklineId在TX-S1创建持久化，epoch从Session单调分配；LaunchSpec→WorkerConfig→WorkerSession/日志与平台工具适配器传同一身份。SessionRuntime只向Core提供本地会话资源，不承载平台绑定校验。BOOTSTRAP是文件和状态包，不是Task消息，也不是把自定义Git当原生git clone。

**副作用：** 数据库短事务只保存意图/激活，对象读取、ZIP、HTTP、SDK在事务外。每个外部动作使用已保存的bootstrapId/createOperationId；未知结果先核对原动作。ready仅表明准备实例可运行，平台最终激活前不允许模型/平台副作用。分支创建是引用已有A，不新造一个空Commit。

**动手/验收：** 先用固定A把两个Blob还原到包并逐字验证，再接Worker安装，最后接事务激活。模拟main推进、包损坏、ready响应丢失和重试：仍是原A、原Q/L/E，不重复分支；已有Session失败也不能由临时清理删除用户目录。

**本步同时建立初始Workline，不能等同步阶段再加。** 新增WorklineRows/WorklineMapper；Session不再拥有永久唯一分支。所有事务前置repo门闩，再Session，完整顺序见05/16。数据库目标只有schema/target.sql.reference，真实迁移先H0比对，原编号不改变。


> **动手提示：** 先画A对应的path→blob→真实文件字节。bootstrap不是镜像，也不是调用git clone。 最先验证：main在创建中推进到B，Session仍从A启动；并发创建不会建两条工作分支。 逻辑与检索目标见[09步骤10](09_文档修正与开发导航.md#step-10)。

### 目标

一个完整Session从创建到ready可用；慢环境操作不占着数据库事务。

### 现有可用入口

`RepositoryAccessService` 保留鉴权职责；`RepositoryRevisionService` 可解析源分支的固定HEAD；旧 `AgentSessionService` 的“持久准备→外部物化→短事务激活”思路可参考，但其Workspace依赖退出新链。[G02][G09]

### 新接线

平台新增 `SessionLifecycleService` 是确定的新入口；已有Controller显式按executionBackend分派。最终新系统只调用新分派，旧分派仅在迁移期间用于旧任务收口。

数据库按05/16及目标DDL核对Session+Workline增量字段；实例信息放独立binding记录，新Task写agent_control_task，不套旧Task CHECK。不要再保留一个新Workspace表作为当前目录状态真源。

实施顺序：

1. 验证仓库写权限——创建工作分支不是纯读操作。
2. 以用户/仓库/请求幂等键解析已有Session。相同键但不同源选择返回冲突。
3. 固定源HEAD=A、会话Q、工作线L1/分支及实例epoch，短事务准备Session、Workline(PREPARING)、Binding。
4. 事务外准备Sandbox、导出A、启动/初始化Worker。
5. ready通过后，短事务创建指向A的新分支并绑定L1，标Workline ACTIVE、激活Q.activeWorklineId与current_runner_epoch，sessionVersion递增。
6. 任一步失败记录可重试/不可重试原因；重复请求核对已有资源，不重新读取新的main HEAD替换A。

分支创建只插引用，不造空Commit；不能直接调用首次push方法时传错expectedBase而导致拒绝。通用BranchService接收“创建指向既有Commit”的显式操作。

### 数据库迁移要求

以步骤 0最新migration编号为准追加迁移，不编辑已经执行的旧migration。不马上DROP旧workspace外键/列；先让旧历史可读取，再在退役步骤删除新执行链不再使用的关联。

## 步骤 11：平台 Task 接收、发送与状态投影

### 行为与数据流：平台保存意图，Worker执行，事件解释结果

**入口/返回：** `TaskApplicationService.submit(...)`接收公共message/expectedWorklineId/expectedSessionVersion/Idempotency-Key；Controller从认证取得actor，不接受用户填私有命令/工具权限。返回Submission/Task查询位置，不同步等待模型。

```text
公共请求 → TX-T1：旧key核对 或 新Task+活跃槽+固定Attempt/Command
  → COMMIT → CommandDispatcher.dispatch(commandId)
  → AgentWorkerClient.send(已保存的信封) → Receipt/UNKNOWN
Worker SessionLog → EventCollector → EventProjector.archiveAndProject
  → TX-E1：原事件 + Task/Attempt投影 + 连续cursor 同事务
  → 公共TaskView/answer；终态只清对应的activeTask/currentAttempt
```

**数据结构与两次受理：** public Submission来自平台持久意图，private Receipt来自Worker受理日志；两者都不是最终answer。就绪环境才分配并冻结attempt/command；普通回收中先存PENDING_DISPATCH，恢复原线后再补固定执行身份。commandId重试固定，新的Recovery attempt只能由明确恢复流程建立，不由Dispatcher网络异常决定。

**锁/失败：** 按TX-T1顺序查同幂等键，再判断可变状态；过期HTTP响应不能把终态退回ACCEPTED。数据库提交后发送前崩溃，由已有Command记录扫描派发；Worker受理后202丢失，查receipt/原样重发。这里的定时器只发粗粒度命令，不运行Engine。事件缺号先补齐，不能用最大sequence跳过缺失前缀。

**动手顺序：** 复用权限/Controller入口→新增控制表Mapper与Task事务→Client/Dispatcher→EventProjector→EventCollector。先用测试HTTP Worker验证同命令恢复，再接步骤9真实Worker。多个Collector可以靠MySQL唯一约束+事务幂等，暂不新增分布式订阅调度器。

**验收：** 两客户端竞争一个活跃槽；两个崩溃点重试只对应一次实际attempt；旧epoch终态只更新旧历史；answer引用完整原响应且权限正确。只查到QUEUED/ACCEPTED不能宣告Runtime已执行。

Task请求固定expectedWorklineId/expectedSessionVersion，Server在受理时冻结workline_id。MERGED工作线不阻止对话或本地分析；仓库发布需线ACTIVE。显式SYNC gate拒绝新Task且保留用户输入，普通后台回收可以先持久受理排队再恢复原线。两者不是同一个门槛。


> **动手提示：** 先列两个崩溃点：DB提交后HTTP发送前，Worker受理后响应丢失。两者都必须能查到原身份。 最先验证：注入两处崩溃仍只执行一次attempt；两客户端并发Submit只能占一个活跃槽。 逻辑与检索目标见[09步骤11](09_文档修正与开发导航.md#step-11)。

### 目标

不使用Agent MQ派发，但Server崩溃或HTTP响应丢失后不会丢任务、重复执行。

### 新平台组件

`TaskApplicationService`：业务受理和活跃槽。  
`AgentWorkerClient`：HTTP发送/查询，仅负责传输。  
`CommandDispatcher`：核对未确认的粗粒度命令。  
`EventCollector`：从Worker订阅事实事件。  
`EventProjector`：幂等归档并更新公共查询状态。

这是职责清单，不要求每个helper再做接口+impl两套类。

### 受理事务

锁Session，按幂等键先查Task，再检查activeTaskId；创建Task、attempt、control-command并预留活跃槽。同一事务提交。

事务后安排发送任务。Server响应202只表示Server已保存请求。核对器扫描待发送记录，可以是定时器；这是防止“事务提交后进程挂掉”导致任务悬空，不是重新把Agent执行安排到服务端线程。

### HTTP结果处理

- 202/重复200：记录已受理。
- 400/403：明确拒绝，向用户给出原因，按状态释放未执行的槽。
- 409：先判断同任务还是另一个任务；不吞掉身份冲突，不自动造新attempt。
- 连接错误/超时：标UNKNOWN，查询原commandId或原样重发。
- Worker不可达：核对Sandbox状态；没有确认旧实例死之前，不能另启Worker挂相同卷。

### 事件归档

新表逻辑名 `agent_event_archive`：UNIQUE(session_id,runner_epoch,sequence)、UNIQUE(event_id)，保存payload摘要与归档offset。不要依赖生产旧agent_step的fenced append强行写新事件。

保存原事件、更新连续cursor、更新Task投影在同一个短事务。收到终态时校验引用原MODEL_RESPONSE已存在且归属/STOP条件满足。缺前置事件则先重放，不能“终态先到了就直接找最新assistant”。

如果Server多副本都订阅同一Worker，可以让数据库幂等去重，先不建设分布式订阅调度。Sandbox创建/重建仍需数据库绑定CAS防重复，不将多副本写权交给内存Map。

### 测试

## 步骤 12：接通模型代理和取消路径

### 行为与数据流：请求由Core组装，凭据由平台持有

**入口：** `ModelGateway.complete(Request,ExecutionControl)`；【已有迁移】OpenAiCompatibleModelGateway的请求/响应/错误分类与thinking往返；【本步实现】纯JavaGateway装配和ModelProxy授权转发。模型主key不进入Worker或Task。

```text
Context产生Request → Gateway编码provider请求并注册取消回调
  → modelEndpoint + modelToken + modelCallId → ModelProxy
  → 校验当前Q/L/E/用途/模型/限制 → 固定供应商出口（替换认证头）
  → 原响应/错误返回Gateway → Response(text,reasoning,toolCalls,finish,usage)
  → Engine持久记录；finally清除本次取消回调
```

**配置来源：** model/thinking/maxOutput来自冻结RuntimeConfig；endpoint/token来自WorkerConfig和部署注入，不由模型选择任意URL。Proxy不改messages、不从数据库重新拼上下文。providerRequestId供排障，modelCallId由Harness稳定关联这次请求，二者不混用。

**取消与异常：** registerCancellable必须处理“注册前已取消”，控制线程关闭正在等待的HTTP call；Proxy断开下游时尽力取消上游。已经发出的调用可能仍计费，usage未返回记缺失，不声称0。网络重试沿已有明确分类并有次数上限；未知响应不推断工具已执行，坏tool JSON仅在可形成安全纠偏上下文时有限纠偏，不能直接dispatch。

**验收：** 主/摘要thinking配置分开且tool turn所需reasoning完整保留；取消慢请求及时返回；错误令牌、任意upstream URL、禁用模型拒绝；关键配置不进日志。先测固定请求/响应，再真实模型read→edit→shell→STOP，逐层对应modelCallId和工具事实。

> **动手提示：** 只转发授权后的固定模型出口，不重新组装messages。取消本地等待不等于供应商撤销收费。 最先验证：请求中upstream URL不能改变真实目的地；Token不落进日志；取消贯穿Worker和Proxy。 逻辑与检索目标见[09步骤12](09_文档修正与开发导航.md#step-12)。

### 目标

Worker能在网络受控的Sandbox中调用模型，但拿不到平台数据库与供应商主凭据。

### 实现范围

继续复用当前模型请求/响应协议。当前Gateway的职责是解析响应并保存text、工具调用、thinking和usage；抽掉Spring配置后留在Worker。[G08]

## 步骤 14：复用托管底座发布 Commit 和工作分支

### 行为与数据流：显式保存代码不等于结束任务

**入口：** Worker的PlatformCapabilities.reportProgress，经固定PlatformOperation.Request进入平台；不是TASK_FINISHED回调。仅接Harness的显式发布，通用PR的业务实现留步骤15后续阶段。

```text
ToolCall → 固定operationId + PROGRESS export/hash/expectedHead
  → PlatformOperationService受理意图 → ArchiveService下载并验证固定树
  → PublicationService固定author/parent/time/message，构造GNOV对象
  → BranchPublicationService短事务：CAS + CommitRecord + 操作结果 + 既有Outbox写入
  → Worker按原operationId查询SUCCEEDED/PUBLISHED或NO_CHANGES
  → 确认treeDigest → 安装对应固定baseline → PROGRESS_RECORDED → 工具结果
```

**数据来源：** repo/branch/author来自平台可信scope；文件来自已封存export，不从Worker当前活动树临时重读；message是本次操作输入，timestamp/parent首次固定后复用。operationId是业务幂等身份，exportId是树包身份，publication不是taskId一对一。一Task可零次/多次发布，完成answer不改变这个数量。

**锁与故障：** 对象先准备、Branch CAS是可见发布点；昂贵校验不持DB锁。CAS冲突保留旧HEAD并返回冲突，不改父提交静默重试。对象写完DB失败可留下不可见对象；DB已提交响应丢失查询原操作，不制造新Commit。只有RECOVERY更新恢复档案，PROGRESS不可用于恢复全会话。

**动手顺序：** 【已有迁移】TransferService的对象校验/Branch更新和ObjectStorage、codec/hasher→窄BranchPublicationService→PublicationService→操作HTTP。保留业务Outbox事务写边界，但通知消费者不是本链的放行前置。

**验收：** 同树重复操作同Commit；新操作可产生下一Commit；任务取消后已发生提交不回滚；恢复为初始内容也要相对当前publishedHead判断；权限撤销/CAS冲突不覆盖别人。Worker确认之前只展示未知/处理中，不宣称已保存。

先按11/16把普通Push、Agent发布和PR最终提交统一为repository门闩内的Branch写入口；共享Outbox表与事务写端口此时建立。Agent发布目标由workline_id→source_branch_id派生，必须线ACTIVE且绑定scope匹配。已受理操作的异步完成与初次授权分开，取消Task不撤销旧副作用；sync/merge等待其状态确定。


> **动手提示：** 先固定一份不可变PROGRESS树和operationId。完成的是仓库副作用，不是Task终态。 最先验证：分支已推进但HTTP响应丢失，重试仍返回同一个Commit；UNKNOWN不生成新身份。 逻辑与检索目标见[09步骤14](09_文档修正与开发导航.md#step-14)。

### 目标

### 提取位置

从现有 `TransferService` 提取可复用的对象完整性、Commit索引、Branch更新逻辑。保留外部Push的expectedHead与fast-forward合同；Agent出版不要绕HTTP上传包。[G05]

新增 `PublicationService` 编排export，通用 `BranchPublicationService` 承担仓库更新。`ObjectStorage`、`GitObjectCodec`、`GitObjectHasher`直接复用。[G06][G07]

### 幂等身份

Publication使用UNIQUE(sessionId,exportId)。创建时保存固定timestamp、message、author、expectedHead；重试读这份记录，不再次生成时间或调用模型起提交说明。

提交说明可由任务标题生成可编辑默认值，不能为了生成message再增加一次必须成功的模型调用。

### 具体算法

只从PlatformOperationService已持久受理的REPORT_PROGRESS进入。完整顺序：固定operationId与导出树→下载并校验purpose=PROGRESS→唯一Publication→固定parent/time/message→构造对象→短事务Branch CAS与operation结果→Worker查询原结果并更新对应baseline。详见08第5节和05 TX-P1/P2。

不再从TASK_FINISHED或RECOVERY_CHECKPOINT_READY自动调用PublicationService。一个Task可以多次调用，publication由operationId唯一，不以taskId唯一。操作超时可能已提交，必须原ID核对；CAS冲突不换父HEAD自动force。取消不会回滚Commit。Task槽由终态投影独立释放。

### 特殊测试

`PublishTest` 必须测试：A→B正常、B→C追加、工作树撤销为A仍发布新Commit、重复请求timestamp不变、对象已写但数据库失败、Branch更新成功返回丢失、权限被撤销、平台收到不属于本Session的包、平台操作结果响应丢失、NO_CHANGES不生成空Commit。

### 注意现有关系索引

`commit_record.branch_name` 不能作为一个Commit只属于某分支的唯一真相；同一Commit可以被多个分支引用。历史查询以分支HEAD沿parent回溯/可重建索引为依据，不用单一branch_name筛选伪造历史。[G05][G06]

## 步骤 16：生命周期、恢复与安全基线收口

### 行为与数据流：恢复状态，不盲目重放副作用

**本步先验收原工作线Harness恢复，不等待通用PR/显式sync。** LifecycleReconciler只管理实例准备、续期、回收、恢复；WorkerRecovery只解释安装后的本地历史/进程事实。它们不运行第二个AgentLoop。

| 场景 | 输入与身份 | 恢复输出/停止边界 |
|---|---|---|
| 同一已确认Binding、本地进程重开 | 当前卷、有效安装标记、原Q/L/E、独立进程锁 | 校验日志，保留序号；未完成attempt标中断，不自动重跑Shell |
| 实例被回收/从RECOVERY重建 | 平台确认的包/连续覆盖、原Workline、重新分配的epoch | 旧日志原身份只读，新epoch从1追加；当前树与baseline一致才READY |
| 模型/工具进行中崩溃 | TOOL_STARTED或MODEL_CALL_STARTED但无完整结果 | 记录未知/中断，用户继续时建立新attempt；不能伪造exitCode或成功 |
| 发布HTTP结果未知 | 原operationId、固定export、平台结果 | 核对对应树与HEAD后继续；不能仅把HEAD换新而保留旧文件 |
| 唯一环境可能仍有写者 | 管理面无法确认停止 | BLOCKED/UNKNOWN并保留资源，不把同卷挂给第二个写实例 |

**回收调用链：** 核对无active/pending Task、写进程及未决平台操作→Worker CHECKPOINT→平台验证并持久RECOVERY和连续事件→ACK→Worker PARKED→STOP→管理面确认销毁。每一步都有原command/export/archive身份；超时先核对，不倒退已保存事实。活跃长模型调用不是空闲，业务idle计时不由SSE心跳更新。

**动手/验收：** 先本地日志重开，再杀Worker中断一次实际命令，最后销毁一次性Sandbox并从已确认归档重建。原卷未停止拒绝接管，归档失败不删除唯一副本，恢复树缺失不借旧历史宣称已完成。网络隔离/同UID攻击的未验证能力继续明确标注，不因恢复成功就宣称任意多租户安全。

> **动手提示：** 先说明每种恢复承诺：当前卷重启、可信RECOVERY恢复、结果未知。不要把任意点无损续跑当默认。 最先验证：归档失败不删除唯一副本；旧实例死亡未确认不挂同卷启新Writer；旧包晚于/早于HEAD要核对。 逻辑与检索目标见[09步骤16](09_文档修正与开发导航.md#step-16)。

### 目标

环境能长期工作也能被回收；故障后状态可解释，不留下运行中的孤儿或假完成。

### 生命周期管理

使用已计划的 `LifecycleReconciler`，不再新增同职责Coordinator，只处理Session级准备、续期、闲置封存、停止和恢复，不观察每个文件版本。

定时器使用有界线程和稳定Session身份。RUNNING/FINALIZING不按普通idleTTL回收；模型无输出时依靠独立health/当前task查询判断。

清理发生网络失败时保持DELETING/UNKNOWN，不写DELETED；重试并核对实际实例。通过metadata查孤儿实例时分页完整读取，只删除确认无现有绑定的受管实例。

### Worker崩溃

控制面先确认旧进程/实例停止且没有残留写者。恢复有保存的卷时，校验日志，当前未完成attempt标INTERRUPTED。不要自动执行旧TOOL_STARTED对应命令。

用户继续建立新的attempt，模型收到中断说明、当前代码/未发布改动和历史结果边界。只要平台还无法确认旧实例死亡，不挂同一可写卷起新Worker。

### 恢复到归档

验证bundle摘要与来源，新的epoch、恢复起点、旧已发布HEAD都在启动记录中明确。若事件档案比代码恢复点更新，超出覆盖的旧轨迹只作历史，不纳入“当前已完成进度”。

一个发布完成而HTTP结果丢失的操作，恢复时以原operationId查询平台结果，不重复构造Commit。旧恢复包不匹配新HEAD时不能只换HEAD。

### 安全基线与后期加固

现在就实现Session/epoch核对、大小/时间/资源上限、压缩包安全、凭据外置、管理端点不公开。高级网络隔离与不同UID/执行隔离可以在本步骤集中完成；未完成以前只允许受控测试，不把任意多租户安全标为已完成。

SDK/模型代理HTTP日志必须遮蔽敏感头。不能把控制token、供应商key写进用户可读取的repo或Prompt。

### 验收

`LifecycleIT`：Server重启不重跑Agent、Worker重启识别中断、TTL续期、闲置回收、卷重挂、从归档新环境恢复、旧实例未确认停止时拒绝接管、回收失败不撒谎、权限撤销无法再发布。

## 步骤 17：切换新任务并退役旧执行链

### 行为与数据流：迁移的是执行入口，旧证据不改写

**入口/前置：** 新Harness的创建、Task、两Task连续性、取消、回答、显式发布与原线恢复已有真实验收；基线/WIP可找回。通用PR/社交功能不作为移除旧Agent执行器的理由或阻碍，但仍在使用旧组件的独立业务不得误删。

| FinishTaskTool/旧CompletionInspector | 新链不装配；历史只读转换 | 新回答查询和旧历史兼容通过 |
| 旧自动Review/专属QA执行入口 | 停止受理并退役，不新增兼容执行适配器 | 触发器/调用方已移除或明确410，已有任务收口、旧报告可读 |
| GitObject/Branch CAS/权限/PR | 保留并复用 | 不是删除对象 |
| RabbitMQ通用依赖 | 按其他业务实际使用决定 | 不能由Agent退役推导全平台删除 |

### 失败回退

新链出现故障时，暂停新Task、保留当前Sandbox/归档、修复后继续。不能将新Session随手标成legacy让旧Runtime读取不认识的新状态。代码部署回退与业务状态回退不是同一回事。

### 行为与数据流：本轮Harness交付如何收口

完整Harness验收必须覆盖03中对应的功能与故障场景；通用PR/社交/通知按各自产品章节验收，仍未实现的保留NOT_RUN，不据此宣称整个GitNova已经完成。下面是贯穿流程的真实演示，不能代替完整验收矩阵：

```text
已有本地测试仓Push到GitNova → 创建固定A的Session/Workline/Worker
  → Task1实际读改测 → 原始事件/工具结果 → 正常answer或真实失败原因
  → Task2读取Task1的文件与历史 → 页面刷新/另一客户端仍见同一结果
  → 另测取消、摘要后回查、显式report_progress与恢复
```

**证据包：** 记录源码commit/配置digest/镜像、Session/Workline/Epoch/Task/Attempt、模型调用ID、事件范围、最终answer引用、实际文件/测试与发布HEAD；密钥脱敏。脚本模型证明控制流，真实模型证明接线，独立测试证明产物，三者分别记录，不以“正常STOP”代替代码正确。

**完成判断：** Core不依赖平台框架、工具不逐次经Server操作Workspace、连续Task/取消/事件回放/原线恢复实际可用、新入口不再双派发旧Runtime。文档/Schema检查仅证明资料一致性，不代填生产PASS。不重新跑无关实验来掩盖缺失功能，也不为了凑工期承诺尚未验证的故障保证。

> **动手提示：** 先把设计证据、隔离探针、真实数据库/容器、真实模型四种结果分开登记。 最先验证：显式发布链与透明回收分别演示；测试总数>0；真实回归不从Mock PASS推导。 逻辑与检索目标见[09步骤18](09_文档修正与开发导航.md#step-18)。

### 必须演示的一条路径

干净环境部署 → 仓库Commit A → Session分支A → bootstrap/INITIALIZE/ready → Task1中显式report_progress产生B → 显式create_pull_request产生Draft → 自然回答（不自动提交） → Task2显式report_progress产生C → PR更新 → 变为Ready → 合并请求固定S/T/revision并核对干净状态 → merge → 原历史保留 → 下一工作Session固定目标H并由bootstrap装入新Worker。另测零report_progress的Task完成后零Commit，以及纯空闲CHECKPOINT/ACK/STOP。
