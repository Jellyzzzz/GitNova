## 开始前：三条写代码的方式

**先写一个可观察行为，再实现它。** 例如先构造“同一任务 POST 两次只能启动一次”的测试，再写受理逻辑，而不是先建十个 DTO 再想调用关系。

**按责任拆类，不按每个动作拆 Service。** 本地日志一个写入者、Worker 一个任务执行器、平台一个窄的 WorkerClient，足以表达多数行为。不要每个字段再包一层 provider。

**核心实现由你写。** 可让模型解释代码或指出反例；完整输入、输出、失败条件以本文为依据。改动后要能回答：为何这个位置需要持久化？什么已经发生？重试会不会重复？

## 步骤 1：建立三个独立模块与协议样例

### 目标

新 Agent 编译时不把平台 Boot 依赖带进去，Server 能引用共享协议而不依赖 Agent 实现。

### 修改位置

新增 `agent-runtime/{agent-protocol,agent-core,agent-worker}`，都放在 `com.gitnova.agent` 包下。Server 继续保留根 `src/`；不要先移动整个仓库。

protocol 编译目标17，core/worker编译目标21。远端根 pom 的 Java 17 与未来 Worker21 是明确差异；不通过直接共享21字节码让原Server意外升级。[G01]

### 实现顺序

1. 建立聚合 pom，统一测试依赖与编码，不继承平台的全部 dependency。
2. `agent-protocol` 定义 `AgentCommand`、`CommandReceipt`、`AgentEvent`、`TaskView`、`WorkerHealth`、稳定错误码。
3. 根据架构文档定义字段约束。不要把用户输入 JSON 直接转 Map 后透传到所有内部方法。
4. 将本包 `examples/` 作为测试 fixture。相同语义但字段顺序不同的请求，生成同样的规范化摘要。
5. Worker 最终打包为可执行 JAR；可使用显式的打包插件，但产物命名稳定为 `agent-worker.jar`，不默认使用 SpringBoot repackage。

建议接口骨架：

```java
// 新建的协议草图；逐字段校验在构造/解析边界实现。
public record AgentCommand(
        int schemaVersion, String commandId, String sessionId,
        long runnerEpoch, CommandType type,
        String taskId, String attemptId, JsonNode payload) {}
```

不要在共享协议中暴露 `AgentStepEntity`、数据库 Mapper、`WorkspaceBinding` 或供应商 SDK 对象。

### 验收

写 `ProtocolRoundTripTest`：中文、多行任务、引号、`$(touch /tmp/not-a-task-command)` 均原样反序列化；非法类型/缺字段明确失败。

写依赖检查，确认 core 的依赖树里没有 `spring-boot`、`mybatis`、`amqp`、OpenSandbox。Server 仅依赖 protocol，而非 core。

实现后运行：

```bash
mvn -f agent-runtime/pom.xml clean install
mvn dependency:tree
```

依赖版本按步骤 0与接入验证固定，不能把 `{latest_version}` 留在最终 pom。构建版本号只是技术身份，不是产品缩水计划。

## 步骤 2：先做本地日志与完整结果存储

### 目标

离开 MySQL 以后，Agent 的原始事实依然可靠可查；不是先把所有内容塞内存，之后再补持久化。

### 新建责任

`FileSessionLog`：一个日志写入者、分配序号、读历史、恢复尾部。  
`FileResultStore`：完整命令输出/大结果保存、摘要、稳定资源身份。  
`FileSessionLog/HistoryIndex（本步仅落盘与索引；完整恢复见步骤 16）`：从日志和最近摘要构造会话状态。

### 写入算法

`append(eventType,payload)` 在短写入锁内确定 sequence，编码一条完整 JSONL，写入 FileChannel。需要耐久确认的记录完成 force 后，才返回 eventId 并通知事件订阅者。失败不能继续假装该响应已经记录。

事件分配和磁盘追加由同一个写入者负责；不要多个线程各自 `sequence++` 再抢着写。

大结果先写唯一临时文件，计算摘要并关闭/force，再原子改名为最终对象，然后在日志中追加引用。实际返回路径的映射以不可变 resultId 为主，不以当前容器路径为长期身份。

### 崩溃处理

启动逐行检查。只允许最后一条不完整记录被隔离/截断；完整行中部校验失败或序号断裂要返回恢复错误。先保存坏文件证据。

看到 `TOOL_STARTED` 没有对应结果时，标为结果未知；不能据此重跑工具，也不能编造一个 exitCode。

同一环境重启继续已有 epoch/sequence；从较早快照重建用平台分配的新 epoch，旧日志只读保留。

### 测试

`SessionLogTest` 覆盖并发追加仍有序、写失败不确认、尾行截断可识别、中间损坏拒绝恢复、重复 eventId 内容不同报错。

`FileResultStoreTest` 覆盖小结果和大结果均有稳定身份、写文件后日志前崩溃只留下孤儿、结果缺失明确报错、摘要不匹配拒绝读取。

### 为什么这不是重 Workspace

这里管理的是 Agent 自己的历史事实，不是每次文件修改的数据库镜像。它可以直接在容器内读写，不请求平台批准每个工具。

## 步骤 3：抽出 AgentEngine，用假模型证明执行边界

### 目标

不启动Server、MySQL、Redis、MQ，给目录和模型入口就能完成一次任务。

### 可复用与必须改造

可从当前模型结构迁移 `ModelRequest/Response/Message`、tool call、usage、thinking、预算和终止原因。当前 ModelGateway 与 Context 类带 Spring 装配与持久化依赖，需要构造器注入纯配置/接口，不能原目录整包复制。[G04][G08]

本地最新自然 STOP 路径优先迁移，不从旧 `AgentCompletionOutcome/finishTask` 反推新的结束语义。[U01]

### 建议的核心接口

```java
public interface AgentEngine {
    AgentOutcome run(TaskInput input, SessionRuntime session,
                     ExecutionControl control);
}

// ToolRuntime 是本地Map分发类，完整签名见 reference 中同名文件。
```

这里的 `SessionRuntime` 是 Worker 内存与本地存储状态，不是数据库 SessionEntity。通过 `SessionRuntime.log()` 写本地事实日志，不新增EventSink接口。

### 完整循环顺序

1. 检查取消、deadline、model/tool预算；应用已受理的后续指示。
2. 通过 ContextCoordinator 构造请求。
3. 保存 MODEL_CALL_STARTED；调用 ModelGateway。
4. 保存完整 MODEL_RESPONSE，再更新内存消息。
5. TOOL_CALLS：逐个执行与保存结果，正确配对 toolCallId；再循环。
6. STOP：验证非空正文、无工具调用、无待应用指示；记录 ANSWER_DELIVERED，引用原始响应。
7. LENGTH/协议错误/网络错误：保留已经发生的轨迹，返回相应终止原因，不冒充回答。

工具异常如何返回模型与系统持久化失败如何停止运行，必须分开。不能把本地日志写失败包装成“模型换个参数再试”。

### 假模型测试

`ScriptedModelGateway` 预设：先返回 read，再 edit，再 shell，最后 STOP。测试实际文件被修改、工具 ID 对应、最终回答文字不被二次总结。

再模拟 STOP 为空、STOP 带工具、LENGTH、重复 toolCallId、取消、工具结果保存失败。新工具定义中找不到 `finishTask`。

### 完成标准

core 单元测试不需要打开端口或数据库；任务最终回答来自确定的响应。此时还不接 OpenSandbox。

精确替换要求原文存在且匹配数量符合预期；“没找到”不是“追加到末尾”。创建模式不能悄悄覆盖已有文件。删除明确记录被删除对象的来源摘要。

保留 bytes 原样，文本工具不负责二进制编辑。二进制文件可以由模型生成的脚本在受限环境内处理，出版通过 byte hash 验证。

### Shell 工具

`LocalShellTool` 解析 `{script,cwd,timeoutSeconds}`，交给 `ProcessSupervisor`。不要让 Server 的 `/tasks` handler 直接执行脚本，更不能把 Task.message 当 script。

ProcessSupervisor 内部：

1. 校验 cwd、超时、参数长度和环境白名单。
2. 创建独立命令身份和输出文件；记录 TOOL_STARTED。
3. 用 ProcessBuilder 在工作目录启动 Linux 进程组。
4. 两个独立读取任务同时消费 stdout/stderr；完整落盘与有界预览分离。
5. 等待退出/超时/取消，记录真实退出状态。
6. 返回工具事实，而不把“命令退出1”直接认定为工具协议失败。

可以用镜像中的 `setsid` 建立进程组，通过受控代码取得并核对 pgid；取消时 TERM→宽限→KILL。核对 pgid>1 且不是 Worker 的进程组。不要假设启动器进程PID永远等于实际进程组ID；要在 Linux 测试中验证启动器是否 fork。

Java 的一次 `destroy()` 只针对一个 Process，不能保证派生/脱离的所有子进程结束。无法确认停止时，拒绝继续编辑或封存，并向平台报告 `EXECUTION_ENVIRONMENT_UNSAFE` 请求停止整个实例。

构建工具输出可能填满管道，必须边运行边读，而不是 `waitFor()` 完才读。输出Reader、控制handler不能和单线程Agent执行器共用同一条阻塞线程。

### 原生命令边界

目录/关键词搜索使用 `rg --files`、`find`、`rg`。镜像没有这些命令时返回环境错误，不把每次缺命令交给模型猜安装。

同一Sandbox不保证两个shell调用共享cd；每次传入cwd。后台服务登记句柄与进程组，可查询/停止；封存前处理仍可能写入代码的后台任务。

### 测试

`LocalToolsTest`：路径越界、符号链接、中文/CRLF、精确编辑冲突、创建覆盖拒绝。

`LinuxProcessIT`：正常0退出、非零退出、同时大stdout/stderr、超时、子进程、取消、后台服务、逃逸/无法确认时环境阻塞。

## 步骤 6：建立常驻 Worker 的 HTTP 受理入口

### 目标

普通 HTTP POST 可以让容器内Agent开始执行；接口不阻塞到任务结束。

### 新建类与职责

`AgentWorkerMain` 装配配置、日志、模型、工具、Engine。  
`AgentWorkerServer` 注册接口。  
`TaskInbox` 做短锁受理、幂等、单活跃任务。  
`ExecutionControl` 提供取消信号、待应用指示和deadline。

### 启动过程

Worker从配置读取sessionId、epoch、workRoot、stateRoot、模型代理地址和受控身份。缺少必要配置退出并记录启动错误；未完成 INITIALIZE 时只开放 live/初始化，不声称 ready。

应用监听0.0.0.0:8081；`/health/ready` 返回实际 Session/epoch，不能只返回字符串“ok”。平台要验证连到的不是另一个会话。

### SUBMIT受理流程

在TaskInbox短锁中：查commandId→核对内容→确认session/epoch→确认IDLE→持久 COMMAND_ACCEPTED→设置currentTask→提交内部执行器。完成后返回202。

若刚记录受理却执行器拒绝提交，应落明确错误并保留该任务身份，不能回滚日志后假装没受理。重启检测到受理未完成也不自动重复Shell。

伪代码只说明顺序：

```text
handleSubmit(command):
    validate(command)
    lock admission:
        if receipt(command.id) exists:
            requireSamePayload()
            return previousReceipt()
        requireSessionAndEpoch()
        requireIdle()
        appendDurableAccepted()
        setCurrentTask()
        scheduleOneExecution()
    return accepted202
```

### 控制请求

CANCEL在handler中立即设置线程安全取消信号，不排在长任务后面。STEER先持久确认再排入有界队列，Engine在安全边界应用。

`SEAL_SESSION/ACK_PUBLICATION` 使用相同协议，但不能绕过任务边界直接改文件。关闭时停止接收新Task，完成已有事件与归档确认。

### 本地联调

实现后启动Worker，再调用本包样例。示例URL仅用于本机联调；云端要使用OpenSandbox解析的端点与headers。

```bash
curl -i -X POST 'http://127.0.0.1:8081/commands' \
  -H 'Content-Type: application/json' \
  -H "X-GitNova-Worker-Token: $WORKER_TOKEN" \
  --data-binary @examples/submit-task.json
```

样例包含合成ID/HEAD，须与测试启动配置一致；时间示例不是生产deadline。真正平台请求由Server生成，不让用户手填内部身份。

### 测试

`WorkerAdmissionIT`：重复POST只启动一次；正文不同409；运行中第二Task409；未初始化503；取消不等待模型完成；恶意Task字符串只进入模型，不在shell执行。

## 步骤 7：事件流、回答关联与可重连通信

### 目标

断线不丢可恢复事件，不重复执行；前端不靠终端日志猜最终回答。

### Worker SSE实现

`GET /events?epoch=1&after=40` 从本地事实日志读取>40的记录，写成SSE；读到尾部后等待追加通知，再从当前游标读。整个迭代只以日志为事实，不靠一次性的内存广播。

每个event写完空行并flush。心跳使用注释行。单个订阅者慢/断连只释放该连接；有界订阅数防止耗尽线程。不要让Engine同步等待所有订阅客户端写完。

逐token或命令片段可以用于显示，但最终必须追加完整MODEL_RESPONSE/TOOL_RESULT。现有ModelGateway若是非流式complete，就先显示模型阶段与工具阶段事件，不伪造字符流；在本次通信接线里实现经测试的流式适配时，原始最终响应仍是唯一回答事实，不允许删掉它。

### 自然回答关联

依次记录 MODEL_RESPONSE → ANSWER_DELIVERED → TASK_FINISHED。ANSWER/TASK事件引用原始响应eventId/modelCallId。持久查询只沿这个引用取文本。

Worker若在完整响应保存后、终态前崩溃，这条响应不能自动成为最终回答：要依据已经提交的终态决定，未决定则中断。

### 测试

`EventReplayIT`：订阅在事件产生之后建立仍能收到；重连从cursor续；同一记录重复传输不改变其身份；慢订阅不阻塞Agent；append和订阅注册交界不丢帧。

`AnswerReferenceTest`：工具调用前文字不是最终回答；被steer推迟的STOP不是最终回答；正文空或reasoning-only拒绝；页面刷新取到完全同一正文。

SSE协议依照WHATWG格式，实现自己的Java/前端解析器时必须测试分帧和UTF-8边界。[S07]

## 步骤 8：完成Worker初始化、封存与恢复包，闭合生产装配

### 目标

Task1发布绝不读到Task2的新变化；取消/失败保留进度但不自动出版。

### 新建组件

Worker：`SessionSealer`、`ExportStore`。  
平台ArchiveService/BundleValidator/DeliveryMapper在步骤11实现；本步只写Worker侧。

### 封存流程

1. 进入FINALIZING，拒绝普通新任务；停止或确认所有可能写文件的受管子进程。
2. 固定发布文件集合。源Commit跟踪文件不能被忽略规则静默丢弃；未跟踪的依赖/构建产物使用显式排除。
3. 在不再有写者的条件下复制/归档tree和state，计算文件及整体SHA256。
4. 写manifest临时文件、验证包、原子发布exportId对应对象。
5. 日志记录SNAPSHOT_SEALED。它引用的包已存在且不可变。
6. Server通过exportId下载，校验身份、路径/容量/摘要，保存到平台耐久存储，再落归档行。

恢复包的覆盖是封存时的完整事件边界。ACK_PUBLICATION在封存后发生，因此重建时需要由平台附上已经确认的最终发布HEAD，不能误以为包内旧expectedHead仍是平台最新值。

### 日志覆盖与导出目录

封存先取得完整日志截止序号N及其字节offset；只把截止N的记录复制成不可变日志段。不要直接zip仍有控制事件写入的活动JSONL。state目录里不放正在生成的bundle，导出区使用单独 `/session/exports`，明确从打包集合排除。SNAPSHOT_SEALED和之后的ACK在N之后产生，恢复时通过平台归档元数据接上出版结果。

### ZIP导入安全与一致性

先读取manifest上限，再逐entry验证，不信任zip声明解压大小。禁止路径逃逸、重复entry、特殊文件和声明hash不匹配。压缩包中未声明的文件拒收。软/硬链接不作为普通文件静默导入。

普通字节和换行必须精确保留。CRLF不能在diff展示时变成LF后再用于出版。代码diff只是展示，不是权威文件内容。

### 失败策略

导出失败：保持FINALIZING/BLOCKED，不放行下一任务污染现场；记录具体原因。下载/平台保存失败：重试同exportId，不重新跑模型。

用户取消/执行失败：可导出标记为FAILED/CANCELLED的恢复包，但默认publication=NOT_REQUIRED。保留dirty标记，下一次明确继续时继承这些未提交修改。

### 测试

`SessionSealerIT`（本步在本地目录验证Worker封存，不要求尚未接入的Server）：写进程未停拒绝封存、同Task重复seal返回同包、恶意压缩路径、大小超限、二进制与CRLF保真、源码tracked文件与ignore冲突、Task2不能越过结算屏障。

## 步骤 10：平台 Session 初始化与工作分支创建

### 目标

一个完整Session从创建到ready可用；慢环境操作不占着数据库事务。

### 现有可用入口

`RepositoryAccessService` 保留鉴权职责；`RepositoryRevisionService` 可解析源分支的固定HEAD；旧 `AgentSessionService` 的“持久准备→外部物化→短事务激活”思路可参考，但其Workspace依赖退出新链。[G02][G09]

### 新接线

平台新增 `SessionLifecycleService` 是确定的新入口；已有Controller显式按executionBackend分派。最终新系统只调用新分派，旧分派仅在迁移期间用于旧任务收口。

数据库严格执行05及schema的Session增量字段；实例信息放独立binding记录，新Task写agent_control_task，不套旧Task CHECK。不要再保留一个新Workspace表作为当前目录状态真源。

实施顺序：

1. 验证仓库写权限——创建工作分支不是纯读操作。
2. 以用户/仓库/请求幂等键解析已有Session。相同键但不同源选择返回冲突。
3. 固定源HEAD=A、分支名、会话身份，短事务插入PROVISIONING。
4. 事务外准备Sandbox、导出A、启动/初始化Worker。
5. ready通过后，短事务创建指向A的新分支，绑定归属，将Session激活。
6. 任一步失败记录可重试/不可重试原因；重复请求核对已有资源，不重新读取新的main HEAD替换A。

分支创建只插引用，不造空Commit；不能直接调用首次push方法时传错expectedBase而导致拒绝。通用BranchService接收“创建指向既有Commit”的显式操作。

### 数据库迁移要求

以步骤 0最新migration编号为准追加迁移，不编辑已经执行的旧migration。不马上DROP旧workspace外键/列；先让旧历史可读取，再在退役步骤删除新执行链不再使用的关联。

### 测试

`SessionProvisionIT`：main在创建期间前进但Session仍固定A；重复请求只有一个分支/绑定；环境失败不显示ACTIVE；分支同名属于别的Session时不覆盖；身份/权限不匹配拒绝。

## 步骤 11：平台 Task 接收、发送与状态投影

### 目标

不使用Agent MQ派发，但Server崩溃或HTTP响应丢失后不会丢任务、重复执行。

### 新平台组件

`TaskApplicationService`：业务受理和活跃槽。  
`AgentWorkerClient`：HTTP发送/查询，仅负责传输。  
`CommandDispatcher`：核对未确认的粗粒度命令。  
`EventCollector`：从Worker订阅事实事件。  
`EventProjector`：幂等归档并更新公共查询状态。

这是职责清单，不要求每个helper再做接口+impl两套类。

### 受理事务

锁Session，按幂等键先查Task，再检查activeTaskId；创建Task、attempt、control-command并预留活跃槽。同一事务提交。

事务后安排发送任务。Server响应202只表示Server已保存请求。核对器扫描待发送记录，可以是定时器；这是防止“事务提交后进程挂掉”导致任务悬空，不是重新把Agent执行安排到服务端线程。

### HTTP结果处理

- 202/重复200：记录已受理。
- 400/403：明确拒绝，向用户给出原因，按状态释放未执行的槽。
- 409：先判断同任务还是另一个任务；不吞掉身份冲突，不自动造新attempt。
- 连接错误/超时：标UNKNOWN，查询原commandId或原样重发。
- Worker不可达：核对Sandbox状态；没有确认旧实例死之前，不能另启Worker挂相同卷。

### 事件归档

新表逻辑名 `agent_event_archive`：UNIQUE(session_id,runner_epoch,sequence)、UNIQUE(event_id)，保存payload摘要与归档offset。不要依赖生产旧agent_step的fenced append强行写新事件。

保存原事件、更新连续cursor、更新Task投影在同一个短事务。收到终态时校验引用原MODEL_RESPONSE已存在且归属/STOP条件满足。缺前置事件则先重放，不能“终态先到了就直接找最新assistant”。

如果Server多副本都订阅同一Worker，可以让数据库幂等去重，先不建设分布式订阅调度。Sandbox创建/重建仍需数据库绑定CAS防重复，不将多副本写权交给内存Map。

### 测试

`TaskDispatchIT`、`EventProjectionIT`：模拟Server在提交后发送前崩；模拟Worker受理后响应丢；模拟事件重复、跳号、不同payload同ID；两个用户/两个请求并发提交；旧epoch晚到事件只作历史不覆盖新attempt状态。

## 步骤 14：复用托管底座发布 Commit 和工作分支

### 目标

Worker只生产代码状态；GitNova平台负责权威Commit/Branch。

### 提取位置

从现有 `TransferService` 提取可复用的对象完整性、Commit索引、Branch更新逻辑。保留外部Push的expectedHead与fast-forward合同；Agent出版不要绕HTTP上传包。[G05]

新增 `PublicationService` 编排export，通用 `BranchPublicationService` 承担仓库更新。`ObjectStorage`、`GitObjectCodec`、`GitObjectHasher`直接复用。[G06][G07]

### 幂等身份

Publication使用UNIQUE(sessionId,exportId)。创建时保存固定timestamp、message、author、expectedHead；重试读这份记录，不再次生成时间或调用模型起提交说明。

提交说明可由任务标题生成可编辑默认值，不能为了生成message再增加一次必须成功的模型调用。

### 具体算法

1. 导入manifest与文件，验证所有bytes hash。
2. 读取expectedHead的Commit mapping；比较完整树。
3. 没变化记录NO_CHANGES；有变化保存新增/变更Blob，删除路径不再出现在mapping。
4. 新Commit父节点=expectedHead。编码后计算SHA，保存对象。
5. 短事务内检查当前授权/Publication状态、CAS分支、写CommitRecord、更新publishedHead和Publication。
6. CAS失败记录CONFLICT，不换parent强写；成功但返回丢失用同publicationId查询原Commit。
7. 保存/出版完成后向Worker ACK，确认TURN_SETTLED后释放平台活跃槽。

锁顺序：出版使用Session→Publication→Branch；PR合并使用关联Session→Merge意图→PR→按(repoId,name)排序的Branch。禁止拿到Branch后再回头锁Session/Publication/PR。对象写入和长网络不放数据库锁内。

### 特殊测试

`PublishTest` 必须测试：A→B正常、B→C追加、工作树撤销为A仍发布新Commit、重复请求timestamp不变、对象已写但数据库失败、Branch更新成功返回丢失、权限被撤销、平台收到不属于本Session的包、ACK丢失、NO_CHANGES不生成空Commit。

### 注意现有关系索引

`commit_record.branch_name` 不能作为一个Commit只属于某分支的唯一真相；同一Commit可以被多个分支引用。历史查询以分支HEAD沿parent回溯/可重建索引为依据，不用单一branch_name筛选伪造历史。[G05][G06]

## 步骤 15：完成通用 PR，而不是 Agent 专用交付表

### 目标

从Session工作分支到可审查、可关闭和可合并的代码协作流程。普通用户分支也能使用同一服务。

### 数据与API

新增pull_request、pull_request_comment（实际migration编号按步骤 0）。PR字段：id、repoId、sourceBranch、targetBranch、authorId、title/body、status、draft、revision、mergedFromHead、mergedCommit、created/updated时间。Session关联可空。

API包括创建、列表、详情、files/diff、comments、ready/draft、close/reopen、merge。每个写入口执行权限检查；评论作者身份来自登录用户，不来自payload。

创建PR时branch必须存在且同仓库、source!=target。源/目标相同树允许Draft，但merge返回NO_CHANGES。避免同一对分支重复开放PR：在已有分支行的稳定锁顺序下查询/创建，或使用数据库能保证的唯一活动关系设计，不仅靠先SELECT再INSERT。

### Diff

计算共同祖先到source的变更供审查；同时显示当前target HEAD用于判断合并状态。不要只直接diff target与source就把target独有的新修改显示成PR要删除的内容。

同一Session的初始A可用于活动改动预览，不是所有PR永久的比较基准。源HEAD变化后按新HEAD计算；基于旧HEAD的review/approve必须带提交身份，不能继承成未经审查的新代码已通过。

本次基础讨论用评论，不强制组织审批流程；UI不要用“有评论/模型通过”冒充人工approval。

### 合并

先实现前述完整策略：fast-forward和三方squash，冲突明确拒绝，不新增双父对象格式。使用JGit纯内容三方合并库时先固定与Server Java17兼容的发布包，测试 `MergeAlgorithm` 的base/ours/theirs输入顺序。[S11]

算法：

```text
读取 sourceHead S、targetHead T、共同祖先 O、PR revision R
计算 mergeTree(O,T,S)
  → 有冲突：返回路径，不更新Branch/PR
  → 无冲突：准备快进目标或squash Commit M
提交事务：
  锁PR并验证R/status
  按稳定顺序锁相关分支，验证仍为S/T
  更新target到S或M
  写索引与PR MERGED/mergedFromHead/mergedCommit
```

如果验证时HEAD改变返回409，让用户刷新重新计算，不默默合并未经展示的新source。

### 合并后

Agent工作分支对应PR合并后，Session不再接受新Coding Task，封存关闭。后续工作从目标最新提交新建Session，避免单父squash血缘被重复计算。

关闭PR可以重开，但已MERGED不允许重开。用户关闭PR不必销毁Sandbox或删除分支；这些是独立操作。

### 测试

`PullRequestIT`：Draft空差异、后续提交刷新、重复创建、评论鉴权、关闭/重开、快进、target前进后无冲突squash、同文件不同段自动合并、删除/修改冲突、二进制冲突、并发两次merge、source在提交前变化、非授权merge、Session合并后禁止继续。

## 步骤 16：生命周期、恢复与安全基线收口

### 目标

环境能长期工作也能被回收；故障后状态可解释，不留下运行中的孤儿或假完成。

### 生命周期管理

新增平台 `SandboxLifecycleCoordinator`，只处理Session级准备、续期、闲置封存、停止和恢复，不观察每个文件版本。

定时器使用有界线程和稳定Session身份。RUNNING/FINALIZING不按普通idleTTL回收；模型无输出时依靠独立health/当前task查询判断。

清理发生网络失败时保持DELETING/UNKNOWN，不写DELETED；重试并核对实际实例。通过metadata查孤儿实例时分页完整读取，只删除确认无现有绑定的受管实例。

### Worker崩溃

控制面先确认旧进程/实例停止且没有残留写者。恢复有保存的卷时，校验日志，当前未完成attempt标INTERRUPTED。不要自动执行旧TOOL_STARTED对应命令。

用户继续建立新的attempt，模型收到中断说明、当前代码/未发布改动和历史结果边界。只要平台还无法确认旧实例死亡，不挂同一可写卷起新Worker。

### 恢复到归档

验证bundle摘要与来源，新的epoch、恢复起点、旧已发布HEAD都在启动记录中明确。若事件档案比代码恢复点更新，超出覆盖的旧轨迹只作历史，不纳入“当前已完成进度”。

一个发布完成而ACK丢失的包，恢复时从平台Publication读取真实结果，不重复构造Commit。

### 安全基线与后期加固

现在就实现Session/epoch核对、大小/时间/资源上限、压缩包安全、凭据外置、管理端点不公开。高级网络隔离与不同UID/执行隔离可以在本步骤集中完成；未完成以前只允许受控测试，不把任意多租户安全标为已完成。

SDK/模型代理HTTP日志必须遮蔽敏感头。不能把控制token、供应商key写进用户可读取的repo或Prompt。

### 验收

`LifecycleIT`：Server重启不重跑Agent、Worker重启识别中断、TTL续期、闲置回收、卷重挂、从归档新环境恢复、旧实例未确认停止时拒绝接管、回收失败不撒谎、权限撤销无法再发布。

2. 创建Session时写executionBackend，之后每个请求只按这个不可歧义的字段路由。

## 附：手写时不依赖IDE猜出来的装配顺序

WorkerAssembly拥有单一资源容器WorkerApplication（嵌套record/AutoCloseable）；new顺序为config→Paths/FileLock→SessionLog→ResultStore/HistoryIndex→Gateway→Token/HistoryReader/Summarizer/Context→ProcessSupervisor→5个本地Tools→ToolRuntime→Engine→WorkerSession→TaskInbox（注入TaskFinalizer）→HTTP。SessionSealer需要WorkerSession、log、ResultStore、ProcessSupervisor，不反向new整个HTTP。回调通过接口传入，禁止循环构造。

所有执行器都由assembly创建，任务线程不拥有HTTP线程；close先拒绝任务，再请求取消/等进程停止，持久终态，停止SSE，关HTTP，最后关log与FileLock。不能停HTTP后等待一个永远不可能到达的ACK；有未结算状态则保存现场并由平台恢复。
