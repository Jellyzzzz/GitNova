# 01｜GitNova总体架构与控制通信

本文是统一后的运行设计。关键字的取值由05、reference与contracts的Schema共同校验；有冲突必须改原文，不能要求实施者选“最新一句”。原始源码和外部资料的固定来源保留于03/10/17；本轮设计修正在audit/修正登记.md。

## 1. 四个职责与三个身份

GitNova Server拥有账号、仓库访问、分支/PR、会话归属和持久业务意图。Core运行模型—工具循环、Context与本地历史。Worker是Core的进程宿主，提供HTTP受理、控制、初始化、快照、SSE与资源装配。Protocol是两端共享的类型/传输契约，不是独立运行服务。

```text
Browser → GitNova Server → 私有HTTP Commands → Sandbox中的Worker → 本地调用Core
                       ← 可重放SSE Events ← 本地SessionLog
Core → ModelGateway → ModelProxy → 供应商模型
Core → 本地工具 → 本地文件/受管进程
Core ToolRuntime → Worker注册的可选平台Tool → Server仓库/PR业务
```

模型推理本身不因此部署在沙箱里；沙箱部署的是我们的Agent程序，模型通常在供应商侧。OpenSandbox只管理执行环境，不替我们执行Agent策略。

**Core先独立工作，Worker再提供托管入口。** 本地驱动与Worker都可直接调用同一个AgentEngine；本地运行不需要平台HTTP、数据库或OpenSandbox。提供工作目录、模型连接、受信运行配置和本地会话资源即可。云端使用ModelProxy，本地开发可使用独立Gateway配置，凭据均不进入Message或日志。运行地点无关不等于操作系统行为相同，Linux进程组取消仍需Linux验证。

Worker接收带Task身份的结构化命令；Core统一使用ModelTypes.Message表达对话。**Task身份、运行控制与消息正文分开，AgentCommand不等于Message。** Worker负责协议、绑定、HEAD/配置等前置校验；Engine不从用户文本推断这些字段，也不要求先存在一条HTTP受理事件才能运行。

Session是一段连续会话；Workline是一轮固定基线和受管分支；Binding是一代执行实例。Session可以有多条历史Workline，current pointer只有一个；每个Task/Attempt固定其工作线，实例epoch在Session内递增且不复用。merge不改变会话身份。

### 1.1 先沿一条Task看数据，而不是先背类名

下图是目标调用链，不表示参考类已经有生产实现。Q/L/E分别简称sessionId/worklineId/runnerEpoch；不是新增Java字段或额外身份。

```text
用户message + public幂等键 + 已看到的工作线/会话版本
  → Server鉴权与受理事务
  → 保存Task/Attempt及固定AgentCommand（含Q/L/E、deadline、配置digest）
  → CommandDispatcher → AgentWorkerClient.send（事务外HTTP）
  → Worker认证/解析 → TaskInbox.accept
  → FileSessionLog.appendHost(COMMAND_ACCEPTED)，保存命令与固定executionId并耐久确认
      ├─ CommandReceipt → Server：这是受理结果，不是answer
      └─ 保留Submit.message原文 → Message(role="user")
           → WorkerSession.Execution绑定原命令、executionId、Writer/Control/Tools
           → taskExecutor：core.run(message, sessionRuntime, control, writer)
           → AgentEngine.run
           → ContextCoordinator.prepare → ModelTypes.Request
           → ModelGateway.complete → ModelTypes.Response → 保存MODEL_RESPONSE
                ├─ TOOL_CALLS → ToolRuntime → 本地文件/进程
                │              → ResultStore对象 + TOOL_RESULT → 再组装Context
                └─ STOP → 保存ANSWER_DELIVERED → AgentOutcome
           → TaskFinalizer.finish → 本地进程安全收尾 → TASK_FINISHED
  → SessionLog → Worker SSE → Server归档/投影事务 → 公共TaskView.answer
```

长Loop只占Worker的任务执行器；控制HTTP、输出消费、SSE不排在它后面。读页面、断开订阅、查询回执都不重新执行Task。Server自身的202与Worker的202是两次不同的持久受理，不互相替代。

| 数据边界 | 生产者 → 消费者 | 保留在哪里/不能拿什么替代 |
|---|---|---|
| AgentCommand / CommandReceipt | Server固定意图 → Worker；Worker受理事实 → Server | 命令重试复用ID/内容；receipt不能当任务完成 |
| USER Message / SessionRuntime / Writer | 本地启动器或Worker → Engine | 原文是消息；共享资源含只读history；Writer固定本次executionId，不把平台Task/Attempt传给Core |
| ModelTypes.Message | 用户输入适配、响应转换、工具结果投影 → Context/Gateway | role/text/toolCalls/toolCallId/reasoningContent统一；命令信封、凭据及Task身份不拼进正文 |
| ModelTypes.Request / Response | Context → Gateway → Engine | 响应先记日志；reasoning不是最终answer，usage不是上下文正文 |
| ToolTypes.Result / ResultStore.Ref | 工具/输出存储 → Engine/历史投影 | 原始事实与模型预览分开；小结果也保留可回查来源 |
| SessionLog.Entry → AgentEvent | 同一日志记录 → Core历史 / Worker协议投影 | Entry是不含平台身份的Core视图；Worker以已固定origin投影AgentEvent。索引与TaskView可重建 |
| AgentOutcome / TaskView.Answer | Engine → Finalizer → 查询投影 | 回答沿事件引用取原文，不通过“最后一条assistant”猜 |
| PROGRESS / RECOVERY | 显式工具/后台封存 → 平台 | 一个用于发布固定树，一个用于恢复；自然STOP不自动产生它们 |

新开发者先按02步骤3实现Core执行链，再接步骤2/4/5的真实本地实现；不先经过图中的Server或HTTP入口。后半条平台归档在步骤11实现。这里安排的是完整系统的施工顺序，不是把范围缩成一条演示路径；所有约定消费者及失败处理仍须实现并验收。

## 2. 依赖和目录

Server依赖protocol及仓库/基础设施适配，不import Core/Worker。Worker依赖core和protocol。Core只依赖自身消息/端口及所需通用库，不依赖agent-protocol/Worker、Spring/MyBatis/MQ/OpenSandbox。同一进程内Core调用本地工具，不逐个通过Server协调文件。

同一FileSessionLog保存通用Entry及不可变origin（本地为空，云端为Worker身份），不是双写两套日志。SessionRuntime只暴露history，执行级Writer自动补本次executionId与来源；Core不能按可变currentTask补归属。Worker将同一记录确定性映射为AgentEvent供SSE/归档，协议v2保持不变。细节见05第2.3—2.5节。report_progress/create_pull_request的实现与PlatformCapabilities属于Worker装配；Core只有通用AgentTool接口。本轮不接MCP。

本地能力先走shell→ProcessSupervisor→cat/sed/rg/find，不重写Linux的读取/搜索算法。仍需实现进程入口、取消/超时、双流捕获与结果预算；Sandbox不会自动替模型调用命令。专用read_file可选，精确edit_file和历史回读按实际需要保留。shell并不天然只读，真实权限由宿主/容器限制，不能用SafePaths的cwd校验假装隔离整个脚本。

```text
agent-runtime/agent-protocol   Java17字节码：消息类型和协议辅助
agent-runtime/agent-core       Java21：Loop、Context、工具、本地日志
agent-runtime/agent-worker     Java21：HTTP/SSE、启动与装配、快照接线
src/.../service/agent/control  Server会话/实例/操作协调
src/.../service/repository     权威分支和对象
src/.../service/pullrequest    通用协作业务
```

参照成熟项目时借鉴行为和失败边界，不复制其整个依赖树。Harness在Server并非天然错误；本轮移走的是已有实现中混杂的执行权和工作树协调，不是靠容器自动消除所有复杂度。

## 3. 初始化与任务路径

新Session：平台鉴权、固定Commit A、准备Session+初始Workline+Binding意图；事务外创建Sandbox和bootstrap；Worker导入文件；平台最终创建指向A的受管分支并激活。创建分支不造空Commit。

bootstrap是固定文件字节+baseline+状态/manifest的ZIP，不是镜像或任务JSON。Server从GNOV mapping读取Blob构建包，通过Worker `PUT /bootstrap/{bootstrapId}`上传；`INITIALIZE`只引用它的ID/hash。Worker先校验staging、安装，再打开SessionLog并构建完整RuntimeServices；不能先打开日志再替换它所在的目录。

Worker应用live只表明控制壳在运行；ready表明Q/L/epoch配置和已安装代码可执行。**ready不等于平台已经激活这个Binding**：准备中的同步实例也可以ready，必须通过平台active指针核对后才获得任务或模型/仓库出站授权。

Task：公共POST先持久受理，再在事务外向已激活Worker发SUBMIT。没环境且只是普通回收恢复时可先排队；显式SYNC gate期间新任务返回409且不创建任务。已有同幂等键的Task重查返回原结果，不因同步/merge后状态变化而再次创建。

## 4. 命令和查询

私有控制完整信封：schemaVersion=2，commandId，sessionId，worklineId，runnerEpoch，type，taskId，attemptId，payload。deadline不随网络重试重置。全部类型匹配和空值规则见05，完整JSON见fixtures；public请求不接收私有信封。

| type | 作用 | 是否启动模型 |
|---|---|---|
| INITIALIZE | 校验并安装既有bootstrap | 否 |
| SUBMIT_TASK | 持久受理一个固定attempt | 是 |
| STEER_TASK | 保存当前任务的补充指示，在安全边界应用 | 后续调用可见 |
| CANCEL_TASK | 运行时取消，不是给模型一句停止 | 否 |
| PREVIEW_CHANGES | 空闲安全点生成确定W预览，null task/attempt | 否 |
| CHECKPOINT_SESSION | 保存RECOVERY，不发布代码 | 否 |
| ACK_CHECKPOINT | 平台包与连续事件已保存 | 否 |
| STOP_WORKER | 有确认归档后停止当前实例 | 否 |

Worker私有API：GET `/health/live`、`/health/ready`；PUT `/bootstrap/{bootstrapId}`；POST `/commands`；GET `/commands/{commandId}`、`/tasks/{taskId}`、`/events?epoch={e}&after={n}`、`/exports/{exportId}`、`/previews/{commandId}`。

Server公共Task/Session入口在16；完整payload在05。Server还提供Worker可调用的 `/internal/agent/sessions/{sessionId}/operations/report-progress`、`create-pull-request`及`operations/{operationId}`查询。控制令牌、模型令牌、平台能力令牌用途分离。

HTTP 202只是该接收层已经受理；网络超时代表结果未知。用同commandId/operationId查回执或重发固定内容，不自动制造新attempt。错误体含code/message/requestId，不包含密钥、堆栈或宿主路径。

## 5. 执行、发布、回收、同步四条链

自然回答：MODEL_RESPONSE先保存 → ANSWER_DELIVERED引用原响应 → 本地工具/子进程安全收尾 → TASK_FINISHED → IDLE。Server归档终态后清对应活跃槽；不生成Commit。

显式发布：模型调用report_progress → Worker先存operationId → 固定PROGRESS树 → Server校验对象 → 仓库CAS与操作结果同事务 → Worker查询结果并安装同一树的baseline。create_pull_request独立，只使用已发布源分支。

空闲回收：无活跃/待发任务、无未决平台操作、无写进程 → CHECKPOINT_SESSION → 平台保存RECOVERY和连续日志 → ACK → STOP → 确认销毁。没有用户新消息不等于空闲；心跳不应无限续业务空闲计时。

显式同步：用户选择H与草稿策略 → 持久syncId/Session gate → 保存旧RECOVERY → 计算候选 → 新Workline/epoch/独立目录初始化 → 平台原子切active指针。冲突不改旧树；详情见12。普通恢复回原W，不能当同步main。

## 6. PR与会话

PR是通用仓库对象，普通分支创建/查看/评论/merge不需要Sandbox。Agent只是调用方。统一仓库ManagedBranchPolicy由控制模块实现，校验受管分支的写入资格，不调用Worker或模型。

merge只合已发布S，候选是merge(O,T,S)。最终事务核对PR.version、S/T、权限；受管来源检查无活跃Task、无未决操作及无显式SYNC gate，标旧Workline MERGED。**不检查W、不调用checkpoint、不关闭Session、不刷新沙箱**。W可以有未发布草稿；旧线禁止再向远端发布，但允许连续会话与本地分析/草稿。

更换代码基线仅由显式sync进行。默认REQUIRE_CLEAN保护草稿；CARRY将B→W迁到H；DISCARD绑定被确认的W摘要与H，先备份。用户丢弃同意不能由模型猜测。

## 7. 事件、权限与一致性

源Entry及origin先耐久追加，再由Worker投影AgentEvent发SSE。页面游标是Server archiveOffset，同Session串行归档后分配，防迟提交事件被跳过。旧线/旧epoch事件保留历史，不清新Task槽。原始工具结果先存字节对象，引用成功后才成为可回查事实。

DomainEvent记录仓库/PR/用户关系业务，不是Agent工具日志。PR/分支结果与Outbox同事务，MQ只投递业务事实；消费者receipt与投影同事务。历史PR版本可异步，但当前Diff和merge必须读权威S/T，不等投影追平。

数据库统一锁序固定为：repository → Session → Workline/Binding → PR → Branch(id升序) → Task/Attempt → 平台/发布/同步/合并操作 → repo计数/Outbox。取了后序锁就不能倒着取前序；只涉及Session的事件投影可以省略repository，但不得之后再取它。具体事务见05/16。

昂贵文件读取、模型、HTTP、ZIP、MQ确认不在数据库事务中。最终授权使用当前读，与授权变更按同repo门闩形成先后；不是拿旧事务快照或Redis旧角色做最终授权。私有列表在SQL权限过滤后分页。

## 8. 双机只是部署

开发Mac运行Server/ModelProxy；Windows32G以WSL2/Linux容器运行OpenSandbox与Worker。两个方向分别验证：Server到OpenSandbox/Worker，Worker到ModelProxy。双方都用配置中的可达端点，不能把容器localhost当Mac。

Browser永远只访问一个GitNova平台，不知道物理机器/私网地址。关闭页面只关订阅，不取消Task；多个客户端共享同一会话和活跃槽。关页面与让承载平台的Mac睡眠是不同操作，后者会影响代理/通信。

SDK endpoint含路径与必要headers，不能用根路径resolve抹掉前缀；创建与ready分开，SDK健康探针不替代Worker业务就绪。真实命令与资源配置沿06，由实机验证支持范围，不新造SDK参数。

## 9. 安全、迁移和交付

明确当前执行安全边界是受控可信开发仓库；同UID shell、网络出站、内存/控制文件攻击并未因为用了容器而自动解决。正式开放不可信多租户前另有执行隔离验收。保留大小/时间/路径/权限/token隐藏等基础限制。

旧数据只读兼容，不复活旧Loop；新旧同Task不能双路执行。旧归档原字节不改，legacy scope用外部映射。目标DDL不是实际迁移；H0读取真实旧库再生成追加Flyway。本轮没有启动在线对象GC。

实现和验收按照02及12—16，源码引用见03/10/17；下一步不确定时使用09/20。是否有架构缺陷只能由明确不变量、反例与真实回归不断验证，不能由文件数量或一次静态PASS保证。
