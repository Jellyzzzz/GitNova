# GitNova Harness-in-Sandbox：总体架构与通信契约

> 本次补全说明：整体终态不变。新增精确施工表（02、04）、强类型命令/状态与完整DDL（05）、固定SDK接线（06）。术语/类名以04和05为准；原始资料的含糊处已同步修改。部署数字是依赖版本，不是产品分期。

本文决定“最终系统如何完整工作”。实施顺序另见 [手写开发指南](02_逐步手写开发与旧链路退役.md)。供应商事实、旧代码事实和用户给定契约的来源编号，统一在 [验收与资料](03_验收矩阵与资料依据.md) 中查询。未标为事实的设计均为本次架构决定。

## 1. 决策与完整范围

### 1.1 我们到底改变什么

把 Agent 的模型—工具循环、运行中上下文、文件操作和命令执行，从 GitNova Spring Boot 服务中抽出，放进 Session 的 Linux Sandbox。平台不再围绕每次工具调用维护活动工作树状态。

不把“容器”当作架构改造本身。现有旧实现中的一部分文件访问本来就是本地 Java 调用，并非真的 RPC；问题是执行权、工作树协调、数据库与临时容器生命周期都压在平台模块中。此次改变的是这些职责和依赖，而不是宣称服务端 Harness 天生错误。[G02][G03]

**共同目标：一次连续 Coding 工作能够在一个本地环境中自然完成，同时平台仍然可靠地受理任务、展示回答、接收代码、提供 PR 和管理资源。**

### 1.2 一次交付必须覆盖的内容

| 业务过程 | 最终行为 |
|---|---|
| Session 初始化 | 固定源分支与 Commit A；创建指向 A 的 Agent 工作分支；准备环境与初始文件树 |
| Task 受理 | 权限检查、持久保存、单 Session 活跃槽、幂等发送、明确是否已被 Worker 受理 |
| Agent 执行 | 本地读写/搜索/命令；上下文压缩、完整工具结果来源与回查；连续多 Task |
| 用户交互 | 进度、后续指示、取消、页面刷新、断连续传；关页面不取消任务 |
| 正常回答 | 自然 STOP 正文保存为 answer，准确关联原始 MODEL_RESPONSE |
| 代码交付 | 固定文件快照、幂等创建 Commit、CAS 推进工作分支；失败只重试发布 |
| PR | 同仓库源/目标分支；列表、详情、文件差异、讨论、Draft/Ready、关闭/重开、合并/冲突提示 |
| 故障与资源 | 实例就绪、续期、健康检查、闲置封存与回收；明确的中断和恢复边界 |
| 迁移 | 旧任务收口、历史可查询、新任务仅走新链、旧执行代码和配置退役 |

不新增平台检索/RAG、跨仓库 Fork PR、复杂组织审批、CI 编排、多个 Sandbox Provider、Kubernetes、预热池。这里是本次完整产品范围，不是承诺后续某个版本才补前述基础能力。

### 1.3 不变量

- **I01**：活动代码只由该 Session 当前 Worker 及其受管理的子进程修改；平台不直接修改正在运行的工作树。
- **I02**：一个 Session 同时最多一个执行任务；取消与后续指示不需要排在这个长任务后面才能处理。
- **I03**：Task 是结构化数据，不是 Shell 参数拼接片段。
- **I04**：容器内部工具调用不经过平台逐条转发；OpenSandbox 只负责环境边界。
- **I05**：回答交付不等于代码正确、不等于代码已发布、不等于 PR 已合并。
- **I06**：发布对象与批准合并都绑定确定的文件树/提交身份，不能读取持续变化的目录充当快照。
- **I07**：重复网络请求不应重复启动同一 Task；已经发生的任意 Shell 副作用不承诺 exactly-once。
- **I08**：恢复对话与恢复代码必须对应；旧环境中的验证是历史证据，不自动变成新环境验证。
- **I09**：一次 Task 只能路由至一个执行后端，不能新旧链双执行。
- **I10**：不会为了“状态少”删除必要的任务身份、事件归档与仓库授权；只删除重复的运行控制权。
- **I11**：Session由平台持久管理，不属于某台客户端或某条SSE连接；同一有权用户可跨设备访问，增加订阅者不创建新Worker，同一Session仍只有一个执行者。

## 2. 三个程序与依赖方向

### 2.1 运行图

```text
浏览器
  │ 公共 Task/Session/PR API + 进度流
  ▼
GitNova Server ──────────────→ 仓库 ObjectStorage / MySQL
  │                            Branch / Commit / PR
  ├── 模型代理 ──────────────→ 模型供应商
  │
  ├── OpenSandbox SDK ──────→ OpenSandbox Server ──→ Docker Engine
  │                               │ 创建和管理
  │                               ▼
  └── 私有任务 HTTP / SSE ──→ Session Sandbox
                               ├── execd：基础环境访问
                               ├── Java Agent Worker：我们的程序
                               ├── /session/worktree：代码
                               └── /session/state：记录与结果
```

OpenSandbox 是执行环境管理产品，不是 Coding Agent。官方区分生命周期服务与沙箱内 `execd`，并支持 Docker 后端与 JVM SDK。[S01][S02][S03]

### 2.2 谁依赖谁

`gitnova-server` 依赖共享协议和 Sandbox 适配器；`agent-worker` 依赖 `agent-core` 与共享协议；`agent-core` 不依赖 Spring、MyBatis、RabbitMQ 或 OpenSandbox SDK。

独立 Agent Core 只需要：工作目录、本地状态存储、模型连接、任务、运行限制。模型连接可以指向平台代理，不能因为使用代理就又依赖平台数据库实体。

### 2.3 代码组织决定

保留当前根工程作为 Server，不先搬动全部后端目录。新增一个独立 Maven 聚合目录：

```text
agent-runtime/
  pom.xml                  # 仅聚合新模块，不替换现有根 pom
  agent-protocol/          # JSON DTO、枚举、契约验证；Java 17 字节码
  agent-core/              # 模型、上下文、工具循环、本地日志；Java 21
  agent-worker/            # HTTP、SSE、启动装配、Linux 进程管理；Java 21
src/main/java/com/gitnova/service/agent/control/  # 新平台控制接线
```

旧根 `pom.xml` 当前声明 Java 17，并包含 Boot、AMQP、MyBatis 等依赖，不能把整个依赖树作为 Worker 的父运行环境。[G01] 共享协议以 Java 17 编译，避免 Server 引用 Java 21 class 后无法启动。新 Worker 用 JDK 21 镜像；本次不强迫 Server 升级 Java。

新源码名称均为拟新增，不是已经存在的类。Maven artifact 版本是构建身份，不是产品拆版本。

### 2.4 物理部署与多客户端：不把开发电脑当会话身份

Session 的业务身份、归属、Task 和回答索引由 GitNova Server/数据库持久保存。浏览器可以缓存 `sessionId`、输入草稿、该订阅最后看到的 `archiveOffset`，但不能成为会话唯一事实源。重新打开页面先查询Server；未发送草稿不会自动上传或跨设备同步。

默认“双机开发”布局：

```text
Mac：IDE + GitNova Server/Model Proxy（调试进程）
  ├─ Mac浏览器 ─────────────┐
  └─ Windows浏览器 ────────┤ 同一个GitNova公共API
                           ▼
                      GitNova Server
                           │ 私网HTTP命令 / SSE / 初始化包 / 导出包
                           ▼
Windows 32G：WSL2 Ubuntu + Docker Desktop Linux Engine
  └─ OpenSandbox Server → Linux/AMD64 Agent Sandbox
                                └─ Worker → Mac的Model Proxy
```

此图的数据库/仓库对象存储沿用现有部署；如它们也迁到Windows，必须备份并修改唯一Server的数据源与持久路径，不能两边各建一份互不相关的数据库却期待共享Session。常驻运行或正式部署时Server可以放在Windows的Linux环境或正式Linux服务器；角色边界与任务协议不变。06分别提供正式Linux布局、默认双机调试布局及Mac仅作客户端的运行选择。

多客户端只表示**同一账户在Mac与Windows各登录后访问同一Session**，不自动新增多人协作权限。每次查询、订阅、提交和取消都重新执行现有Session归属/仓库权限检查。两个不同账户没有因为知道sessionId就获得访问权。

同一Session可以有多个独立SSE订阅者，各自从自己的cursor补传。任一客户端断线或关闭，只结束该订阅；第二个设备访问已有Session不重新create Sandbox、不增加runnerEpoch。两个设备同时提交不同Task，仍由现有平台活跃槽和Worker受理锁裁决：一个被接收，另一个得到明确BUSY/409。重试同一逻辑提交保留同一幂等身份。

**关闭客户端不等于关闭运行宿主。** 默认布局下Mac停止Server也停止Model Proxy，不能承诺Worker仍能发出下一轮模型请求；Windows睡眠/重启会影响Docker与Sandbox，不能仅按浏览器断线处理。这些故障沿原有中断/重连/恢复语义处理，不伪装成透明继续。需要Mac合盖仍执行时，把运行服务也移到常驻机器，并保留同一持久数据。

代码从Mac到Windows以Git提交、构建产物或受控文件传输同步；**不把Mac活动工作目录通过SMB/NFS挂给Agent**，也不让两个编辑器直接写同一Session卷。初始化仍由Server导出固定Commit A，之后活动文件只由Worker修改。

## 3. Task 如何到达 Linux 中的 Agent

### 3.1 先建立一个可访问的应用端点

Worker 在容器内监听 `0.0.0.0:8081`。这意味着接收容器网络接口上的连接，不是直接把端口暴露给公网。端口对外如何可达由 OpenSandbox/部署网络决定。

平台为每个 Session 保存 `sandboxId`。发送任务前，平台通过 SDK 获取该 Sandbox 内 `8081` 服务的端点；官方 JVM SDK 提供 `getEndpoint(port)`，并提供 `useServerProxy` 配置用于无法直连沙箱地址的场景。[S03]

**本项目选择 Server-proxy 访问模式。** GitNova Server 不保存一个永久可用的 Docker IP，不在前端暴露 Sandbox 地址或管理凭据。重建后重新解析端点。

供应商返回的端点可能包含代理路径、协议/地址和必要 headers。适配器把它规范化为我们自己的 `WorkerEndpoint(baseUri, requiredHeaders)`。访问时保留前缀路径和必需 headers；不要用 `URI.resolve("/commands")` 把代理前缀截掉。SDK 对安全端点要求转发 headers 的说明见官方 SDK 文档。[S04]

不能假设 Server 的 `localhost:8081` 就是容器中的端口。默认双机布局中，Server的OpenSandbox地址是Windows可达私网地址，而Worker的模型代理地址是Mac可达私网地址。`host.docker.internal`只指容器所在Docker Desktop宿主，不会指向另一台Mac。完整地址矩阵见06；容器`localhost`也不代表上述两台主机。

### 3.2 请求经过什么

```text
用户输入：“修复空指针问题，并运行相关测试”
  ↓
POST /api/repos/{repoId}/agent/sessions/{sessionId}/tasks
  ↓ Server：验证用户和仓库写权限，保存 Task、预留活跃槽
  ↓ Server：从 Session 找到 sandboxId，解析 WorkerEndpoint
POST <WorkerEndpoint>/commands       Content-Type: application/json
  ↓ OpenSandbox 代理将 HTTP 转至容器应用端口
  ↓ Worker HTTP handler 解析 JSON
  ↓ TaskInbox 幂等受理、追加本地记录
  ↓ taskExecutor 启动 AgentEngine
  ↓ 文件和 Shell 工具在容器内部执行
```

这里有两个 HTTP 服务：平台的业务服务和 Worker 的控制入口。Worker 有 HTTP 入口，不等于又把 Harness 搬回平台服务；判断标准是 Agent 内部执行是否直接使用本地文件与进程，是否脱离平台的逐工具状态协调。

### 3.3 为什么不使用 SSH 或把任务拼成命令

不使用 `docker exec ... '<用户文本>'` 承载每条 Task。初始化进程可以由基础设施启动，但后续任务使用 JSON。用户文本里的引号、换行、中文和 `$(...)` 都必须作为普通文本进入模型上下文，而不是被 Shell 提前解释。

Worker 不为每条 Task 重启，不依靠终端页面或最后一行 stdout 判断任务完成。

### 3.4 接收与执行分离

Worker 受理成功后返回 HTTP 202，不等待模型完成。HTTP handler 必须迅速释放；长任务在 Worker 内的单任务执行器中运行。控制请求与事件连接使用独立执行资源，不能因为 Agent 正在调用模型而无法取消。

存在 Java 线程是正常的；我们去掉的是 MQ + 平台 Worker 的分布式执行派发链，不是去掉进程内部的并发。

JDK `HttpServer` 可以提供轻量 handler/执行器，Java HTTP 客户端支持发送请求与读取响应流。[S05][S06] 本方案选 JDK HttpServer + Jackson，避免为了几个私有入口再引入整套业务 Boot。

## 4. 协议：命令、事件和查询

### 4.1 API 清单

**平台公共接口**（保留已有前缀；具体 Controller 在迁移步骤中适配）：

| 方法和路径 | 含义 |
|---|---|
| `POST /api/repos/{repoId}/agent/sessions` | 创建/幂等重试 Session，返回准备状态和工作分支 |
| `GET .../sessions/{sessionId}` | 查询环境、活跃任务、最近归档和已发布 HEAD |
| `POST .../sessions/{sessionId}/tasks` | 提交新 Task，202 返回稳定 taskId |
| `GET .../sessions/{sessionId}/tasks/{taskId}` | 查询执行状态、answer、发布状态 |
| `POST .../tasks/{taskId}/steer` | 对尚未结束的任务追加指示 |
| `POST .../tasks/{taskId}/cancel` | 请求取消；返回受理状态，不谎称已经停止 |
| `GET .../sessions/{sessionId}/events?after={archiveOffset}` | 从服务端归档续传页面事件 |
| `POST .../sessions/{sessionId}/suspend` | 安全封存并回收空闲环境 |
| `POST .../sessions/{sessionId}/resume` | 从最近可信状态恢复环境 |
| `POST .../sessions/{sessionId}/close` | 封存并关闭；不是删除仓库分支 |
| `POST .../tasks/{taskId}/publication/retry` | 重试同一不可变成果的发布 |
| `POST .../tasks/{taskId}/publication/skip` | 保留成果归档但本次不推进分支，解除结算阻塞 |

省略号表示同一 `/api/repos/{repoId}/agent` 前缀，生成 OpenAPI 时必须展开，不能照抄省略号。

**Worker 私有接口**：

| 路径 | 含义 |
|---|---|
| `GET /health/live` | Worker HTTP 进程存活，不证明可执行任务 |
| `GET /health/ready` | 返回 sessionId、runnerEpoch、状态、工作树初始化结果 |
| `POST /commands` | 统一接收命令，按 type 分发 |
| `GET /commands/{commandId}` | 查询受理/拒绝/执行结果，用于发送超时后的核对 |
| `GET /tasks/{taskId}` | 查询本地任务执行与结算状态 |
| `GET /events?epoch={n}&after={seq}` | 重放并持续输出指定事件流 |
| `GET /exports/{exportId}` | 下载已封存、不可变的成果包；不接受任意文件路径 |

HTTP 响应错误使用稳定 `code` 与可读 `message`，不回显密钥、宿主路径或整段异常栈。

### 4.2 命令信封

```json
{
  "schemaVersion": 1,
  "commandId": "cmd-...",
  "sessionId": "s-...",
  "runnerEpoch": 1,
  "type": "SUBMIT_TASK",
  "taskId": "t-...",
  "attemptId": "a-...",
  "payload": {
    "message": "修复空指针并运行测试",
    "expectedPublishedHead": "确定的提交身份",
    "deadlineAt": "服务端生成的 UTC 时间"
  }
}
```

身份由平台生成，不能由模型指定。`attemptId` 对应一次明确的执行尝试；网络重发不创建新 attempt。只有已经确认中断且用户选择继续/重试，才创建新的 attempt。

`runnerEpoch` 是粗粒度实例所有权代数。重建环境时平台增加它，不在每次读写文件时增加。它不是旧 Workspace generation。

命令类型及规则：

- `INITIALIZE`：只在 BOOTING/尚未初始化时导入已上传的可信启动包；重复相同内容返回原结果，不能覆盖运行中的文件。
- `SUBMIT_TASK`：IDLE 且没有未结算 Task 时受理。相同 commandId + 相同规范化内容返回原任务；相同 ID + 不同内容为 409。
- `STEER_TASK`：先持久接收，在工具批次结束/下次模型调用前应用；若最终回答已经提交，则返回 `TASK_ALREADY_FINISHED`，不悄悄创建新 Task。
- `CANCEL_TASK`：控制线程立即设置取消信号，取消模型 HTTP 请求、请求停止命令进程；只有确认停止后写取消结果。
- `SEAL_SESSION`：进入不再接收新任务的结算屏障，固定代码与会话状态；活跃任务不被悄悄杀掉，返回明确 BUSY 或由用户先取消。
- `ACK_PUBLICATION`：平台已存好归档并明确发布结果后，Worker 更新已发布 HEAD/保留旧 HEAD，释放本次结算屏障。内容必须绑定 exportId 和 taskId。
- `CLOSE_SESSION`：仅在空闲且需要保留的成果已确认归档后退出，不先删除工作数据。

命令规范化采用固定字段 DTO 的确定性 JSON；不依赖输入字段顺序。用于幂等比较的摘要不包含重试时变化的 HTTP 请求追踪头。

### 4.3 受理响应与状态码

新受理返回 202 和 `accepted=true`。相同请求重复到达返回 200、`duplicate=true` 和原执行状态。初始化未就绪返回 503；另一个任务占用 Session 返回 409；不匹配身份/凭据返回 403；结构非法返回 400；超过请求大小返回 413。

平台公共 Task POST 在**自己的数据库事务提交后**即可返回 202。它表示平台已受理，不表示 Worker 已接收，也不是任务完成。页面显示“正在发送/环境准备/执行中”等分别由状态决定。

### 4.4 事件信封与 SSE

```json
{
  "schemaVersion": 1,
  "sessionId": "s-...",
  "runnerEpoch": 1,
  "sequence": 42,
  "eventId": "s-...:1:42",
  "taskId": "t-...",
  "attemptId": "a-...",
  "type": "MODEL_RESPONSE",
  "payload": {"modelCallId": "m-...", "finishReason": "STOP", "text": "最终正文", "toolCalls": []}
}
```

`sequence` 在一个 epoch 内由本地单写入日志分配。相同 epoch 的 Worker 重启继续已有序号；从旧快照新建环境则使用新 epoch，不能回退序号后覆盖服务端既有记录。事件身份和历史引用包含 epoch，不依赖当前容器路径。

核心事件：`COMMAND_ACCEPTED`、`TASK_STARTED`、`MODEL_CALL_STARTED`、`MODEL_RESPONSE`、`TOOL_STARTED`、`TOOL_RESULT`、`CONTEXT_SUMMARY_CREATED`、`STEER_APPLIED`、`ANSWER_DELIVERED`、`TASK_FINISHED`、`SNAPSHOT_SEALED`、`TURN_SETTLED`、`RECOVERY_INTERRUPTED`。

完整模型响应与工具结果是事实记录。可见的逐字输出/日志片段是展示事件；不靠片段拼接替代最终完整响应。推理内容是否保存按现有模型协议处理，默认不经公共页面事件暴露。

Worker → Server 使用 SSE。Server 主动建立私有 GET 连接，Worker 在响应体中持续写事件。**这已经实现结果回传，不需要 Worker 再反向调用 Server 的事件回调接口。** 命令向下 POST，事件沿 GET 响应向上返回。

SSE 使用 `text/event-stream`、UTF-8、事件 ID 和空行分帧；需要主动刷新输出。心跳注释不占业务序号。SSE 标准提供事件 ID/重连语义，但事件存储、查重、补发必须自己实现。[S07]

Server 每次先保存事件和投影，再更新该 epoch 的连续接收游标。收到重复事件且摘要相同则忽略；身份相同但内容不同要报警并阻止继续投影。跳号时从最后连续位置重连；不能直接跳到最新序号。

Worker 订阅实现用“读日志到当前尾部—等待追加通知—从游标继续读”，不能先播放旧日志再盲目注册监听，留下二者之间的丢帧窗口。慢客户端不阻塞 Agent：只断开该订阅，重连从本地日志重放。

### 4.5 页面进度与回答

前端只连 GitNova Server。公共进度流从平台归档输出，游标是 `archiveOffset`，不要直接用当前 Worker 序号作为跨 epoch 的页面游标。

当前系统使用 Header 认证时，前端选 `fetch` 流式解析 SSE，不把 Bearer Token 放 URL，也不假设原生 EventSource 可以任意添加 Authorization 头。解析必须处理 UTF-8 字符跨 chunk、CRLF、空行和多行 data；测试不能假设一个网络 chunk 等于一个事件。

公共查询仍维持用户已确定的形状：

```json
{
  "status": "COMPLETED",
  "terminalReason": "ANSWER_DELIVERED",
  "answer": {"content": "原始 STOP 正文"},
  "publicationStatus": "PENDING"
}
```

答案查找依据完成事件所引用的原始响应 ID。平台校验同 Session/Task/attempt、正文非空、STOP、无工具调用；不从“最后一条 assistant”推断答案。[U01]

### 4.6 各命令的 payload 与可重试语义

这张表是实现 DTO 的依据。表中身份来自平台，内部路径由 Worker 配置推导，不让外部请求指定任意目录。

| type | payload 中的必要字段 | 成功意味着什么 | 重复/失败时如何处理 |
|---|---|---|---|
| INITIALIZE | bootstrapId、bootstrapSha256、baseCommit、publishedHead、runtimeConfigDigest | 已从固定启动目录读取并校验启动包，工作树与本地状态就绪 | 同摘要重复返回原结果；不同内容不能覆盖已初始化会话 |
| SUBMIT_TASK | message、expectedPublishedHead、deadlineAt | 命令和Task已本地受理，之后异步执行 | 同commandId不重启；同ID不同内容409 |
| STEER_TASK | message | 指示已保存，尚不意味着已经用于模型请求 | 返回acceptedSequence；STEER_APPLIED再报告实际应用位置 |
| CANCEL_TASK | reason | 取消请求已接受，正在停止 | 真正停止后出现CANCELLED；已结束返回原结果 |
| SEAL_SESSION | purpose（SUSPEND/CLOSE/MANUAL）、expectedActiveTaskId（可空） | 已受理在安全边界封存的请求 | 活跃任务不被隐式终止；包已存在则返回同exportId |
| ACK_PUBLICATION | exportId、archiveId、publicationId（可空）、outcome、publishedHead | 平台确认归档及出版结论，Worker可以结算当前Task | 必须匹配当前待结算包；重复确认不再推进状态 |
| CLOSE_SESSION | confirmedArchiveId | 所需数据已保存，可以有序停止Worker | 未完成归档返回冲突；不负责自行删除持久卷 |

`ACK_PUBLICATION.outcome` 限定为 PUBLISHED、NO_CHANGES、SKIPPED、NOT_REQUIRED。FAILED/CONFLICT不是成功ACK：平台先重试，或用户明确跳过；不能用失败ACK悄悄放行下一Task。

`GET /commands/{commandId}` 返回原请求摘要、受理/拒绝状态、关联Task与当前执行状态；404只说明该Worker当前日志未发现此身份，不代表别的epoch或已经丢失的实例从未执行。`GET /tasks/{taskId}` 同时返回executionStatus与settlement状态，避免只看COMPLETED就误判可以提交下一Task。

### 4.7 选择HTTP + SSE的取舍

POST表达离散命令，GET事件流表达持续结果；无需双向WebSocket会话状态，也不要求Worker主动连接平台回调。但平台要维护到活跃Worker的流连接，代理必须支持流式flush和足够的读超时。SSE不是可靠消息系统，可靠性来自本地日志、事件身份、平台事务游标及重放。

本项目不把每个Tool执行封装成网络命令，也不让SSE连接承载执行所有权。事件连接断开，只影响可见性和归档延迟；超过存储/任务期限后，Worker按明确策略暂停或结束，而不是无限积压。

## 5. 任务受理、并发与无 MQ 可靠发送

### 5.1 平台数据库只保留业务级事实

新增接线不复用旧 MQ 的 Run claim 过程。保留现有 Session/Task 身份与历史查询，扩展以下逻辑信息；实际列迁移在最新本地基线上编写：

| 位置 | 必要信息 |
|---|---|
| Session | actor/repo、sourceBranch、baseCommit、agentBranch、activeTaskId、executionBackend、状态 |
| Sandbox binding | sandboxId、runnerEpoch、应用 readiness、到期时间、最近归档、配置/镜像摘要 |
| Task/attempt | 请求内容与摘要、执行状态、当前 attempt、发送命令 ID、answerEventId、最终原因 |
| Control command | commandId、内容摘要、PENDING/DELIVERED/UNKNOWN/REJECTED、下次核对时间 |
| Event archive | eventId、epoch/sequence、归档 offset、Task/attempt、内容摘要与 payload/大结果引用 |
| Publication | exportId、expectedHead、结果 Commit、固定 message/time、状态与错误 |
| Snapshot archive | bundle 摘要、对象位置、事件覆盖、工作树摘要、发布 HEAD |

这里的 Control command 记录是未完成业务动作的交付记录，不是 RabbitMQ 替身，不复制整个工具生命周期。后台核对只处理少量“可能未送达/未结算”的任务级记录。**彻底不保留未送达意图，就无法保证 Server 在数据库提交后、HTTP 发送前崩溃时任务不丢。**

### 5.2 一次提交的顺序

1. 用当前数据库权限检查 actor 与 repo；锁 Session 行，确认可接收任务。
2. 先按请求幂等键查已有 Task。命中则验证请求摘要并返回原 Task，即使它已经结束也不能再次执行。
3. 没有已有 Task 时，确认 `activeTaskId` 为空，插入 Task/attempt/control command 并占用槽；一个短事务提交。
4. 事务外发送 HTTP。不可持有数据库事务等待模型、Sandbox 冷启动或网络。
5. 发送失败标为 UNKNOWN/PENDING，核对器使用**同一个 commandId 与 attemptId**重发或查询。
6. Worker 收到请求，持久记录 COMMAND_ACCEPTED，再启动执行；重复请求只返回记录。

从任务表核对待发送意图可以恢复服务端崩溃，不需要把模型 Loop 放回 Server 线程池。服务端仍需要有限的 I/O 线程用于 HTTP，不承担实际 Coding 工作。

### 5.3 运行与控制不能互相堵塞

Worker 有一个 Agent 执行线程/执行器和独立控制 handler。对 SUBMIT 的“检查空闲—记录受理—设当前任务”使用同一短锁。取消信号是线程安全对象；STEER 队列有上限。超过上限明确拒绝，不无界累积。

收尾时，在同一任务边界锁下检查已经受理但未应用的 STEER，再决定是否提交 ANSWER_DELIVERED。否则“用户刚补了一句，模型刚好结束”会丢指示。

CANCEL 与自然结束也在终态提交点裁决：取消先被接受且仍可作用，则不再提交正常回答；最终回答已经提交后取消返回 already-finished。两种路径不能各写一个相互冲突的终态。

## 6. Agent Worker 的本地工作模型

### 6.1 模块职责

`AgentEngine` 运行模型—工具循环；`ContextCoordinator` 组装上下文；`FileSessionLog` 保存原始事实；`ToolRuntime` 分发本地工具；`ProcessSupervisor` 管命令及子进程；`AgentWorkerServer` 只负责传输与调度边界。

这些名字定义责任，不要求一开始写十层接口。纯算法可直接类组合；只有模型连接、本地状态与跨系统边界需要可替换接口。

### 6.2 基础工具面

- `shell`：脚本、cwd、超时；执行 `bash`/`rg`/构建命令。cwd 必须在允许工作根内。
- `read_file`：按范围读取文本；读取完整字节不经平台；返回是否截断和继续读取位置。
- `edit_file`：明确区分创建、精确替换、删除；旧文本/内容哈希不匹配则拒绝，不能静默覆盖。
- `history_read` / `history_search`：保留当前 Session 原始结果的精确读取和有界文字检索。不是本次新建平台搜索引擎。

Read/Edit 保留是为了稳定交互，不是 Linux 无法做到。`listFiles/findFiles` 等可以并入原生命令。不要仅凭工具数量减少就宣称效率提升，必须回归实验。

`ToolRegistry` 可以保留成一个普通 Map 分发器；取消的是 Spring 注入及平台执行依赖，不是 schema 校验和统一错误语义。

### 6.3 命令执行

使用 Java ProcessBuilder 指定 cwd、环境与 argv；需要 Shell 语义时明确启动 `/bin/bash -lc`。[S08] 模型生成的脚本只在允许的 Sandbox 内执行；用户原始 Task 不直接执行。

stdout/stderr 并行消费，避免管道堵塞。完整结果在有配额的本地结果文件中保存，给模型有限预览；超过硬存储上限时明确 `captureTruncated=true`，不能声称完整回查仍可用。

非零 exitCode 是命令运行事实，不自动等于工具基础设施失败。超时、无法启动、用户取消、正常非零退出分别编码。

每条命令用独立进程组执行并登记。取消先 TERM，再经过宽限 KILL，确认停止。ProcessHandle 的一次 descendants 枚举不能证明所有逃逸进程都停止；不能确认时将 Worker 置为无法安全继续，由平台停止整个 Sandbox。只有确认旧实例结束后才可以重建/重新挂载可写卷。

后台服务也必须登记；需要浏览器预览可以使用受管理的后台句柄，但本次不新增完整在线 IDE。封存时停止可能写代码的后台进程，不用“它应该是只读”充当保证。

### 6.4 Context 迁移契约

保留滚动摘要、输入预算、最近完整交互组、大结果外置、小结果稳定来源、历史回查，以及原始响应到最终 answer 的精确关联。[U01][U02][G04]

初始沿用已经工作的阈值配置，不趁迁移调 75%/80%/85%。摘要与原始记录分别存储：摘要覆盖语义，不覆盖原始证据。新 Task/历史 Task 的限制必须带范围；不能把上一条“只改测试”的指令标成当前所有任务的限制。

历史结果身份采用 `resultId = sourceEventId`，提供轻量本地 path/URI 映射。不能把 `/session/state/...` 的真实绝对路径当作跨容器永久身份，也不应仅因路径更自然就扔掉来源字段。

一次搜索找到足以回答当前问题的证据可以停止；只有声称“不存在”“全部”“最后一次”等需要对应范围完整性的结论才必须穷尽相关范围。不要引入强制遍历全历史的工具指令。

### 6.5 正常 STOP

有效 STOP 正文先持久保存为完整模型响应，再成为最终 answer。只有 reasoning、正文空、长度截断、仍包含 tool calls，都不能冒充正常回答。[U01]

新架构不用每次请求前全树 fingerprint，但 Worker 仍需确认自己发起的工具批次已经结束、没有待应用指示、当前执行未取消。代码封存有自己的静止边界。移除旧 drift 检查前，要先禁止平台和第二个 Worker 并发修改活动工作树。

## 7. 状态存储、归档与结算屏障

### 7.1 不恢复重 Workspace

建议一个 Session 的命名卷挂载到 `/session`，Worker 配置：工作树 `/session/worktree`，状态 `/session/state`；`/session/worktree`、`/session/state` 可通过受控目录映射指向它们。也可以采用两个卷，本文实现统一用一个会话卷以便归档。

这只是文件存储，不为每个文件建立数据库行。旧 Workspace generation/fingerprint 不再逐工具同步。

Docker 卷独立于容器；它不保护宿主磁盘故障。[S09] OpenSandbox 的挂载配置与已发布 SDK 兼容性由接入测试确认。[S01]

### 7.2 本地事实日志

按 epoch 保存 JSONL，单个写入者负责序号、字节追加和必要 fsync。受理、原始模型响应、工具开始/结果、回答、任务终态、封存引用是耐久边界。UI 的逐字 delta 可以聚合，不要求每 token 一次 fsync。

写大结果先临时文件 + force + 原子 rename，再追加引用事件。中途崩溃留下无引用文件可以清理；不能先追加永久引用却尚未保存数据。

启动扫描只允许修剪未完成的最后一条记录，并保留损坏样本；中间缺行、内容摘要不匹配则停止恢复，不能跳过后假装连续。

已有进行中的 Task 在进程重启后标为 INTERRUPTED，不自动重放未知副作用。确认“尚未开始”的命令能安全重新受理，已经受理的同 ID 请求仍然返回原记录。

### 7.3 为什么回答完成后还需要短暂结算

当模型回答时，本地文件还不是稳定的仓库 Commit。为了不让 Task 2 的文件混进 Task 1 的提交，选择以下顺序：

```text
持久 MODEL_RESPONSE
  → ANSWER_DELIVERED / TASK_FINISHED
  → Worker 进入 FINALIZING，暂不受理下一条普通 Task
  → 停止写入进程，封存文件树与会话状态
  → SNAPSHOT_SEALED(exportId)
  → Server 下载、校验并耐久保存归档
  → Server 发布 Commit 或确认无变化/用户明确跳过
  → ACK_PUBLICATION
  → Worker 写 TURN_SETTLED，进入 IDLE
  → Server 清除 activeTaskId
```

这是任务级交付屏障，不是每个 Tool 的分布式事务。它牺牲少量任务间延迟，换取顺序清楚、没有多份待发布工作树的实现。发布失败时回答仍可见，下一条任务暂时被阻塞；用户可以重试或在已归档的前提下明确跳过发布。

取消/失败也要保存可恢复的脏工作状态，但默认不自动发布代码。下一次继续时明确带上“前次中断，存在未发布变化”；不悄悄清空工作树。

### 7.4 封存包

使用 ZIP + manifest（JDK 可处理），按**固定的文件树快照**导出，不直接开放任意文件下载接口：

```text
bundle.zip
  manifest.json
  tree/...
  state/summary.json
  state/events/...
  state/tool-results/...
```

manifest 至少包含 sessionId、taskId、attemptId、epoch、事件覆盖、初始 baseCommit、expectedPublishedHead、treeDigest、文件路径/大小/SHA256、状态快照摘要、Worker/镜像配置摘要。

封存时先固定 `throughSequence=N` 和对应日志字节边界，只复制完整到N的记录；不要把仍可能被控制handler追加的活动日志直接作为ZIP输入。封存后产生的SNAPSHOT_SEALED/ACK等由平台的归档元数据和后续日志补充，不冒充已存在于包内。

导出暂存与已完成ZIP放在 `/session/exports`（或独立导出目录），不放进将被递归打包的 `state/` 或 `tree/`。旧ZIP、下载临时文件与构建缓存不进入恢复包，防止递归膨胀。只有确认平台耐久接收后，才能清理对应本地导出对象。

使用压缩包只是一种传输格式，不代表 ZIP 本身安全。平台导入前拒绝绝对路径、`..`、重复路径、符号链接/特殊文件、超额解压、摘要不匹配；文件字节与换行必须原样保留。

源 Commit 已跟踪的文件不能因为新排除规则被静默删除；排除规则主要作用于新生成的构建产物、缓存、依赖目录。固定 `.git`、Agent 内部状态等不应作为代码发布。原有对象格式不能表达的文件类型必须显式拒绝，不静默跳过。

当前 GNOV Commit 主要表达 path→blob，不完整表达原生 Git 的 mode/symlink 等元数据。[G06] 沙箱恢复包可保存受支持的普通文件执行位；发布不能声称已经获得原生 Git 完整兼容。`mvnw` 等脚本执行能力要在镜像测试中确认，必要时用明确的 Shell 调用而不是猜执行位。

## 8. Session 与 Sandbox 生命周期

### 8.1 初始化原子点

短事务中创建 PROVISIONING Session，记录固定 A、分支名、幂等键、执行后端。准备环境的慢操作在事务外。

本方案选择：同一个 Session 初始化流程中，**在 Worker 基于 A 初始化就绪后**，用短事务创建指向 A 的 Agent 分支并将 Session 标为 ACTIVE。不是等第一条 Task 才建分支，也不为初始化造空 Commit。

如果分支创建或事务失败，Session 仍是 PROVISIONING/FAILED；按幂等键与固定身份继续/清理。接口不能提前把未成功准备的环境显示为可工作的 Session。

分支名 `agent/<完整SessionId或防碰撞编码>`，遵循现有长度规则；若同名已存在且不归此 Session，返回冲突，禁止覆盖。新增资源创建请求超时先核对 metadata/session 标签，不盲目再次创建，清理孤儿实例时也要确认无当前绑定。

### 8.2 空闲与续期

使用 SDK 续期，平台定时核对剩余期限；不要假设关闭 SDK 客户端就会销毁 Sandbox。[S10] 建议工程默认：实例 TTL 30 分钟、每 5 分钟续期、IDLE 15 分钟尝试封存回收；这些是待环境测试调整的初值，不是性能承诺。

RUNNING 或 FINALIZING 不触发普通 idle 回收。Worker 心跳健康与模型暂时无输出分开：长推理期间没有 token 不代表进程死了。

回收前确认归档、事件和发布结果；没确认成功就显示回收受阻，不先删卷。容器停止确认后可以回收实例，持久会话卷保留到配置的保留期；真正删除卷需用户删除会话或既定清理策略并记录。

### 8.3 故障表

| 故障 | 处理 | 不允许的处理 |
|---|---|---|
| 浏览器断开 | Server/Worker 继续；前端游标重连 | 取消任务 |
| Server→Worker POST 超时 | 同 ID 查询/重试受理 | 新建第二个 Task |
| Server 重启 | 根据绑定重连事件，核对未送达命令 | 让 Agent 从头再做 |
| Worker 进程崩溃，卷保留 | 先确认没有残留写进程；恢复日志，活跃 attempt 记中断 | 盲目重放 Shell |
| Sandbox 被销毁，卷保留 | 确认旧实例停止，增加 epoch，启动新环境与一致状态 | 新旧共享同一可写卷同时执行 |
| 卷/宿主丢失 | 用最近归档恢复；明确之后的进度可能丢失 | 只恢复对话而声称代码没丢 |
| 平台不可达但 Worker 还活 | 当前任务本地运行；记录有界缓冲；结算前等归档/发布确认 | 无限无配额运行或忽略任务 deadline |
| 发布失败 | 重试同一个 export/publication | 重新调用模型修改代码 |
| 权限被撤销 | 停止新代理请求与发布；已有本地操作按任务 deadline/取消收口 | 用启动时权限永久发布 |

旧环境没有确认死亡时不能迁移写权。epoch 只能拒绝旧平台请求，不能阻止旧进程写共享磁盘。

### 8.4 恢复输入

恢复包中的对话、摘要、工具结果和工作树必须来自同一 seal 覆盖。新环境的开始事件写明 `restoredFromSnapshot`、`restoredCodeHead`、`coveredThrough`、`unpublishedChanges`。如果从更早 Commit 降级恢复，旧的未来轨迹仍可作为历史查看，但不能当作当前工作进度送回模型。

## 9. 仓库发布与 PR 的完整边界

### 9.1 复用与提取

现有 `GitObjectCodec`、`GitObjectHasher`、`ObjectStorage`、`BranchMapper`、`CommitRecordMapper` 可继续作为仓库底座。旧 `TransferService.updateHead()` 已体现对象就绪后发布 HEAD、首次插入/后续 CAS 和元数据记录，但其中方法有 private 和 Push 专属语义。[G05][G06][G07]

不要简单从 Agent 调一遍 HTTP push。提取平台内部 `BranchPublicationService`，普通 Push 与 Agent 发布共享权威检查。新的 Agent 工作分支在绑定存续期间由平台出版接口管理；普通 Push 对受管分支应拒绝或走明确的维护入口，不能绕过 Session 的基准。

### 9.2 发布步骤 1. 保存不可变 export 并验证来源、路径、大小、hash。重新检查仓库写权限。
2. 以 `(sessionId, exportId)` 唯一创建 Publication；一次性固定 expectedHead、message、timestamp、author 信息。
3. 与 expectedHead 的**完整树**比较。相同则记录 NO_CHANGES；否则构建新 Blob 和单父 Commit。首次父为 A，后续父为上次已发布 B。
4. 保存对象。重复保存内容寻址对象应可重用；不要在重试时重新生成 timestamp，导致同一成果产生不同 Commit。
5. 短数据库事务中检查 Publication 身份与状态，CAS 工作分支，写 CommitRecord、更新 Publication/Session 的发布 HEAD。
6. 成功后发送 ACK_PUBLICATION。ACK 丢失重发同 ID；数据库已 PUBLISHED 时返回原 Commit，不再次创建。

对象存储写入无法靠 MySQL 回滚；失败可以留下不可达对象，但不能发布引用缺失对象的 HEAD。CAS 冲突不 force，不自动把父改为新 HEAD 覆盖他人提交。[G05]

注意撤销：工作树恢复到最初 A，但当前工作分支在 B 时，这仍然需要提交一个以 B 为父、内容为 A 的新 Commit。不能用“相对初始 A 无 diff”跳过它。

### 9.3 PR 是仓库功能，不是 Agent 工具

本次实现同仓库 PR：源分支、目标分支、作者、title/body、OPEN/CLOSED/MERGED、draft、revision、评论、最终 mergedCommit。Agent Session 只是可选关联。

支持在工作分支仍指向 A 时建立 Draft PR，明确显示“暂无已发布差异”，禁止无差异合并。随着平台发布 B/C，PR 根据最新源 HEAD 展示内容。没有 PR 也可以查看分支 Diff。

工作中的临时差异与已发布 PR Diff 分开。默认页面看已发布内容。用户点击“预览当前改动”时，Worker 仅在下一个工具安全边界导出有界预览；执行尚未结束显示等待，不能声称看到逐字实时、事务一致的文件树。

### 9.4 合并策略：保留当前对象格式，同时处理目标分支前进

这是本文的明确设计取舍：**支持快进与三方 squash 合并，不新增双父 Merge Commit 格式。** 不是只做 PR CRUD 后把合并无限延期。

- 目标 HEAD 是源 HEAD 的祖先时，可选择 fast-forward，保留源提交链。
- 目标分支已经前进时，查共同祖先，三方合并 `base/target/source` 文件树；成功后创建以当前 target 为唯一父的新 Commit，记录 PR 的 mergedFromHead。界面标明 squash。
- 非冲突文件按三方规则处理：source==base 取 target，target==base 取 source，source==target 取共同内容；删除/新增/二进制冲突明确报告。
- 同一文本文件双方都修改时，使用成熟三方内容合并算法，不自己手写脆弱补丁拼接。建议将 JGit 的 `MergeAlgorithm` 作为纯内容库调用；不启用它的仓库传输或替换 GNOV 存储。[S11]
- 合并前固定 sourceHead、targetHead、PR revision；计算在事务外，提交时重新锁 PR，按稳定顺序确认两个 branch HEAD 未变，再更新目标和 PR。冲突/HEAD 改变返回 409，不写成功状态。
- 冲突时返回具体文件与版本，不把冲突标记当可合并代码。用户可让 Agent 在工作分支修复或另建任务后重新尝试。

由于 squash 不保留双父血缘，本次在一个 Agent 工作分支的 PR 已 MERGED 后，将其 Session 标记为工作流完成，不继续往该已合并工作分支堆新任务。下一个不相关/后续工作从目标最新 HEAD 新建 Session。这避免把已 squash 的差异重新作为新贡献计算，也符合一项连续工作对应一条 Session 分支的约定。

真实 Git 的多父图、跨仓库 PR、重命名启发式和组织保护规则不在本次范围。单父提交链和三方 squash 的限制须在产品上明示，不冒充 GitHub 全兼容。

## 10. 安全与网络：边界先接好，加固后集中做

基础阶段只用于可信测试仓库和受控用户；不宣称可立即托管任意互不信任用户的代码。

平台与 Worker 使用独立的短期控制身份，且每条命令核对 Session/epoch。OpenSandbox 管理 API Key 不进前端，不进任务正文。Worker 控制密钥使用独立 header，避免覆盖端点 requiredHeaders 中的 Authorization。

模型调用走平台 Model Proxy：认证 Worker/session/模型范围，注入供应商真实 key，设置额度和超时。真实 provider key、MySQL、MQ、JWT 签名私钥不进入沙箱。代理不是 Agent Loop，不维护 messages 或替模型决定工具。

不能保留旧 `network none` 同时期待新 Worker 能联网请求模型；需要允许模型代理和必要依赖源。只是设置 HTTP_PROXY 环境变量不能防止直接出网，正式出站控制必须由网络层落实。复杂 egress、额外内核隔离、Secret Vault 集中在后续安全实施步骤完成，但入口/出口位置从现在固定。[S12]

Worker 与工具程序同处环境，不代表内部状态天然防篡改。开发阶段不以本地日志作为权限依据。公开部署前验证文件权限、可写目录范围、Agent/子进程身份分离或等效隔离；并始终由平台独立校验出版对象和授权。

## 11. 观测、限额与错误展示

日志统一携带 sessionId、taskId、attemptId、runnerEpoch、commandId/eventId；模型供应商 requestId 单独保存。禁止在普通日志打印凭据和完整私有源码。

至少记录任务发送等待、Sandbox ready 耗时、模型/工具耗时、上下文与摘要 token、事件积压、最后连续归档序号、未结算出版、Sandbox 到期、清理失败。

资源上限必须同时限制：平台活跃 Session、Worker 单 Session 任务数、HTTP body、控制队列、输出预览、完整日志/结果、工作树文件数/字节、Shell 子进程、SSE 订阅。参数集中配置，测试用小上限触发边界，不把某个固定数当可推广 SLO。

错误不混为“Agent 失败”：发送未确认、环境未就绪、模型协议错误、命令退出非零、执行中断、快照失败、发布冲突、PR 冲突，应分别可读。

## 12. 迁移完成的定义

不是新 JAR 能启动就完成。需要同时满足：

- 新 Task 使用 `SANDBOX_AGENT` 后端，全链没有旧 MQ 分发或平台 Workspace 的逐工具调用。
- 旧 `finishTask` 不在新模型工具定义内，自然回答保真；旧 Run 的历史还可读。
- Context、历史结果和多 Task 行为回归通过，比较时明确模型/环境/工具面变化。
- Task 通信、取消、重连、归档、出版、PR、回收和降级恢复各有故障测试。
- 旧活动任务已经排空，新旧后端不能处理同一任务；不重放旧队列改造用户文件。
- 旧执行组件、配置、启动依赖和无用测试替身已经删除或移到只读历史适配，不只是停用一个开关。
- 撤回新链时只停止接收并保留成果，不让旧 Runtime 接管它不理解的新会话状态。

最终架构原则：**执行状态共置；平台权限与持久成果外置；通信收缩为任务级；恢复只承诺明确安全边界。**
