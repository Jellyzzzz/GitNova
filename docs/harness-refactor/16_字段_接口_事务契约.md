# 16｜字段、API、SQL与事务契约

## 1. 命名与迁移原则

数字ID沿用现有user/repository/branch的类型；Session/Workline/Operation使用UUID文本身份；Commit仍是GNOV SHA1身份，包和文件校验用SHA256，二者不能互换。时间在服务中用Instant，数据库DATETIME(6)统一UTC。分支历史引用使用branchId与创建时显示名，不能只靠可被删除重用的name。

本包数据字典是目标契约。已执行Flyway不改，不运行DROP；先用H0的实际schema做增量diff。统一包只有schema/target.sql.reference一套目标：已经执行的旧表只追加迁移，尚未执行的直接从统一目标生成，不先装旧再删。

SQL例子中的 `:name` 为参数语义，落地MyBatis用`#{name}`；表名固定，不拼用户字符串。索引/外键实际migration要在真实MySQL检查。示意SQL不是已部署事实。

## 2. Session相关数据

### agent_workline（新增）

`workline_id` PK；`session_id`归属；`ordinal`会话内序号；`repo_id`；`base_commit`固定起点；`published_head`确认远端；`source_branch_id`保留稳定历史ID；仅无法映射的迁移旧行可空，并保留source_branch_name；`target_branch_id`及target_branch_name；`status` PREPARING/ACTIVE/MERGED/RETIRED/SOURCE_MISSING；`latest_recovery_archive_id`；`merged_pr_id`可空；`version`；created_at/updated_at。

唯一(session_id,ordinal)，受管source_branch_id唯一。活动指针由Session.active_workline_id维护，不用status=ACTIVE去猜“当前”，因为MERGED工作线仍可能是当前可分析的代码。分支删除后保留稳定旧身份/名字快照，不自动把同名新分支接回来。历史引用不配置ON DELETE CASCADE/SET NULL；可指向已经物理删除的分支身份，但当前操作必须重新检查活分支存在。若采用软删除，则同样保证同名新建获得不同ID。

### agent_session（增量，不另建表）

新增active_workline_id、session_version、sync_operation_id、next_runner_epoch、current_runner_epoch等，完整增量列见唯一目标SQL。next_runner_epoch是已分配上界，失败准备实例的epoch也不能回收复用。旧base_commit/agent_branch_name/last_published_head是旧单线结构：新写路径不再以它们为真源；迁移可暂做只读兼容，不与workline双写两套“权威HEAD”。workflow_state只表达OPEN/CLOSED；已有MERGED行迁移成旧工作线MERGED与Session OPEN必须核对用户实际关闭状态，不能批量把人工关闭的会话重开。

### agent_sync_operation（新增）

sync_id PK、session_id、actor_id、request_key、request_digest、old_workline_id、expected_session_version、target_branch_id、target_head、change_policy、expected_tree_digest、old_archive_id、old_tree_digest、old_published_head、old_epoch、bootstrap_id/bootstrap_sha256/bootstrap_storage_key、new_workline_id、new_epoch、state、error_code、created_at/updated_at。

state=PREPARING/SNAPSHOTTING/INSTALLING/SUCCEEDED/CONFLICT/FAILED。唯一(session_id,actor_id,request_key)。准备中的newWorkline不自动成为active。失败之后需要新的目标/策略使用新requestKey；临时恢复同意图保留syncId。不能把超时强制记FAILED来绕过未知安装状态。

### 既有Agent表的增量

Binding、Task、Attempt、Command、EventArchive、Archive、PlatformOperation、Publication固定workline_id；条件更新都核对scope。旧event的JSON及digest不重写，迁移只增加可追溯的归属映射。新command/event/manifest字段见19。Token作用域绑定session/workline/epoch和用途，模型不选择这些身份。

## 3. PR数据

### pull_request

id PK、repo_id、number、author_id、source_branch_id、target_branch_id、source_branch_name/target_branch_name历史显示、title、body、status OPEN/CLOSED/MERGED、draft、version、created_repo_sequence、closed_repo_sequence可空、merged_repo_sequence可空、closed_source_head/closed_target_head/closed_comparison_base可空、source_workline_id可空、merged_from_head/merged_target_head/merged_commit、create_request_key/create_request_digest、created_at/updated_at/merged_at。

唯一(repo_id,number)；唯一(repo_id,author_id,create_request_key)；生成列open_slot=`CASE WHEN status='OPEN' THEN 1 ELSE NULL END`，唯一(repo_id,source_branch_id,target_branch_id,open_slot)。关闭时保存确定source/target HEAD；comparisonBase未计算可空，后续按这两个固定HEAD求得。已合并使用merged_*，不因源分支删除改写。新PR始终有分支ID，删除后历史ID不置空；nullable只兼容无法映射旧数据。MERGED不可重开。版本通过UPDATE WHERE version=:expected推进，修改0行不是成功。

### pull_request_revision

id、pr_id、source_branch_id、repo_sequence、source_head、target_head_seen可空、comparison_base可空、source_event_id、occurred_at。唯一(pr_id,source_branch_id,repo_sequence)，源事件身份重复返回原记录。首revision用创建PR时分配的repoSequence；异步版本用分支事件sequence，不拿全局自增id作业务顺序。

### pull_request_comment

id、pr_id、author_id、body、version、request_key/request_digest、reply_to可空、thread_root可空、resolved、deleted_at、created_at/updated_at；anchor字段可空：comparison_base、source_head、path、side LEFT/RIGHT、start_line/end_line。普通评论所有anchor空；行评论所有必需anchor齐。保存的是字节版本的坐标，不是“当前文件第9行”。索引(pr_id,id)；唯一(pr_id,author_id,request_key)。回复只能同PR且只组织一层线程。

### pull_request_merge

merge_id、pr_id、actor_id、request_digest、expected_pr_version、source_head、target_head、merge_base、strategy、fixed_message、fixed_timestamp、candidate_commit、state PREPARING/COMPUTING/SUCCEEDED/CONFLICT/FAILED、error_code、created_at/updated_at。对象引用在意图/最终PR中保留，避免GC与提交竞争。

### pull_request_mutation（短事务变更回执）

mutation_id UUID PK、pr_id、actor_id、request_key、request_digest、action、result_json、created_at。唯一(pr_id,actor_id,request_key)；action和目标commentId（如有）进入摘要。仅用于PR元数据/close/reopen、评论修改/删除/resolve；创建PR、创建评论、merge与sync使用各自已有身份，不重复再写一份回执。

在取得repo/PR门闩并验证当前访问权限后先查回执，同key不同规范化内容409；原结果只回报当次结果，客户端仍可GET当前状态。新变更、回执与业务事件一起提交。没有长时间PENDING，没有REQUIRES_NEW；本次不自动清理这类回执；以后清理时需明确请求键有效期与过期标记，不能删除回执后把很旧的key重新当新操作。H0可复用满足这些条件的既有幂等表，不并存两套。

## 4. 用户关系与统计

user_follow(follower_id,followee_id,created_at)联合PK，反向索引(followee_id,follower_id)。

repository_star(user_id,repo_id,created_at)联合PK，反向索引(repo_id,user_id)。

repository_watch(user_id,repo_id,mode,include_pr,include_comments,include_branch_updates,version,created_at,updated_at)联合PK；mode见14，无行表示PARTICIPATING。

user_social_stats(user_id PK,following_count,followers_count,version)；repo_social_stats(repo_id PK,star_count,version)。计数非负只是最后兜底，不能用GREATEST(count-1,0)掩盖重复扣减。记录关系变更的真实结果再改计数；统计可以根据关系重建。

## 5. 事件与投影

repo_counter(repo_id PK,next_pr_number,event_sequence)。同仓库写门闩内分配，rollback时也回滚计数；不使用MAX+1猜号码。

domain_event_outbox(event_id PK,schema_version,type,scope_key,scope_sequence可空,repo_id可空,actor_id,subject_id,occurred_at,visibility_at_creation,payload_json,payload_hash,status,claim_token,lease_until,attempts,next_attempt_at,error_code,created_at,published_at)。索引(status,next_attempt_at)，repo事件唯一(scope_key,scope_sequence)。无repo事件scopeSequence空，eventId保证身份。

domain_event_receipt(consumer_name,event_id PK组合,payload_hash,processed_at)。其插入和投影处于同一事务。

user_notification(id PK,event_id,recipient_id,channel,repo_id可空,subject_type,subject_id,type,created_at,read_at可空)。唯一(event_id,recipient_id,channel)，索引(recipient_id,read_at,created_at,id)。不持久化不可撤销的私有全文摘要。

activity_entry(id PK,event_id唯一,actor_id,repo_id,subject_type,subject_id,type,visibility_at_creation,occurred_at)。索引(actor_id,occurred_at,id)，读时重新join当前repository可见性。

## 6. API清单与成功语义

所有公共写请求从认证上下文得actor；不存在权限时不回显他人的私有PR信息。URL中的repo/session/pr归属逐一检查。业务冲突409、无权限403或统一隐藏404按现有约定，非法结构400，未认证401，限额429，过大请求413。

| 路径（均在/api下） | 请求要点 | 成功代表 |
|---|---|---|
| POST repos/{r}/pulls | source/target/title/body/draft/requestKey | 已持久创建唯一PR，不代表mergeable |
| GET repos/{r}/pulls | status/cursor/limit | 当前ACL过滤后的列表 |
| GET repos/{r}/pulls/{p} | 无 | PR元数据、当前权威S/T、prVersion |
| GET .../{p}/compare | 可指定固定历史S/T；受仓库范围校验 | O→S与当前比较身份，不产生业务写 |
| GET .../{p}/revisions | cursor/limit | 不可变历史投影，可能落后但不冒充当前 |
| GET .../{p}/comments | cursor/limit、可选固定sourceHead | 当前有权看到的讨论和历史锚点 |
| POST .../{p}/comments | body/requestKey/可选anchor/reply | 评论已保存，通知可以稍后到达 |
| PATCH .../{p}/comments/{c} | body或deleted/expectedVersion/requestKey | 当前有权修改的评论已更新 |
| PATCH .../{p}/comments/{c}/resolved | resolved/expectedVersion/requestKey | 同PR线程根的解决状态，不代表审批 |
| PATCH .../{p} | title/body/draft/expectedVersion/requestKey | 元数据更新，不等于审批 |
| POST .../{p}/close 或 reopen | requestKey/expectedVersion | 状态已确定变更，不删分支/环境 |
| POST .../{p}/merge | mergeId/prVersion/sourceHead/targetHead/strategy/message | 202仅意图已接受；结果查mergeId |
| GET .../{p}/merges/{m} | 无 | 原合并意图的确定状态/结果 |
| POST repos/{r}/agent/sessions/{q}/change-preview | 当前工作线；不传任意目录 | 确定W摘要与变更，BUSY/不可用不能当clean |

## 7. 全局锁顺序与事务边界

以本次低并发模块化单体为前提，**仓库写先锁repository行**；需要Agent资格时接着锁Session→Workline/Binding；之后PR→Branch（按id升序）→Task/Attempt→操作/计数/Outbox。两个路径不允许一边先Session再Repo，另一边先Repo再Session。现有Agent路径如果会最终写repo，需要迁到同顺序；纯日志事件投影只有Session且不再获取repo，不能形成反向边。

Follow先按id升序锁两名user真实行再按同顺序锁user_social_stats，不再获取repo。Star先repo再repo_social_stats。通知/Feed消费先按eventId建立receipt，再只读当前ACL和写自己的投影，不持通知行锁反过来修改PR。

| 事务 | 必须一起提交 | 绝不放进去 |
|---|---|---|
| PR创建 | PR/首revision/编号/Outbox | 完整Diff计算、网络 |
| 评论 | 评论/幂等身份/Outbox | Markdown重渲染/发MQ |
| Branch发布 | CAS/CommitRecord/操作结果/Outbox | 文件上传、模型调用 |
| Merge最终提交 | target CAS/PR结果/merge结果/Workline终态（如有）/Outbox | checkpoint、Sandbox创建 |
| Sync准备 | 固定选择/操作意图/Session gate | 下载归档、建Sandbox |
| Sync激活 | 新Workline/Binding/Session指针/Sync结果 | HTTP等待、清理旧环境 |
| Follow/Star | 关系/计数/必要事件 | Redis与MQ等待 |
| Consumer | receipt/该事件投影/派生Outbox | 提前ACK、外部邮件 |

同一事务内的通用提交方法用REQUIRED参与外层，不用REQUIRES_NEW切断原子性。基于代理的Spring事务要由外部Bean调用或TransactionTemplate明确开启，避免同类this调用导致注解不生效。多步文件/网络Saga不能声称由@Transactional一起回滚。

## 8. 你应能手写出的SQL骨架

```sql
-- 最终提交前：所有相应检查均在同一短事务内
SELECT id FROM repository WHERE id = :repoId FOR UPDATE;
SELECT * FROM pull_request WHERE id = :prId AND repo_id = :repoId FOR UPDATE;
-- 两个分支以稳定id顺序锁定，核对S/T
UPDATE branch SET head_commit = :candidate
WHERE id = :targetId AND repo_id = :repoId AND head_commit = :expectedTarget;
-- 必须=1；否则整个事务回滚，不只返回一条错误字符串
UPDATE pull_request SET status='MERGED',version=version+1,merged_commit=:candidate
WHERE id=:prId AND status='OPEN' AND version=:expectedVersion;
-- 同事务写merge结果和Outbox；每一个影响行数都检查
```

```sql
-- 已经取得本关系使用的统计行锁，关系DELETE决定是否扣减
DELETE FROM user_follow WHERE follower_id=:me AND followee_id=:other;
-- 仅删除影响行数=1时执行两条统计UPDATE
UPDATE user_social_stats SET following_count=following_count-1 WHERE user_id=:me;
UPDATE user_social_stats SET followers_count=followers_count-1 WHERE user_id=:other;
```

这些不包含完整授权/幂等/锁取得步骤，不能孤立复制成成品方法。方法前置条件和失败回滚要在13/14的测试中验证。

## 9. viewToken与cursor怎样落地

`viewToken`只绑定已展示的prId、PR元数据version、O/S/T、算法版本及过期时间。固定用Base64URL JSON加HMAC-SHA256，由平台密钥签发；同一密钥在多Server副本一致，密钥不进前端。不采用另一种无签名兼容路径；使用JDK Mac与MessageDigest.isEqual核验；它防客户端改参数，不替代当前仓库权限检查。

列表cursor绑定viewer、filter、排序和最后一项的(createdAt,id)，可沿相同签名方式生成。分页仍重新检查ACL。过期/筛选不匹配返回明确错误，前端重新取首屏，不在服务层吞异常并从头重复。写入幂等摘要不把这类可刷新的展示token纳入同一业务意图：先验证token，再对其解出的固定业务字段规范化；这样重新签发相同R/S/T不会成为不同merge意图。

检索目标：`javax.crypto.Mac HmacSHA256`、`Base64.getUrlEncoder`、`MessageDigest.isEqual`、`keyset pagination composite cursor`。先用固定键测试往返和改一字节拒绝，再接真实密钥配置。

## 10. HEAD、树摘要与变更版本各自防什么

expectedHead防别人推进分支；prVersion防PR状态/元数据并发修改；oldTreeDigest防用户确认舍弃的草稿已变化；worklineId防同Session的旧任务写到新分支；runnerEpoch防旧实例越权；operationId防同意图重复执行。它们不是重复字段，也不能靠一个UUID全部替代。

## 11. 统一表、字段和请求边界

逐列SQL类型与Java字段映射由[schema/target.sql.reference](schema/target.sql.reference)生成到[sql-field-map](contracts/sql-field-map.md)，不要手工维护另一份不同字段表。Mapper只能填写当前动作允许的列，不能把整行POJO直接UPDATE所有列。所有reference的行类型仅供映射，不代表已实现业务方法。

`user_notification.version`随read状态真实变化递增；read入口是 `{read:boolean, expectedVersion:long}`。`domain_event_failure`固定保存有界原信封和重放状态。`domain_event_outbox.causation_event_id`追溯派生来源；原事件可空。类型、派生序号与队列契约见contracts/business-events.md。

公开Task为 `{message,expectedWorklineId,expectedSessionVersion}` 加Idempotency-Key请求头；它不是私有AgentCommand。Server为Task分配taskId，准备环境完成后才固定attempt/epoch并构造schemaVersion=2的SUBMIT_TASK。旧界面发送任务也要带预期工作线，防两个标签页同步后把旧输入静默送到新基线。pending旧Task有可靠终态后才允许sync；sync gate期间返回明确冲突，不能同时自动派发。

PR merge示例统一为 `{mergeId,prVersion,sourceHead,targetHead,strategy,message}`，strategy固定FF_OR_SQUASH。metadata/comment等短写请求的requestKey进入其回执；浏览器不能随重试重建mergeId、operationId或业务requestKey。公共authorId/workline创建身份、权限列表由Server派生，不能从模型或用户payload授予。

大小限制集中在contracts/limits.json。字符长度、UTF-8字节数与HTTP请求字节上限不同：三者都验，不用一个整数代表全部。私有信封版本2只管理Agent网络契约；业务事件版本独立从1开始，不全局替换任何schemaVersion数字。
