## 2. 使用方法：不懂时先定位缺口

面对一个类，先写两三句：**我收什么输入、拥有什么状态、成功以后外部能观察到什么。** 写不出来时先读对应行为，不先堆方法。能说清行为但不认识API时，按下文搜索目标查官方文档，并在临时目录写最小实验；实验不是生产保证，必须再合进失败/并发验收。

本指南中的“第一项测试”是进入该组件的起点，不是删掉后续可靠性要求。每步所有既定测试通过才能放行。明确地区分“还不会FileChannel”与“文档没有规定初始化顺序”：前者按需学习，后者是需要修正的设计缺口，不能让开发者猜。

## 3. 初始化与日志的施工顺序（本轮设计决定）

### 3.1 两种启动内容，不创建第二套Workspace

- **控制壳**：WorkerConfig、受控目录、`/session/worker.lock`、bootstrap上传/校验组件、HTTP服务。此时没有SessionLog、TaskInbox或AgentEngine；live可成功，ready不可成功。
- **已激活运行内容**：安装后的worktree/state/baseline、本地日志、结果存储、Engine、TaskInbox和Sealer。由WorkerApplication作为一个完整RuntimeServices句柄发布，不让handler读到半装配对象。

`/session/worker.lock`由WorkerApplication持有并最后释放，不能放进RECOVERY包。FileSessionLog接收这把已取得的锁，仅使用自己的ReentrantLock串行append；关闭日志不释放全进程锁。两种锁分别处理进程与线程竞争。

### 3.2 INITIALIZE按这条顺序实现

收到完整AgentCommand后验证session/epoch、commandId和Initialize摘要；BOOTING的幂等回执来自`/session/control/install.json`，不是尚不存在的Session日志。安装目录与control目录分离，不打包control锁和临时包。

先在incoming收完整ZIP并核对SHA；再解包到隔离staging目录，校验scope、各文件hash、路径/类型/数量/字节限额。校验失败不触碰目标目录。对于恢复，不重放旧命令，只装载有证明的树、baseline与历史覆盖。

在没有活跃运行句柄的前提下，写入并耐久保存PREPARED标记，记录固定bootstrapId/hash/session/epoch和本次目标目录。然后安装树、state和baseline，校验目标一致性，最后写INSTALLED标记。**多个目录改名不是一个原子事务**；中间崩溃依赖固定安装意图恢复，不能声称“一次atomic move使全部目录同时成功”。

标记通过后才打开FileSessionLog/ResultStore，创建SessionRuntime/WorkerSession、Context/进程管理、Sealer、Finalizer、Inbox及执行装配入口；每次受理后再创建绑定该Execution的Writer/Control/平台工具与轻量Engine。写WORKER_READY并原子发布完整运行句柄后，ready才返回可执行。

PREPARED阶段重启：持外部进程锁，核对还是同一bootstrap意图；从同一已校验输入继续或重做尚未激活的安装，不能接受另一个包覆盖。INSTALLED阶段重启：核对标记，不再次从原bootstrap覆盖可能已经修改的工作树；打开当前状态并执行WorkerRecovery。不同epoch/恢复包进入新的空状态根或新卷，旧实例先确认停止。READY响应丢失时，重发相同INITIALIZE返回原结果，不重装。

### 3.3 建议先写的实验与测试

先做“空目录安装两个文件后读取”，再做“同一包初始化两次”，然后在PREPARED、安装一半、INSTALLED、READY前后插入故障。断言同一个输入可恢复、不同输入被拒绝、已运行文件不会重置、进程锁文件不被替换。最后才与真实日志和HTTP结合。

检索目标：`FileChannel.tryLock`、`Files.move ATOMIC_MOVE AtomicMoveNotSupportedException`、`FileChannel.force`、`crash consistent install marker`。force的保证依赖本地存储/设备，不能从本地落盘推出宿主永久丢失也不丢数据；跨宿主保存仍靠平台RECOVERY归档。
