# 11｜总体架构、功能范围与复用边界

## 1. 先固定三个不同的对象

**Session** 是会话身份和访问控制边界，保存连续对话的归属，不因PR合并、浏览器关闭、容器销毁自动结束。

**Workline（代码工作线）** 是一次基线和受管源分支的绑定。包含baseCommit、当前确认publishedHead、sourceBranch及可选PR。PR合并会结束该代码线的发布资格，但不结束Session。

**Binding** 是某个workline当前的物理执行实例：sandboxId、runnerEpoch、ready状态等。恢复同一工作线可以换Binding；显式切换基线通常产生新workline。两者都不能冒充用户新的聊天线程。

因此关系是 Session 1:N Workline；每条工作线有历史Binding，但最多一个活动写实例。Task/Attempt固定workline和epoch，不能因Session当前指针变化而把旧结果算到新工作线。

## 2. 模块和依赖

继续使用一个Spring Boot后端，不添加微服务、分布式事务框架或独立社交服务。按当前工程风格在 `src/main/java/com/gitnova/{service,mapper,entity,controller}` 下分业务包，不为整齐迁走无关旧代码。

```text
网页 ─────────────────────────┐
Agent的受控平台能力 ────────────┤
                              ▼
                        应用层编排
             ┌────────────────┼────────────────┐
             ▼                ▼                ▼
       pullrequest         social          agent/control
             │                │                │
             └────────── repository/access ─────┘
                              │
                  对象验证 + Branch CAS
                              │
                   数据库事务内业务事件
                              ▼
                    Outbox → RabbitMQ
                          /
                    notification    activity
```

PR业务对象不得引用AgentEngine、WorkerEndpoint或Sealer。Agent来源的发布限制由应用层识别受管分支后调用Agent协调逻辑；普通PR不会调用Sandbox。所有merge入口均经统一应用编排，不能另留一条绕过受管分支检查的Controller。

Core继续只依赖任务、日志、工具和模型连接。`report_progress/create_pull_request`调用通用仓库/PR服务；新增Follow、Watch和通知不应修改Core。业务事件与Agent执行日志是两套不同的协议，不能混用。

## 3. 源码事实与本次要补的能力

沿用此前读取的GitNova历史基线为 `316112ae38747a5f5ceef95aa6e6b095fa76c919`。可见远端分支列表中没有当前本地 `harness-in-sandbox` 新分支，**不能据此认定你本地没有实现，只能认定本轮无法验证进度**。

| 能力 | 可见源码事实 | 实施时怎么处理 |
|---|---|---|
| Branch CAS | BranchMapper已有findHead/compareAndSetHead，返回影响行数 | 复用，不重新造分支数据库；补统一写入口和受管分支约束 |
| 对象模型 | CommitObject只有一个可选parent，mapping是path→blob | 保持单父；支持FF和三方squash，不伪造双父Merge Commit |
| Push | TransferService先验证对象/祖先，再推进HEAD、写索引、发布PostReceiveEvent | 提取共享仓库事务；不可把ApplicationEventPublisher当成耐久MQ |
| 仓库授权 | RepositoryAccessService写操作查MySQL，私有读取可以用角色缓存 | 新敏感读取补权威读取路径和批量ACL，不把最多5分钟旧成员缓存当即时撤权保证 |
| 缓存/限流 | 历史已有Redis接入 | 保留已有逻辑；新增功能先数据库正确，再加可重建缓存 |
| Outbox/MQ | 此前已读Agent专用OutboxPublisher，其DispatchPayload绑定runId/reason；没有审计全部调用者 | 首先检索实际表/Publisher/Consumer；达到15的契约才复用，不凭名称认定可直接搬用 |
| 新Agent、PR、社交功能 | 最新本地未提交代码不可见 | H0逐项记录已有/新增/测试；不能把参考类当已实现 |

源码定位和链接见17的GN系列。旧对象读取可能仍在事务中，本次需要明确区分“事务外昂贵校验”和“事务内最终CAS”；本次关闭在线对象GC。只在停写、列出所有分支/PR历史/进行中操作/恢复归档引用后做人工离线清理；不在准备与提交之间删除候选对象。

## 4. 一次完整交付的功能清单

**PR闭环**：同仓库分支创建，Draft/Ready，列表/详情，源版本历史，文件Diff，普通讨论与固定版本行评论，关闭/重开，FF或三方squash合并，固定HEAD并发检查，源分支删除后的历史可读。

**Session衔接**：合并后Session保留；沙箱原树不被改动；显式同步固定目标H；默认脏树拒绝同步；用户可明确选择移植草稿或在备份后舍弃；同步失败旧数据可恢复，完成后同Session进入新workline。

**用户侧**：主页和当前有权查看的仓库；Follow/Unfollow及列表；Star/Unstar及收藏列表；Watch的参与/全部/自定义/忽略设置；站内通知已读状态；关注对象的公开动态。

**支撑能力**：权限、幂等、分页、业务事件Outbox、MQ重复消费、缓存失效、源码与故障测试。

不在本次承诺：跨仓库Fork、完整Issue系统、组织审批/Code Owners/CI门禁、邮件/Webhook供应商、聊天系统、无限级评论、全文/向量检索、多Agent、模型训练、Git协议兼容或任意多租户安全认证。不是以后补当前基础功能，而是明确产品范围。

## 5. 几个容易“抽象过头”的地方

PR不继承Issue；Follow/Star/Watch不挤进通用relation表；运行态事件不承担业务通知；不为每张表创建interface+impl两套Service；不为本次同步添加通用工作流引擎。

复用三方树合并器做两件事：PR计算merge(O,T,S)，草稿迁移计算merge(B,H,W)。两者输入语义不同，必须在调用处显式命名。PR服务不拥有本地目录，SyncService不改变远端目标HEAD。

`PullRequestRevision`与PR行上的`version`不是一回事：前者是确定源代码版本的记录，后者是标题、状态等更新用的乐观版本。事件消费者延迟不能让PR详情或merge使用过时HEAD。详细方案在13。

## 6. 一致性取舍

本次在低并发仓库写场景采用**短事务内每仓库写门闩**，固定使用已有repository行的SELECT FOR UPDATE作为门闩；不新建repo_write_guard表。H0只核对物理表/主键名称，不再次选择锁模型。普通Push、Agent发布、PR创建/merge、分支删除和仓库授权变更都遵循同一顺序。文件/网络操作绝不在锁内。

这比引入复杂分布式锁简单，但同仓库写入会串行；要记录事务耗时，不能宣称高吞吐无代价。跨仓库仍可并行。以后确有指标证明瓶颈再细分锁，不先为假想流量优化。

授权变更同仓库门闩参加提交校验，保证撤权与敏感写入形成明确先后关系。列表中的私有信息由MySQL当前ACL过滤；不在SQL分页后删掉无权限项却仍暴露原total。

## 7. 开发前第一项实验

创建两个普通分支A与B，完全不启动Agent。先实现“读两棵确定树→按路径和blob比较→返回Diff摘要”。再引入PR行和merge事务。这样你先证明托管基座可支撑协作，不从十张空表开始猜产品。

检索：GitNova `TransferService.updateHead`、`BranchMapper.compareAndSetHead`、`CommitObject.mapping`；OneDev `open/checkUpdate`；Gitea `recordMergeIntent`。不会的JGit/MySQL细节只查17给出的官方入口。
