# 接口、状态、数据库和字节契约

本文件补齐原三份文档未落实到代码的部分。不是另一套架构：仍为 HTTP 命令、SSE 事件、常驻 Worker、任务级封存确认。这里新增的具体字段、SQL 和包位置是设计决定；不声称它们已经存在于 GitNova。

## 1. 代码签名与 JSON 规则

`reference/agent-protocol/src/main/java` 包含完整字段与枚举；`reference/agent-core` 包含跨职责接口。目标目录见04。HTTP层使用 Jackson `readTree` 读取信封，按 `type` 显式选择 `AgentCommand.Initialize/Submit/Steer/...` 记录类型；不得打开 default typing，也不根据请求传来的 Java 类名反序列化。`schemaVersion=1` 是线协议识别，不是产品分期。

新增纯辅助类 `com.gitnova.agent.protocol.json.ProtocolJson`：统一 ObjectMapper（JavaTimeModule，UTC，拒绝未知字段及尾随JSON）和 `canonicalBytes(Object)`。规范化递归按对象字段名排序，数组保留顺序，数字按字段定义解码后输出，UTF-8，不做Unicode规范化或trim用户message。哈希为SHA256。Task幂等摘要使用repoId、actorId、sessionId、原文及明确用户参数；deadline、attemptId等由第一次受理生成，不在重发时重新计算。

参数限制统一从配置注入：请求body默认1MiB、message默认128KiB、commandId/taskId/attemptId为规范UUID、sessionId为创建时的UUID；branch长度遵循原BranchName。`eventId=sessionId:epoch:sequence`，scope校验不能只靠长度。对真实源码内容和事件payload设独立配额，不用request body上限限制全部归档。

### 1.1 信封字段的空值规则

| 命令 | taskId/attemptId | payload类型 | 额外条件 |
|---|---|---|---|
| INITIALIZE | null/null | Initialize | BOOTING；bootstrapId与SHA256匹配 |
| SUBMIT_TASK | 两者必填 | Submit | expectedPublishedHead/configDigest与本地一致；deadline未到 |
| STEER_TASK | 两者必填 | Steer | 目标是当前attempt且输入仍开放 |
| CANCEL_TASK | 两者必填 | Cancel | 已结束返回原结果；未知attempt返回明确404 |
| PREVIEW_CHANGES | 可空；有task必须匹配当前attempt | Preview | 不改变发布HEAD；工具安全边界执行 |
| SEAL_SESSION | 空闲场景null/null | Seal | 活跃任务返回BUSY，不隐式取消 |
| ACK_PUBLICATION | Task结算两者必填，空闲封存两者null | Ack | exportId必须是当前待结算包 |
| CLOSE_SESSION | null/null | Close | 无活跃/未结算任务，归档确认后才退出 |

原文提到“实时预览”却没有协议入口，本次补上PREVIEW_CHANGES及GET `/previews/{commandId}`，不更改已有编码/发布流程。预览有捕获时刻和基准HEAD，是可过时的UI数据，不作为发布快照。

### 1.2 工具参数的最终形状

| 工具 | 参数 | 返回关键字段 |
|---|---|---|
| shell | action=RUN/START/POLL/STOP；RUN/START用script/cwd/timeoutSeconds，POLL/STOP用processId/cursor | processId、running、exitCode(nullable)、stdout/stderr预览、对象引用、truncation、停止确认 |
| read_file | path、startLine、endLine | lines[{number,text}]、hasMore、nextStartLine、fileSha256 |
| edit_file | mode=CREATE/REPLACE/DELETE，path；create内容，replace原文+新文/expectedSha，delete expectedSha | changed、beforeSha256、afterSha256、bytes |
| history_read | resultId、view=stdout/stderr/result、startLine/endLine | 原始来源、片段、captureTruncated、continue参数 |
| history_search | query、caseSensitive、cursor可空、limit | 原始来源命中、范围是否完成、nextCursor |

`LocalEditTool`负责文本精确编辑，二进制修改可以在shell中进行；最终发布按真实字节。工具参数没有平台WorkspaceId、FencingToken、全局generation。取消命令不是模型工具。

## 2. 事件 payload 单一字典

所有原始事件存入本地log和平台私有归档；浏览器只接白名单映射。Map用于异构payload容器，但下面字段按EventType校验，不接受任意结构。

| EventType | payload必需字段 | 谁产生/谁消费 |
|---|---|---|
| COMMAND_ACCEPTED | command完整信封、requestDigest | TaskInbox→receipt重建/平台命令投影 |
| WORKER_READY | publishedHead、runtimeConfigDigest、restoredFromArchive可空 | 初始化→平台就绪 |
| USER_MESSAGE_RECEIVED | message、sourceCommandId | Engine/Inbox之一，严格仅一次→Context |
| TASK_STARTED | configDigest、expectedPublishedHead、deadlineAt | Engine→Attempt状态 |
| MODEL_CALL_STARTED | modelCallId、requestDigest、inputEstimate、purpose=MAIN/SUMMARY | Engine→审计 |
| MODEL_RESPONSE | modelCallId、finishReason、text、reasoningContent(私有)、toolCalls、usage | Gateway后→Context与回答校验 |
| TOOL_STARTED | modelCallId、toolCallId、toolName、arguments、processId可空 | Engine→故障判断 |
| TOOL_RESULT | modelCallId、toolCallId、toolName、status、result、objects、historyReadback | Engine→HistoryIndex/Context |
| CONTEXT_SUMMARY_CREATED | summaryText、coveredThrough{epoch,sequence}、retainedGroups、configDigest | Context→后续请求 |
| HARNESS_FEEDBACK | kind、message、sourceScope | Engine→纠偏与恢复说明 |
| STEER_APPLIED | commandId、acceptedEventId、appliedBeforeModelCallId | Engine→确认指示已应用 |
| ANSWER_DELIVERED | responseEventId、modelCallId | Engine→平台回答指针 |
| TASK_FINISHED | status、reason、answerEventId可空 | Worker收尾→Task execution投影 |
| SNAPSHOT_SEALED | exportId、bundleSha256、bundleBytes、treeDigest、throughSequence、purpose | Sealer→ArchiveService |
| TURN_SETTLED | exportId、archiveId、outcome、publishedHead | ACK执行后→清活跃槽 |
| PREVIEW_READY | commandId、expectedPublishedHead、capturedSequence、changedFiles、truncated | safe boundary→UI预览 |
| RECOVERY_INTERRUPTED | oldAttemptId、restoredArchiveId、coveredThrough、unpublishedChanges、reason | Recovery→新状态与用户提示 |
| WORKER_STOPPING | reason、confirmedArchiveId | Worker→生命周期 |

`TOOL_RESULT`先引用已经保存的对象再append；append得到eventId后，模型可见resultId就是该eventId。临时输出文件名称可以是UUID或内容hash，不需要预占未来事件序号。历史读取产生的TOOL_RESULT仍记录，但`historyReadback=true`使其不进入原始历史召回集合。

TASK_FINISHED不清Session活跃槽；TURN_SETTLED才清。旧文档里的STEER_ACCEPTED在具体协议中由COMMAND_ACCEPTED(type=STEER_TASK)表达，避免两个不同的受理事实发生半提交。

### 2.1 回答关联与公开投影

链为TASK_FINISHED.answerEventId→ANSWER_DELIVERED.responseEventId→MODEL_RESPONSE.text。校验同session/task/attempt、STOP、非空正文、toolCalls空；MODEL_RESPONSE在被引用前已归档。Answer原文不经过第二次总结。无工具的中间STOP若被已受理steer否决，就不产生ANSWER_DELIVERED。

公共SSE只输出：状态、工具名/经过清洗的预览、已交付answer、发布/资源问题。**不直接把包含reasoningContent、模型认证头、完整provider响应的私有事件流转发给浏览器。** 原始私有档案可以受权限保护调试访问。

### 2.2 SSE游标

Worker内：(epoch,sequence)；平台页面：archiveOffset。Worker用UTF-8、`id:`、`event: agent`、单行JSON `data:`、空行帧结束。Server解析SSE时先增量解码再分行，多个data用换行拼接；不假设一次read等于一条JSON。心跳只写`: keepalive\n\n`，无业务序号。

平台归档先锁Session行，再锁该epoch Binding，检查expectedSequence。插入event+更新投影+连续cursor同事务。`archive_offset`虽是AUTO_INCREMENT，也只在持有同Session串行锁时分配；否则事务先分配后提交乱序会使页面跳过迟提交事件。跨Session不是一条公开流，不要求全局offset连续。

## 3. Worker状态表：只用这一份

| 状态 | 可受理操作 | 状态变化/拒绝规则 |
|---|---|---|
| BOOTING | live、INITIALIZE、内部身份检查 | INITIALIZE→INITIALIZING；SUBMIT=503 |
| INITIALIZING | 同初始化请求重查、live | 成功→IDLE；失败→BLOCKED；禁止覆盖活动树 |
| IDLE | SUBMIT、PREVIEW、SEAL、CLOSE | SUBMIT→RUNNING；seal→FINALIZING；close→STOPPING |
| RUNNING | STEER、CANCEL、PREVIEW排到边界、查询 | cancel→CANCELLING；Engine终态→FINALIZING；新Task=409 |
| CANCELLING | 重复cancel、查询 | 确认模型等待与子进程停止→FINALIZING；不明→BLOCKED |
| FINALIZING | 查询、已受理命令重查 | 无新写者；完成固定export→WAITING_SETTLEMENT |
| WAITING_SETTLEMENT | ACK_PUBLICATION、查询 | 正确ACK→IDLE；发布失败仍等待，用户skip后亦需成功ACK |
| BLOCKED | 查询、明确恢复/管理员处理 | 禁止执行及seal；不自动重放shell |
| STOPPING | 查询/live | 关闭→STOPPED；不接新任务 |
| STOPPED | 无应用请求 | 平台通过Sandbox状态确认结束 |

每个状态迁移要么由一条耐久事件决定，要么属于可重建的短暂处理中状态。WorkerSession不再复制每个文件的状态，只保留当前Task/attempt、输入开放性、待结算export与HEAD。

### 3.1 STEER与STOP的线性化位置

锁序：TaskInbox受理锁→ExecutionControl锁→SessionLog追加锁；Engine只取ExecutionControl→SessionLog，**不能在持有Control锁时回调取得Inbox锁**。在同一Control锁下：STEER先耐久受理再入队；STOP检查队列为空、未取消后才保存ANSWER_DELIVERED并关闭输入。谁先获得锁，谁先成立。落日志失败不能假装受理或完成。

HTTP取消请求必须能响应长模型调用。取消回调在锁外运行，注册时检查此前是否已取消。不得让取消请求排在单线程Agent执行器后面。默认执行器：一个单Task线程；独立控制HTTP执行器；独立输出消费；有界SSE连接。WorkerAssembly拥有它们并逆序关闭。

## 4. 平台状态不是第二套逐步Agent引擎

Task分三个轴：execution status、settlement status、publication status（完整枚举见reference）。例如COMPLETED+WAITING_ACK+PUBLISHED表示回答和仓库发布都已完成，但Worker尚未确认可以继续；COMPLETED+BLOCKED+FAILED表示回答仍可读但发布失败。

Session.activeTaskId在平台受理事务设置，TURN_SETTLED才清；在Worker明确拒绝未开始任务时也可清。FAILED/CANCELLED需要先归档脏工作树并ACK(NOT_REQUIRED)后才放行。若Worker已经确认停止且环境不可恢复，可经显式中断流程清槽，同时Session置BLOCKED，不能直接接新任务假装现场完整。

## 5. 数据库：完整DDL与映射

使用 [schema/agent_control.sql](schema/agent_control.sql)。它不是“只列建议字段”：包含10张新控制/归档/PR表和旧Session的增量字段、唯一约束、外键、状态约束。**没有运行真实MySQL验收**，实际执行在02步骤 10；应用前使用库副本并保留备份。

旧agent_task/agent_run的CHECK仅允许旧ACTIVE/WAITING_USER等组合，不能往其中硬写PENDING_DISPATCH。新执行写agent_control_task/attempt；旧表保留只读。这是迁移兼容，不是长期运行两套执行器。

按步骤执行：先 `python3 scripts/install_migration.py <repo>` 看目标编号，再审查本地新增迁移/同名列；通过后加`--write`复制为最新V编号；Flyway验证并执行。脚本只负责创建一个新迁移文件，不修改库，也不证明它可与未知本地DDL合并。若同名列已存在，必须在副本上核对定义后合并，而不是执行DROP重建。

| 表 | 角色 | 对应Mapper |
|---|---|---|
| agent_session（增量） | 业务身份、固定A、工作分支、活跃槽、当前epoch | SessionControlMapper |
| agent_sandbox_binding | 每epoch实例身份/创建操作/续期/接收游标 | SessionControlMapper |
| agent_control_task | 用户任务、当前attempt、回答及结算投影 | TaskControlMapper |
| agent_control_attempt | 一次执行尝试，历史attempt不覆盖 | TaskControlMapper |
| agent_control_command | 已保存但可能尚未送达的任务级控制意图 | TaskControlMapper |
| agent_event_archive | Worker不可变事实与公共游标基础 | EventArchiveMapper |
| agent_snapshot_archive | 已耐久保存的bundle及后续结算附记 | DeliveryMapper |
| agent_publication | 固定一次发布的父HEAD/time/message/结果 | DeliveryMapper |
| pull_request / comment / merge | PR生命周期、讨论、幂等合并 | PullRequestMapper |

控制命令表确实承担耐久发送意图，不能宣称“无MQ就无消息可靠性状态”；不同的是它不调度平台内AgentLoop，不存每次文件变动，不要求每tool数据库事务。

ControlRows中每个静态POJO与表一一对应：字段名按下划线转驼峰，主键字符串不用Long；`archive_offset`映射Long，JSON/LONGTEXT映射String，MyBatis不擅自重排canonical正文；DATETIME(6)统一UTC。加 `mybatis-plus.configuration.map-underscore-to-camel-case=true` 并显式测试generated field不被insert。

### 5.1 全局数据库锁顺序

所有可能触及同一对象的事务按：**Session（多个按id排序）→Binding→Task→Attempt→Publication/MergeRequest→PR→Branch（repoId,name排序）→归档游标更新**。

单独PR merge若关联Agent Session，必须先查id后锁Session，再锁PR，不能先PR再Session。普通Push没有Session时只锁Branch；受管branch普通Push在进入Branch写之前拒绝。外部网络、zip、模型、Git对象大文件IO都在DB事务外。Deadlock即使顺序一致仍可能由其他索引产生，事务可有限重试相同已固定意图，不重做模型。

### 5.2 SQL事务施工单

每个编号对应一个Service的@Transactional方法。一个公共方法调私有同类@Transactional不会自动开启新事务；应使用独立事务Bean或TransactionTemplate。

**TX-S1 创建会话意图（SessionLifecycleService）**

鉴权后生成UUID/固定branch selector；先按creation key查询已存在行并比较creation_request_digest。不存在时读取一次A，再INSERT Session(PROVISIONING,SANDBOX_AGENT,A,agent/<UUID>)及Binding(epoch=1,CREATING,createOperationId,salt,config)。冲突读取赢家，scope/message不同409。事务后调用OpenSandbox。幂等键兼容旧库全局唯一，必须包括身份scope检查，不把撞key的别人的Session返回。

**TX-S2 激活**

SELECT Session FOR UPDATE→Binding FOR UPDATE；检查相同createOperationId/currentEpoch/BOOTING且worker ready scope正确；Branch不存在时插指向A；存在则检查属于同Session且仍A，不能仅因SHA相同抢占别人分支；UPDATE Session ACTIVE/version+1。DB失败不重取main。环境资源已存在但未激活，由reconciler核对继续。

**TX-T1 受理Task（TaskApplicationService）**

SELECT Session FOR UPDATE；先SELECT task WHERE(session,key)，命中比较原请求digest直接返回，不再检查空槽造成重试409。未命中才检查ACTIVE、workflow OPEN、activeTaskId为空；INSERT Task(PENDING_DISPATCH,currentAttempt=NULL)；INSERT Attempt(id,deadline,epoch,head,config)；UPDATE task.currentAttempt；INSERT command确定JSON；UPDATE Session.activeTaskId。全部提交后返回202并安排发送。

**TX-T2 发送确认**

Dispatcher读同commandId信封。对网络错误/5xx标UNKNOWN并退避，不换deadline/message/attempt。对200/202保存receipt。拒绝400/403或确定identity conflict可REJECTED；503/BUSY按实际理由重查状态，不能把另一个活跃任务清掉。更新Task仅在currentAttempt仍匹配且尚未开始时发生，迟到受理响应不能把COMPLETED回滚到ACCEPTED。

**TX-T3 取消先于SUBMIT的竞态**

公共cancel先锁Session/Task置cancel_requested，再保存确定CANCEL意图。SUBMIT是否已经受理未知时，不能只收到Worker404就清槽。Dispatcher查询原SUBMIT receipt：已受理则重发取消；可证明从未发送且受控取消了待发记录则Task CANCELLED、结算NOT_REQUIRED并清槽；网络不明保持待核对，不另起Worker。Worker CANCEL未知attempt返回404（不会预留无限cancel tombstone），平台负责这个先后关系。

**TX-E1 归档与投影（EventProjector）**

锁Session→Binding；若event已存在，核对digest并返回；若seq≠last+1，抛GAP触发重连。INSERT archive；检查类型必要字段并按当前attempt/epoch条件更新task。ANSWER_DELIVERED查询responseEventId，做scope与STOP校验。TASK_FINISHED更新execution/terminal/finishedAt但不清槽。TURN_SETTLED检查archive/publication的权威结算结果匹配后更新settlement=SETTLED并清Session槽。最后update last_archived_sequence；同事务回滚任何不合法事件。

**TX-A1 保存归档**

网络下载与校验后先将zip写平台归档存储并fsync/原子发布；再INSERT snapshot_archive，UNIQUE(session,export)冲突核对bundle hash；更新Session.latestArchive。跨对象存储/DB失败允许孤儿对象，不允许DB声称文件存在但还没保存。不要将执行中的worktree以临时服务器路径当永久归档key。

**TX-P1 固定发布**

锁Session→Task→Publication（已存在读取）；首次根据已验证manifest与HEAD创建Publication，固定commit_epoch_millis、作者、message、父HEAD。唯一session+export保证相同成果重试不变；外部对象构建用这条记录，不再调用模型起message。失败记录不删除。

**TX-P2 原子可见与ACK**

对象完整后，锁Session→Task→Publication→Branch。检查session工作分支归属、未merge/close、当前权限、Publication.expectedHead；相同result已经PUBLISHED直接读原结果。分支CAS一次，写CommitRecord/缓存、Publication结果与Session.lastPublishedHead。更新snapshot_archive结算附记、插同身份ACK command；同事务提交。ACK网络发送在事务外，丢失由Dispatcher重发。NO_CHANGES保留HEAD但也保存归档与ACK；FAILED/CONFLICT不得假成功ACK。

**TX-P3 明确skip**

只允许已经STORED的恢复包且该Publication未成功；锁Session/Task/Publication重新读状态，若已发布返回现状，不能改成skip。记录SKIPPED、旧HEAD和ACK，未发布工作文件保留。下个Task前向模型明确dirty变化仍在。失败/cancel同理NOT_REQUIRED，不自动提交坏代码。

**TX-R1 创建/评论/状态**

PR创建以(repo,source,target,status=OPEN)唯一；已有open返回同对象或409。draft可以无差异；no diff不可merge。评论单独idempotency且作者从认证取得。修改draft/close/reopen带expectedRevision；SQL `UPDATE ... WHERE id=? AND revision=? AND status=?` 影响1才成功；merged不能reopen。

**TX-R2 merge**

先固定请求revision/sourceHead/targetHead与idempotency，创建merge意图；在事务外读取对象算三方候选并固定timestamp/message。提交事务按全局锁序，确认关联Session没有activeTask、已结算、workflow OPEN；确认PR OPEN且非draft；两HEAD/revision没变。FAST_FORWARD复用source；SQUASH新单父commit parent=原target。目标branch CAS、CommitRecord、PR MERGED、merge COMMITTED、Agent Session workflow MERGED同事务。若target是另一个活跃受管branch则拒绝；防Agent Session仍在写时merge后产生无人管理提交。

## 6. ZIP、Manifest和baseline的具体规则

为当前工作树建立轻量`baseline`目录/manifest，只在初始化或发布成功ACK时更新，用于本地预览和tracked判定；不是逐tool同步。SKIPPED不更新baseline。PUBLISHED在ACK时从同一个seal中取树更新baseline，然后记录TURN_SETTLED；替换失败保持WAITING_SETTLEMENT，重发ACK可继续幂等完成。

包内固定三个顶级前缀：tree/（候选发布源码）、state/（Agent日志/结果/摘要）、baseline/（上次发布的只读比较基准）。manifest.json位于根，不能把exports放入自身；日志截止N使用明确字节offset，不能zip活动文件尾部。

`treeDigest = SHA256(concat(entries))`：TREE条目按规范相对路径UTF-8字节词典序；每条写 `uint32_be(pathBytes.length) + pathBytes + int64_be(size) + raw32ByteFileSha256`。stateDigest同样计算STATE+BASELINE条目并包含kind前缀，避免同路径跨集合冲突。manifest自身不进入自己的hash。case敏感与Unicode原文保留，禁止NUL、绝对路径、..、反斜杠歧义路径、重复规范化路径。

只支持普通文件/目录；符号链接、硬链接、设备文件不静默解压成真实源码。用Commons Compress读取central external attributes，流式计实际解压量，zip声明size不是信任边界。导入先到隔离临时目录，全部hash与scope验证通过后原子切换；不直接解压覆盖活动树。恢复时可执行位来自manifest并限制为普通user执行权限，不能设置setuid等。

tracked集合以最近已发布baseline为准；即使一个tracked文件符合node_modules等排除，也不能默删。新增依赖/构建产物默认排除；用户显式要求提交这类文件时给明确拒绝/受控选择，不悄悄遗漏。Task失败/cancel也封存脏树，但publication=NOT_REQUIRED。

### 6.1 封存包不包含ACK，恢复怎么接上？

snapshot row保存 `settled_published_head/settled_outcome/settlement_command_id`，它们是平台发布事务写的，不让Worker自述。恢复包N之后的发布成功已经发生时：平台给新INITIALIZE的bootstrap附加 `settlement.json`（含旧export/archive及确定HEAD/结论）；Worker验证它属于该恢复包，将baseline切到对应sealed tree（PUBLISHED）或保留旧baseline（SKIPPED），重建IDLE；记录新的恢复事件。不能从包内旧expectedHead覆盖平台已经成功的B。

首次卷重启未丢数据时读本地完整TURN_SETTLED优先；从旧归档恢复使用平台附记，且新epoch+清楚的恢复覆盖。同Task旧的模型未来轨迹可历史查询，不注入“当前已经完成”上下文。

## 7. PR公共接口（精确路径）

根路径 `/api/repos/{repoId}/pulls`：POST创建；GET列表。子路径 `/{prId}` GET详情；`/{prId}/diff` GET固定heads差异；`/{prId}/comments` GET/POST讨论；`/{prId}/draft` PATCH切draft；`/{prId}/close` POST、`/{prId}/reopen` POST、`/{prId}/merge` POST。写请求使用现有登录态，create/comment/merge带Idempotency-Key；状态修改带expectedRevision。

merge body：`{expectedRevision, sourceHead, targetHead, method:"AUTO"}`，AUTO在固定snapshot上选择FAST_FORWARD或SQUASH并保存意图，不在重试时换head。返回`{prId,status,mergeMethod,mergedCommit,sourceHead,targetHead}`；409返回稳定code与conflictingFiles/currentHeads，让用户刷新，而不是自动把新内容并进去。

Agent Task补充入口：`POST /api/repos/{repoId}/agent/sessions/{sessionId}/tasks/{taskId}/retry`（仅明确中断后新attempt）、`POST .../sessions/{sessionId}/preview`（PREVIEW_CHANGES）、`GET .../sessions/{sessionId}/previews/{commandId}`。其余公共接口保持01；“随时查看PR”看的是已发布diff，当前预览标注捕获时刻。

## 8. 完成SQL与协议后如何验收

先运行离线contract编译与JSON fixture校验；然后在MySQL副本执行新migration，验证旧历史不变、唯一约束、UPDATE影响行数及回滚；至少用两个真实数据库连接测TX-T1和TX-R2并发。不能用单线程Mock Mapper证明锁和外键正确。

这里已经决定表、字段、职责和事务顺序；尚未把“这些DDL在你的最新库上执行成功”当作事实。没有Docker/MySQL服务的文档生成环境无法提供该证据，02给出本机验收步骤，07明确记录这个区别。

## 11. 施工闭合补充：原有功能不因迁移消失

`Submit.mode`为CODING/REVIEW/QA；平台公共普通Task固定CODING，旧CodeReviewListener适配入口固定REVIEW，已实现的仓库QA固定QA。mode写入agent_control_task.task_mode、命令摘要与TaskInput，不由用户绕过授权指定。CODING才执行自动发布。QA/REVIEW默认只注册read_file/history工具；不能仅靠prompt声称只读而仍暴露任意shell。

ReviewReportTool仅在REVIEW模式出现，用结构化findings写报告对象，不是finish工具；回答仍为自然STOP。Server核对报告的repo/base/target与授权范围、路径和行号后写review_comment。旧ReviewVerifier的校验可迁到LegacyCapabilityAdapter。旧QA/suggest若只是stub，清单标STUB，不宣称新增了它；已使用的能力未接通则禁止删除原调用链。

临时Review/QA Session可直接调用同一环境准备方法，但publication=NOT_REQUIRED。普通Coding Session仍按原约定创建工作分支；不要为只读Review额外制造代码提交。旧接口返回约定由适配器维持，真实字段按步骤 0盘点，不强行把异步Task DTO塞进原同步返回。同步兼容调用设置总deadline并查询新Task，超时明确返回任务身份，不永久占线程。

## 13. 仓库发布与归档的补充裁决

SessionSealer封存的baseline是最近一次已发布的完整树（不是只有hash）。本次Task修改后源tracked集合=baseline中的所有路径；新增文件ignore生效，已有tracked文件不因ignore被排除。成功ACK后用对应export中的tree原子替换baseline；NO_CHANGES保持等价baseline；SKIPPED/NOT_REQUIRED保持之前baseline并标dirty。以后即使新增文件进入ignore也不能静默从已发布树消失。

恢复归档N时，Server必须附带该archive的已确认settlement。PUBLISHED用包tree和settledHead更新baseline；SKIPPED保持包baseline。归档N之后的未封存历史只作为可查询证据，不直接重放到当前进度。ACK已处理但TURN_SETTLED未收到时，平台重连或发送同ACK，不创造新publication。

ControlTypes含运行期token以便创建API使用，但不得写canonical命令正文、archive manifest或普通日志。持久库只保存tokenSalt与可撤销身份；通过服务端HMAC主密钥+session/epoch/用途派生令牌，模型令牌与控制令牌用途分离。主密钥轮换后按绑定重新签发/重建，不能默默把旧密钥保存在Worker源码。

## 14. 初始化与HTTP读取不能向后依赖封存实现

步骤 6先创建WorkerResources接口，HTTP类只调用receiveBootstrap/initialize/export/previewJson；步骤 8由LocalWorkerResources使用BundleCodec/ExportStore实现。这样可以先独立测试HTTP受理，而不将一个空的生产ExportStore写出来冒充完成。TaskFinalizer同样是先声明、后注入生产实现。两个接口的完整签名在reference。

SQL方法和对应锁/更新条件见[Mapper施工表](contracts/mapper-contracts.md)，SQL字段见[逐列字典](contracts/sql-field-map.md)。这两份不是额外的产品阶段，而是05的文件级展开。

## 15. 字节格式最终补充

所有digest条目排序以UTF-8无符号字节词典序为准，不使用受语言/locale影响的默认排序。TREE用于托管源码内容摘要，写pathLength:uint32_be、pathBytes、size:uint64_be、sha256:32bytes。STATE和BASELINE共同进入stateDigest，额外在每条前面写kind字节（STATE=1、BASELINE=2），最后写executable字节（0或1）。长度/size必须在限额内，不允许负值。manifest最终由确定性JSON编码；ZIP外层sha绑定manifest全部字段，所以不允许替换permission或scope。

现有GNOV只记录path→blob，不具备原生Git可执行位/符号链接模式。封存/恢复可以保存普通可执行权限元数据，但发布不能宣称GNOV因chmod单独生成了原生Git模式变化。首次bootstrap没有模式证据时使用普通文件权限；执行无可执行位脚本用`bash ./mvnw`等明确解释器，不能因为Linux目录存在就假定拥有完整Git工作副本。
