# 接口、状态、数据库和字节契约

本文件补齐原三份文档未落实到代码的部分。不是另一套架构：仍为 HTTP 命令、SSE 事件、常驻 Worker、显式平台能力与独立恢复归档。这里新增的具体字段、SQL 和包位置是设计决定；不声称它们已经存在于 GitNova。

## 1. 代码签名与 JSON 规则

`reference/agent-protocol/src/main/java` 包含完整字段与枚举；`reference/agent-core` 包含跨职责接口。目标目录见04。HTTP层使用 Jackson `readTree` 读取信封，按 `type` 显式选择 `AgentCommand.Initialize/Submit/Steer/...` 记录类型；不得打开 default typing，也不根据请求传来的 Java 类名反序列化。`schemaVersion=2` 是线协议识别，不是产品分期。

新增纯辅助类 `com.gitnova.agent.protocol.json.ProtocolJson`：统一 ObjectMapper（JavaTimeModule，UTC，拒绝未知/重复字段及尾随JSON）和 `canonicalBytes(Object)`。内部Mapper初始化后固定，公开mapper()返回已配置副本，内部编码不受调用方修改副本影响。规范化递归按对象字段名的**UTF-8无符号字节词典序**排序，数组保留顺序，保留显式null，数字按字段定义解码后输出，UTF-8，不做Unicode规范化或trim用户message；不声称规范化任意JSON数字表示。哈希为SHA256。Task幂等摘要使用repoId、actorId、sessionId、expectedWorklineId、expectedSessionVersion、原文及明确用户参数；deadline、attemptId等由第一次受理生成，不在重发时重新计算。

四个方法的输入、算法、旧Codec复用点与测试见[ProtocolJson施工说明](reference/agent-protocol/src/main/java/com/gitnova/agent/protocol/json/ProtocolJson.md)，施工位置保持02步骤1.3。readCommand/canonicalBytes/sha256沿用IOException边界，值对象静态约束用IllegalArgumentException；不新增协议异常类。HTTP仅将请求解码/构造失败映射400，编码/内部I/O失败不能误报为用户参数错。新协议排序规则不回改既有CanonicalJsonCodec及旧持久化摘要。

参数限制统一从配置注入：请求body默认1MiB、message最多32000个Unicode字符且UTF-8最多128KiB、commandId/worklineId/taskId/attemptId为规范UUID、sessionId为创建时的UUID；branch长度遵循原BranchName。`eventId=sessionId:epoch:sequence`，scope校验不能只靠长度。对真实源码内容和事件payload设独立配额，不用request body上限限制全部归档。

### 1.1 信封字段的空值规则

| 命令 | taskId/attemptId | payload类型 | 条件 |
|---|---|---|---|
| INITIALIZE | null/null | Initialize | BOOTING，只初始化一次 |
| SUBMIT_TASK | 两者必填 | Submit | IDLE、身份与当前HEAD一致；本地未发布改动不因此被清空 |
| STEER_TASK/CANCEL_TASK | 两者必填 | Steer/Cancel | 目标当前attempt，受理与生效分开 |
| PREVIEW_CHANGES | null/null | Preview | IDLE且无写进程时捕获；RUNNING返回BUSY；不发布 |
| CHECKPOINT_SESSION | null/null | Checkpoint | IDLE，无执行/未知平台操作；仅后台 |
| ACK_CHECKPOINT | null/null | CheckpointAck | 指向当前RECOVERY包与连续事件覆盖 |
| STOP_WORKER | null/null | StopWorker | PARKED且archiveId已确认，Session不关闭 |

Worker→Server的两种平台请求使用独立的PlatformOperation.Request和contracts/platform-operation.schema.json，不进入上述command枚举。核心请求字段为operationId/session/workline/epoch/task/attempt/toolCallId；模型只提供业务参数，平台从授权Session推导repo和身份。

#### 1.1.1 AgentCommand外层构造器：按这个顺序写

外层构造器只判断“这条命令自身是否合法”，不读数据库、文件、Worker状态或当前时间。规则直接放紧凑构造器，不要求新建Validator/helper。UUID统一为小写`8-4-4-4-12`十六进制形式，不能只校验长度，不自动trim或重建ID。

1. `schemaVersion == 2`；不支持的线上版本拒绝，旧历史格式由独立历史读取路径解释。
2. `commandId/sessionId/worklineId`均非null且是规范UUID；`runnerEpoch >= 1`。
3. `type/payload`均非null。必须先查type；否则`type == SOME_ENUM`全部为false会放过空type。
4. `SUBMIT_TASK/STEER_TASK/CANCEL_TASK`的taskId、attemptId必须同时为合法UUID；其余五种命令二者必须同时为null。空串不等于null。
5. 按1.1表逐项匹配type与Payload实际类型；sealed只限制实现集合，不保证组合正确。
6. Payload字段由对应内部record校验，不在外层再抄一次。构造失败抛带字段名/原因的`IllegalArgumentException`，不把完整载荷或密钥拼进错误。

| 内部Payload | 构造时检查的字段 | 不在这里判断 |
|---|---|---|
| Initialize | bootstrapId合法UUID；bootstrapSha256/runtimeConfigDigest小写64hex；baseCommit/publishedHead小写40hex | 包是否已上传、hash是否与磁盘相等、是否BOOTING |
| Submit | message非空白；expectedPublishedHead小写40hex；deadlineAt非null；runtimeConfigDigest小写64hex；worklineStatus为ACTIVE/MERGED/SOURCE_MISSING之一 | deadline是否已过、HEAD/配置是否仍匹配、当前线是否允许发布 |
| Steer / Cancel | message / reason非空白 | 目标attempt是否当前执行、输入是否已关闭 |
| Preview | expectedPublishedHead小写40hex | 是否IDLE、是否仍有写进程 |
| Checkpoint | purpose非null且为已知枚举 | 是否可以进入QUIESCING |
| CheckpointAck | exportId/archiveId合法UUID；bundleSha256小写64hex；coveredThrough非负 | 是否本实例等待的包、平台是否已保存连续日志 |
| StopWorker | confirmedArchiveId合法UUID | 是否PARKED、是否真的可以销毁 |

可配置的body字节、消息Unicode字符/UTF-8字节、嵌套深度等限额由解析/受理入口使用同一配置执行；record不读取环境变量或Spring配置。消息字符数不能直接用Java UTF-16的`String.length()`冒充Unicode字符数。语义固定的ID/hash格式则是协议自身限制。

#### 1.1.2 字段从哪里来、谁使用

| 字段/结构 | 赋值者与来源 | 消费者与生命周期 |
|---|---|---|
| commandId | Server首次建立控制意图时分配并保存 | Dispatcher/TaskInbox去重；同命令重发不换ID |
| sessionId/worklineId/runnerEpoch | Server已鉴权并固定的Session/Binding；LaunchSpec注入WorkerConfig | 外层只验格式；Worker受理比较当前实例，日志/平台适配保留归属；不传给Core输入 |
| taskId/attemptId | 平台首次受理Task/创建attempt时保存 | Worker固定在Execution及Writer.origin中；恢复后的新attempt与网络重试不是一回事 |
| type/payload | Server根据明确的用户操作/后台动作构造 | HTTP显式按type解码，不分析自然语言推TaskMode |
| message | 用户原话 | Submit.message→Core String入口/ModelTypes.Message(role="user")→用户事件→Context；不trim、不改写、不变成shell脚本 |
| expectedPublishedHead | 平台固定Workline.publishedHead | 受理时比较已安装baseline的已发布HEAD；不是当前脏工作树hash，不会清空草稿 |
| deadlineAt | 平台首次受理时结合运行策略固定 | ExecutionControl在执行边界检查；超时重发不得续期；历史反序列化不检查“现在” |
| runtimeConfigDigest | 对冻结RuntimeConfig规范化后计算 | INITIALIZE/Submit与Worker绑定配置比较；不是让Task传一份新权限表 |
| worklineStatus | 平台构造Submit时的已锁定工作线事实 | Worker耐久记录当前execution的RUNTIME_CONTEXT后单独注入；不混进用户正文，不代替平台实时授权 |
| requestDigest | Worker对已解析合法私有AgentCommand的规范化完整内容计算SHA256 | commandId内容冲突检查；不要混用公共Task的幂等摘要，两者输入不同 |

`ExecutionScope`仅复用Q/L/E的值比较，不承载权限。ID、版本、摘要的数值应原样透传；Worker不能发现不匹配后“帮请求改成当前值”再执行。

#### 1.1.3 校验放在哪一层，失败交给谁

| 层 | 检查内容 | 成功输出/失败边界 |
|---|---|---|
| HttpJson / ProtocolJson | 先限制输入大小；解析一份完整JSON；必需键存在；拒绝未知/重复键、尾随内容和错误字段类型 | 产生AgentCommand；格式失败400，超body限制413。nullable字段允许值null，不代表允许缺失键 |
| Payload与AgentCommand构造器 | 本节静态约束及type配对 | 产生合法值对象；IllegalArgumentException在HTTP边界转安全错误，不把堆栈返给用户 |
| Worker认证/TaskInbox受理 | 令牌用途与身份匹配；原命令摘要；已绑定配置；运行状态、目标attempt、实际deadline | 产生持久受理回执；没有成功记录受理就不能发ACCEPTED。相同命令重查在可变状态检查前返回原事实 |
| 具体资源/工具边界 | 实际文件/包hash、路径、进程、当前平台授权 | 产生执行结果；检查值对象不等于副作用已获准 |

`readTree`不会自动按record拒绝所有未知字段：按Schema允许键集合检查外层键，再按type转具体Payload；构造record前区分缺失键与显式null，避免Jackson给primitive默认0。不要打开default typing。规范化只稳定字段排序/编码，不移除有意义字段来“让digest一致”。

私有HTTP映射集中在HttpJson：身份/token失败403；请求格式400；超限413；新任务忙/ID或内容冲突409；未知命令/任务查询404；初始化尚未完成503；存储不可确认500/503且不得伪造REJECTED证明“从未执行”。网络错误由客户端保留UNKNOWN并查原ID。业务code表达具体原因，不能把所有409都当可自动重试。重复已受理请求可200返回原身份与acceptedSequence并标duplicate；首次受理202。

#### 1.1.4 CommandReceipt不是TaskView

| Receipt字段 | 来源/规则 |
|---|---|
| commandId、Q/L/E、taskId、attemptId | 已验证的原命令；回执不另分配任务身份 |
| requestDigest | 上述私有命令的固定摘要，用于重查一致性，不是成功证明 |
| status | ACCEPTED表示受理事实已可靠保存；REJECTED表示已确认拒绝，不表示一次未知副作用失败 |
| acceptedSequence | Submit/Steer/Cancel等受理日志的COMMAND_ACCEPTED.sequence；不是任务结束位置。INITIALIZE尚无SessionLog时可null，事实来源是control/install.json |
| duplicate | 本次交互命中了此前同内容命令；不决定是否执行，执行去重靠持久受理记录 |
| code/message | 有界、安全的受理说明；不是模型最终回答 |

解析失败未形成合法命令时返回ApiProblem，而不是用伪UUID凑CommandReceipt。TaskView来自执行事件投影；COMPLETED必须能沿answerEventId找到原响应，202绝不能直接投影为COMPLETED。

### 1.2 工具参数的最终形状

| 工具 | 参数 | 返回关键字段 |
|---|---|---|
| shell | action=RUN/START/POLL/STOP；RUN/START用script/cwd/timeoutSeconds，POLL/STOP用processId/cursor | processId、running、exitCode(nullable)、stdout/stderr预览、对象引用、truncation、停止确认 |
| read_file | path、startLine、endLine | lines[{number,text}]、hasMore、nextStartLine、fileSha256 |
| edit_file | mode=CREATE/REPLACE/DELETE，path；create内容，replace原文+新文/expectedSha，delete expectedSha | changed、beforeSha256、afterSha256、bytes |
| history_read | resultId、view=stdout/stderr/result、startLine/endLine | 原始来源、片段、captureTruncated、continue参数 |
| history_search | query、caseSensitive、cursor可空、limit | 原始来源命中、范围是否完成、nextCursor |
| report_progress | message、summary | operationId、confirmed、PUBLISHED/NO_CHANGES或明确失败/UNKNOWN、branch/commit/treeDigest |
| create_pull_request | title、body、draft | operationId、confirmed、PR_CREATED/PR_EXISTS或错误、pullRequestId |

工具实现顺序以shell为先：通过模型选择的shell调用使用`cat/sed/rg/find`等环境命令；镜像必须实际包含这些程序，不能把它们视为Linux内核自动提供的Agent工具。`read_file`为可选的有界行读取适配，不是启动Core的前置；需要稳定行号、分页或独立只读能力时再迁移旧实现。`edit_file`可复用已有精确替换算法，不要求用shell重写。工具参数没有平台WorkspaceId、FencingToken、全局generation；取消命令不是模型工具。

## 2. 事件 payload 单一字典

下表是Worker向平台归档的AgentEvent字典，不是Core输入协议。Core写SessionLog.Entry，Worker按第2.3节补固定归属并映射为AgentEvent；本地只有一份事实日志，SSE/平台投影不是第二个独立写入源。浏览器只接白名单映射。Map用于异构payload容器，但字段按事件类型校验，不接受任意结构。

| EventType | payload必需字段 | 谁产生/谁消费 |
|---|---|---|
| COMMAND_ACCEPTED | command完整信封、requestDigest | TaskInbox→receipt重建/平台命令投影 |
| WORKER_READY | publishedHead、runtimeConfigDigest、restoredFromArchive可空 | 初始化→平台就绪 |
| USER_MESSAGE_RECEIVED | message（完整ModelTypes.Message，role=user） | Engine记录初始用户输入一次→Context；Inbox仅受理；来源命令由Worker按task/attempt关联，不要求Core查命令 |
| TASK_STARTED | executionId、configDigest、deadlineAt | Core的EXECUTION_STARTED由Worker转换；deadline取受理命令；环境消息单独按HARNESS_FEEDBACK记录 |
| MODEL_CALL_STARTED | modelCallId、requestDigest、inputEstimate、purpose=MAIN/SUMMARY | 主调用Engine/摘要调用Summarizer→审计，各自唯一写入 |
| MODEL_RESPONSE | modelCallId、finishReason、text、reasoningContent(私有)、toolCalls、usage | Gateway后→Context与回答校验 |
| TOOL_STARTED | modelCallId、toolCallId、toolName、arguments、processId可空 | Engine→故障判断 |
| TOOL_RESULT | modelCallId、toolCallId、toolName、status、result、objects、historyReadback | Engine→HistoryIndex/Context |
| CONTEXT_SUMMARY_CREATED | summaryText、coveredThrough{epoch,sequence}、retainedGroups、configDigest | Core使用{streamId,sequence}，Worker按已存来源映射epoch；Context只消费Core形式 |
| HARNESS_FEEDBACK | kind、message、sourceScope | Engine→纠偏与恢复说明 |
| STEER_APPLIED | commandId、inputId、acceptedEventId、appliedBeforeModelCallId、message（USER Message） | Core只写inputId及消息/来源引用，Worker由已受理映射补commandId；不在Core反查命令 |
| ANSWER_DELIVERED | responseEventId、modelCallId | Engine→平台回答指针 |
| TASK_FINISHED | status、reason、answerEventId可空 | Worker收尾→Task execution投影 |
| RECOVERY_CHECKPOINT_READY | exportId、bundleSha256、bundleBytes、treeDigest、throughSequence、purpose=RECOVERY | 后台Sealer→ArchiveService；不触发发布 |
| CHECKPOINT_STORED | exportId、archiveId、coveredThrough | ACK_CHECKPOINT执行后→允许停环境，不清Task槽 |
| PLATFORM_OPERATION_STARTED | operationId、type、toolCallId、requestDigest | Worker发送前耐久记录→不明副作用核对 |
| PLATFORM_OPERATION_RESOLVED | operationId、result | 核对平台权威结果→原始工具结果 |
| PROGRESS_RECORDED | operationId、exportId、commit、treeDigest | Worker确认baseline安装→用户可见真实提交 |
| PULL_REQUEST_RECORDED | operationId、pullRequestId、sourceHead | 已确认PR→用户业务视图 |
| PREVIEW_READY | commandId、expectedPublishedHead、capturedSequence、treeDigest、observedAt、dirty、changedFiles、truncated | safe boundary→UI预览 |
| RECOVERY_INTERRUPTED | oldAttemptId、restoredArchiveId、coveredThrough、unpublishedChanges、reason | Recovery→新状态与用户提示 |
| WORKER_STOPPING | reason、confirmedArchiveId | Worker→生命周期 |
| WORKLINE_SWITCHED | syncId、oldWorklineId、newWorklineId、targetHead、changePolicy、sourceArchiveId | 激活后的首个SUBMIT记录/引用，Context使用；不能在准备实例ready时伪造成功切线 |

`TOOL_RESULT`先引用已经保存的对象再append；append得到eventId后，模型可见resultId就是该eventId。临时输出文件名称可以是UUID或内容hash，不需要预占未来事件序号。历史读取产生的TOOL_RESULT仍记录，但`historyReadback=true`使其不进入原始历史召回集合。

TASK_FINISHED必须在本地进程安全收尾后写入；Server归档它时按当前attempt清Session活跃槽。后台快照事件不清除后来新受理Task的槽。旧文档里的STEER_ACCEPTED在具体协议中由COMMAND_ACCEPTED(type=STEER_TASK)表达，避免两个不同的受理事实发生半提交。

### 2.1 回答关联与公开投影

链为TASK_FINISHED.answerEventId→ANSWER_DELIVERED.responseEventId→MODEL_RESPONSE.text。校验同session/workline/epoch/task/attempt、STOP、非空正文、toolCalls空；MODEL_RESPONSE在被引用前已归档。Answer原文不经过第二次总结。无工具的中间STOP若被已受理steer否决，就不产生ANSWER_DELIVERED。

公共SSE只输出：状态、工具名/经过清洗的预览、已交付answer、发布/资源问题。**不直接把包含reasoningContent、模型认证头、完整provider响应的私有事件流转发给浏览器。** 原始私有档案可以受权限保护调试访问。

### 2.2 SSE游标

Worker内：(epoch,sequence)；平台页面：archiveOffset。Worker用UTF-8、`id:`、`event: agent`、单行JSON `data:`、空行帧结束。Server解析SSE时先增量解码再分行，多个data用换行拼接；不假设一次read等于一条JSON。心跳只写`: keepalive\n\n`，无业务序号。

平台归档先锁Session行，再锁该epoch Binding，检查expectedSequence。插入event+更新投影+连续cursor同事务。`archive_offset`虽是AUTO_INCREMENT，也只在持有同Session串行锁时分配；否则事务先分配后提交乱序会使页面跳过迟提交事件。跨Session不是一条公开流，不要求全局offset连续。

### 2.3 事件写入：通用Entry、执行级Writer与平台信封

Core定义的唯一历史端口是reference中的SessionLog，里面的Entry/Position/Writer都是嵌套类型，不再新建一套EventSink/Journal接口。

| 类型 | 职责 |
|---|---|
| SessionLog | 只读history：read、boundary、awaitAfter；没有append、bind和close存储方法 |
| Position(streamId, sequence) | 本地历史定位；streamId是不透明日志段身份，不是Core解析的runnerEpoch |
| Entry(eventId, position, executionId, type, occurredAt, payload) | Core看到的执行事实；不含taskId/attemptId/worklineId |
| SessionLog.Writer | 固定executionId的append句柄；append返回已经耐久提交的Entry；close仅撤销该句柄 |
| FileSessionLog | 存储实现/拥有者，提供history只读视图、bind与宿主写入；Core只取得上述两个窄接口 |

**FileSessionLog具体方法（实现卡在02步骤2）：**

- 构造：`FileSessionLog(Path stateRoot, String streamId, FileLock directoryLock)`；本地启动器生成并保存streamId；云端用`sessionId + ":" + runnerEpoch`，Core不拆解它。
- `SessionLog history()`：返回只读接口视图，不把具体FileSessionLog传进Core。
- `SessionLog.Writer bind(String executionId, Map<String,String> origin)`：冻结executionId与origin；本地origin为空，Worker传已校验的Q/L/E、taskId、attemptId、commandId。origin不进入模型文本。
- `appendHost(String type, String executionId, Map<String,String> origin, Map<String,Object> payload)`：仅宿主控制层使用，普通工具拿不到。无任务的宿主事件executionId可null；Core writer不可null。
- `readStored(Position after, Position through, int limit)`：供Worker重建回执/SSE，返回内部StoredEntry；Core只读投影后的Entry。
- `close()`：存储拥有者关闭通道，不释放外部FileLock。

StoredEntry放在FileSessionLog内部，字段为schemaVersion=1、Entry entry、Map<String,String> origin。磁盘行为`{record: StoredEntry, digest}`，digest针对record规范化字节；不是先存Core日志再另外写一份平台日志。历史读取只投影entry，但不删除原始origin。payload/origin都必须稳定快照，不能只浅拷贝可变嵌套值。这个是新Harness的本地格式，不静默重写旧生产历史。

编码只需通用Jackson与确定性JSON规则，复用已掌握的递归排序算法放在FileSessionLog内部即可；不能为调用ProtocolJson而让Core重新依赖agent-protocol，也不为此新建通用框架模块。规范字节保持UTF-8对象键排序、数组顺序、null和字符串原文，读取时校验版本/hash，再构造Entry。

写入流程固定为：

```text
Writer.append(type, payload)
  → 检查当前句柄未关闭，采用构造时固定executionId/origin
  → 同一存储追加锁内分配sequence、eventId、occurredAt
  → 校验并冻结payload → 编码record/digest → 完整write → force
  → 发布可读Boundary、唤醒等待者 → 返回Entry
```

eventId=`streamId + ":" + sequence`；云端仍为Q:E:sequence，因此平台既有eventId规则不变。本地无需伪造平台Task或Binding。每段sequence从1开始；重开同段继续，不重编号旧结果。Boundary只返回当前段已确认位置与完整字节尾部；跨段读取遵循已保存段顺序/选择范围，不能按streamId字符串排序。未知段或不存在的游标明确报错。

**Worker适配在同一事实之后完成：** readStored取得entry+origin，用已固定origin填AgentEvent的Q/L/E/task/attempt，沿用entry的sequence/eventId/time/payload。Core的EXECUTION_STARTED映射为TASK_STARTED；STEER_APPLIED按inputId/acceptedEventId关联原命令补commandId；摘要coveredThrough的streamId按原段origin转为epoch。映射是确定性的，不在重发时取当前Task、当前工作线或当前时间。Core历史不反过来读取平台信封。平台原始归档保存这份确定的AgentEvent；不向协议v2随意增加外层字段。

AgentEvent仍按原schema校验正值epoch/sequence、scope一致、task/attempt配对及各EventType要求。WORKER_READY、checkpoint等宿主事件不凭空填当前Task；不得从ThreadLocal或可变worker.currentTask补归属。

**句柄关闭不是把存储关掉。** A执行结束关闭A的Writer，B使用新Writer；A的迟到回调不能追加到B，也不能覆盖终态。Worker在确认受管进程和输出收尾后，使用固定A身份写TASK_FINISHED，再释放槽。必要迟到诊断由宿主单独记录为诊断，不改写已结束执行。禁止Core Writer直接伪造COMMAND_ACCEPTED、TASK_FINISHED等宿主事件。

| 事实 | 唯一写入责任 |
|---|---|
| COMMAND_ACCEPTED、运行映射 | TaskInbox：耐久受理时保存command与executionId；相同命令重查不重跑 |
| USER_MESSAGE_RECEIVED、EXECUTION_STARTED | Engine通过本次Writer记录，初始用户消息只写一次 |
| MODEL_CALL_STARTED、MODEL_RESPONSE | Engine；摘要调用由Summarizer用同一Writer记录purpose=SUMMARY |
| TOOL_STARTED、TOOL_RESULT | Engine统一记录；工具与Supervisor不再写第二份同名事件 |
| CONTEXT_SUMMARY_CREATED | Coordinator在覆盖/预算校验成功后记录，再发布摘要 |
| STEER_APPLIED | Engine写inputId、原USER Message及受理引用；不读AgentCommand |
| ANSWER_DELIVERED | Engine在Control的STOP边界保存响应引用 |
| TASK_FINISHED | Worker Finalizer确认安全收尾后，以该次固定身份写入 |

append不是best-effort监听回调。force失败停止确认与后续执行；已force但返回丢失属于结果未知，按日志对账，不能自动重放Shell。缺失对象/损坏记录明确失败；只有已确认事件能进入下一模型请求。新格式版本演进需要解码策略，不能依赖当前Java DTO忽略旧字段。

### 2.4 本地字节对象与模型观察不是同一个对象

```text
工具输出流 → ResultStore.Capture → finish()返回Ref(objectId,sha256,size,captureTruncated)
工具结构化结果 + Ref集合 → executionWriter.append(TOOL_RESULT) → sourceEntry
sourceEntry.eventId就是resultId → HistoryIndex记录来源
sourceEntry + 原始结果 → ToolObservationProjector → ModelTypes.Message(role=tool)
```

`captureId`是单次临时写入身份，`objectId`定位不可变字节，`resultId`定位带task/tool/scope的历史事实，三者不要混为一个字段。Ref.size只表示实际已保存字节；超过捕获上限的原文不会因为存在Artifact而恢复。小结构化结果可直接在事件payload，stdout/stderr等字节对象按引用保存；不强制小结果多复制一份外置文件。

对象完成发布后才能追加引用它的事件；事件追加失败可能留下孤儿对象，但不能反过来留下已确认的悬空引用。HistoryIndex是投影，丢失可从日志重建；readback事件保留在执行史，但historyReadback=true时不进入原始证据召回集合。读取必须验证Session、原事件、Ref和实际hash；不能将任意用户路径当历史对象路径。

### 2.5 Core输入与Worker执行绑定

**不创建TaskInput，也不把它换个名字搬回Core。** AgentCommand保留在Worker；Core入口接原始文本或Core自己的ModelTypes.Message。

```text
Worker接收AgentCommand
  → 校验绑定/授权/幂等/配置/deadline
  → 保存COMMAND_ACCEPTED和固定executionId
  → 为本次执行绑定Writer、Control、平台工具
  → core.run(原文, sessionRuntime, control, writer)
Core
  → 原文包装为USER Message，只记录一次
  → Context → Model → ToolRuntime → Observation → 自然STOP
Worker
  → 按绑定的Task/Attempt关联结果并安全收尾
```

入口参考：

```java
AgentOutcome run(ModelTypes.Message input, SessionRuntime session,
                 ExecutionControl control, SessionLog.Writer events);

// 同一入口的便捷重载，内部包装USER Message；不trim或重写原文。
AgentOutcome run(String userText, SessionRuntime session,
                 ExecutionControl control, SessionLog.Writer events);
```

Message统一为role/text/toolCalls/toolCallId/reasoningContent，不新增ChatMessage/UserPrompt。用户入口只允许role=user，text非空白但逐字保留；toolCalls为空，toolCallId/reasoningContent为null。响应和工具结果由实际执行转成assistant/tool消息。身份、取消和授权不包装成用户消息。

| 数据/能力 | 谁提供 | Core需要知道什么 |
|---|---|---|
| 原始输入/Message | 本地调用者或Worker | 本次用户要求；不会解析AgentCommand |
| SessionRuntime | 宿主 | sessionId、目录、只读history、ResultStore；多个执行共享资源 |
| SessionLog.Writer | 本地存储或Worker绑定适配器 | executionId、append事实并取得稳定引用；不知道平台Task/Attempt |
| ExecutionControl | 每次执行单独创建 | 取消、deadline检查、后续输入、STOP竞态；不依赖HTTP |
| RuntimeConfig/ToolRuntime | 受信装配 | 预算和实际可用工具，不从正文提权 |
| ToolTypes.Context | Engine | executionId、toolCallId、SessionRuntime、Control；没有taskId/attemptId |
| AgentOutcome | Engine | 原始answer与事件引用、结束原因；不是平台验收或发布结论 |

**Worker的Execution是WorkerSession内的运行句柄，不是新顶层Service。** 至少固定acceptedCommand、executionId、Control、Writer、该次ToolRuntime；Map按taskId+attemptId查句柄。taskId/attemptId等取自不可变acceptedCommand。取消旧attempt不能取消后来新attempt；迟到回调只能访问原句柄。Writer关闭、平台客户端和执行器由拥有者按生命周期释放。初始executionId只分配一次并记录在受理事实中；重查不能另建身份或重新调度。

**平台能力通过工具装配，不是AgentEngine第五个必填参数。** Worker在受理后创建绑定该次身份的PlatformCapabilities，再构造ReportProgressTool/CreatePullRequestTool，和本地工具一起交给已有ToolRuntime。Engine可以每次轻量装配，但共享会话历史/存储/模型连接；不能在共享工具实例中覆盖currentTask。平台协议结果在Worker转为普通ToolTypes.Result，Core不import PlatformOperation。没有平台能力时不注册工具，不提供假成功实现。MCP以后可以作为另一种AgentTool适配；本轮不实现MCP、不把本地工具强制MCP化。

**环境消息不再塞进TaskInput。** Worker将必要workline事实写成当前execution的HARNESS_FEEDBACK(kind=RUNTIME_CONTEXT)，先耐久保存再进入Loop；本地运行可没有这条。Context只将受信宿主产生的环境记录单独注入，工具输出/摘要中的同名字符串不升级权限。配置/令牌/完整命令信封不自动成为prompt；环境说明不代替平台实时授权。

**当前输入保护与历史分组：** Engine记录USER_MESSAGE_RECEIVED得到原事件引用。Context按Writer.executionId查本次原始输入与已应用Steer，保留其原文；摘要覆盖之后按引用补回且只补一次。Group使用executionId与源Position，不用Task/workline字段判断当前要求。上一执行的局部要求仍带历史来源，不能自动升格；持久用户指令按已有显式引用保留。跨工作线选取由Worker的history视图做，Core不能凭摘要决定跨域可见性。

**Steer/Cancel：** ExecutionControl.Steer使用inputId、USER Message、acceptedEventId。inputId是补充输入身份，本地入口可自行生成；Worker持有它与命令的映射，Core不解析commandId。只有STEER_APPLIED才进入模型历史，已受理未应用的输入不能伪装已看见。Cancel仍调用控制信号，不伪装为“请停止”消息。

**独立本地调用的前置：** 打开真实FileSessionLog/ResultStore，生成一个本地executionId，用空origin绑定Writer，创建Control与本地ToolRuntime，直接run一句话。无需Task、AgentCommand、数据库、Worker或平台认证。调用者最终关闭该Writer和受管进程；同一Session的底层存储在会话结束才关闭。

本输入边界的必过验收：原文/角色不变；无COMMAND_ACCEPTED仍可运行；两次本地执行共享历史；摘要保留当前原文与补充；A迟到写入不归B；关闭Writer不关闭共享history；持久写入失败不继续；未装平台工具时仍能完成本地任务。这些不代替工具、Context、Worker等模块的其他验收。参考编译/文档检查不能代替真实实现测试。

### 2.6 Context的数据转换与预算口径

`SessionLog.Position(streamId,sequence)`是原始历史位置；`Group(first,last,executionId,messages)`是闭合交互；`Summary(text,coveredThrough,configDigest)`是有损投影；`HistorySnapshot(groups,summary,through)`是一份固定读取上界内的数据。这些结构不各自拥有新的持久化authority。Summary覆盖的是源历史前缀，不是摘要事件自己的位置。

`SessionHistoryReader.load`在固定boundary内重组历史；`project`产生合法配对消息。`DefaultContextCoordinator.prepare`每次将最新可信系统规则、当前Task原文/已应用补充、当前环境事实与历史投影组合，返回**完整ModelTypes.Request**，不是只有summary字符串。旧Task限定保留来源，不悄悄变成当前Task约束；跨工作线选择沿已有context-handover合同，不在本轮重构新增Memory推断。

预算定义：`inputLimit = contextWindow - maxOutputTokens - safetyMarginTokens`；固定系统/工具占用为fixedTokens，动态上下文容量`dynamicLimit = inputLimit - fixedTokens`。当前Task原文也计入动态上下文；不能一边固定扣除、一边在消息中再次扣。以动态预计用量/动态容量比较summaryTrigger、compactTrigger，处理后重新核算整个Request是否可发送。保护内容本身超限时返回明确预算错误，不删除有效用户要求强行继续。

实际provider usage是计量事实，本地估算用于新增内容/首轮/上下文替换后的预测；上次usage不能直接当下次请求大小。observeResponse只在主响应已保存后更新同一主请求形状的usage锚点；摘要模型usage单独记录，不能覆盖主锚点。摘要后消息形状改变应使旧锚点失效或重建。保持旧算法/参数，不在迁移时偷偷换阈值。

摘要候选校验成功、coveredThrough确实来自闭合组且落日志后才发布到下一请求；失败保留旧摘要与历史。未超硬输入预算可按已定义的降级策略继续；超限则明确停止/报告，不能在一次prepare中无限递归摘要。摘要请求自身也受预算、deadline和取消控制。

## 3. Worker状态表：只用这一份

| 状态 | 可受理操作 | 状态变化/拒绝规则 |
|---|---|---|
| BOOTING/INITIALIZING | 初始化与健康检查 | 初始化成功IDLE，失败BLOCKED |
| IDLE | SUBMIT、PREVIEW、后台CHECKPOINT | SUBMIT→RUNNING；真正无活动才checkpoint→QUIESCING |
| RUNNING | STEER、CANCEL、查询；预览返回BUSY | 同一Task内部可调用多次report_progress/PR；另一Task拒绝 |
| CANCELLING | 重复取消、查询 | 确认本地进程停止后收尾；不保证取消已发生的外部副作用 |
| FINALIZING | 查询、旧请求重查 | 仅本地任务收尾；TASK_FINISHED后IDLE，不等待发布 |
| QUIESCING | 查询、同回收命令重查 | 冻结RECOVERY包；拒绝新的写者；完成后AWAITING_ARCHIVE |
| AWAITING_ARCHIVE | ACK_CHECKPOINT、查询 | 正确ACK后PARKED；归档失败保留环境，不销毁 |
| PARKED | STOP_WORKER、查询 | 已停止写入且档案确认后STOPPING；新Task由平台恢复后投递 |
| BLOCKED | 查询和明确恢复处理 | 无法证明写进程已停/存储损坏时禁止继续 |
| STOPPING/STOPPED | 停止确认 | 只改变实例状态，不把业务Session关掉 |

pendingPlatformOperationId是Worker本地耐久记录的外部动作身份，不是Task全局结算状态。未知时禁新外部副作用及回收；当前Task仍可读写本地文件、报告实际未知或自然结束。

### 3.1 STEER与STOP的线性化位置

锁序：TaskInbox受理锁→ExecutionControl锁→SessionLog追加锁；Engine只取ExecutionControl→SessionLog，**不能在持有Control锁时回调取得Inbox锁**。在同一Control锁下：STEER先耐久受理再入队；STOP检查队列为空、未取消后才保存ANSWER_DELIVERED并关闭输入。谁先获得锁，谁先成立。落日志失败不能假装受理或完成。

HTTP取消请求必须能响应长模型调用。取消回调在锁外运行，注册时检查此前是否已取消。不得让取消请求排在单线程Agent执行器后面。默认执行器：一个单Task线程；独立控制HTTP执行器；独立输出消费；有界SSE连接。WorkerAssembly拥有它们并逆序关闭。启动分为控制壳与初始化后激活两段，详细顺序以09第3节为准。

### 3.2 异常返回边界：不要全部catch成工具参数错

| 情况 | 处理责任与输出 | 是否允许继续Loop |
|---|---|---|
| 工具未知/参数错误/精确编辑冲突 | ToolRuntime/具体Tool返回INVALID_ARGUMENT或CONFLICT及字段位置、事实 | 结果先记录再供模型纠偏；仍受预算限制 |
| 命令已结束且exitCode非0 | LocalShellTool返回真实Exit事实 | 可以；任务可能本来就在调查失败 |
| 网络超时/模型协议错误/输出截断 | Gateway分类，Engine记录反馈或终止原因；仅协议完整且可界定时按有限策略纠偏 | 不无限重试；未解析出的工具不能执行 |
| 已取消/deadline/预算耗尽 | Control/Engine返回对应AgentOutcome原因，Finalizer安全收尾 | 不继续新的模型/工具动作 |
| 原始结果保存或日志force失败 | 存储错误向外传播，Worker阻止后续执行与假成功 | 不允许；不能当“模型换个参数就能解决” |
| 无法确认子进程已停止 | Worker进入BLOCKED，请平台处置实例 | 不释放为可执行IDLE，不封存会变的目录 |
| 平台操作响应未知 | 保存原operationId，按原ID查结果 | 本地分析/回答可继续；禁止新的平台副作用与回收 |

ACK/SSE/HTTP响应丢失不改变已经持久的事实。没有可靠记录不能证明“肯定未发生”；恢复时查原身份与实际资源，不重放未知Shell。异常类可放所属组件内，避免为了每种错误新建一套跨层异常框架；稳定code/状态与日志来源比类数量重要。

## 4. 平台状态不是第二套逐步Agent引擎

Task只有执行/回答投影；progresses是agent_platform_operation按Task查询出的零到多条结果。删除Task上的settlementStatus与单值publicationStatus，避免一次任务多个Commit时覆盖历史。dirty状态仅在实际核对后给值，未测为null。

Worker写TASK_FINISHED前完成本地安全收尾；Server在同事务保存终态并清activeTaskId，只匹配当前attempt。平台不可达时Worker不需要等归档才能发最终回答，但平台尚未保存的回答不能伪装为已可跨设备查询。实际数据库成功后才对外返回可靠查询结果。

后台回收状态在Binding；Session.status不因环境销毁改变业务语义。新Task受理与回收取同Session锁，环境待恢复时Task为PENDING_DISPATCH且currentAttemptId可空；就绪后按唯一事务补Attempt与SUBMIT。只看历史不恢复环境。

### 5.1 初始化与任务（保留原TX编号）

**TX-S1**：repo门闩→Session创建幂等→固定A→准备初始L1与Binding。Session.next_runner_epoch增量分配每个新实例epoch，失败也不复用。activeWorkline可在初始准备指L1但尚无active Binding；不可接实际执行。创建意图/包/实例都绑定原ID。

**TX-S2**：repo→Session→L1/Binding→受管分支。ready证据与Q/L1/epoch/A/config一致后建指向A的分支、标L1 ACTIVE并激活current_runner_epoch，Session.session_version+1；不同内容/其他归属分支不得占用。网络操作不在事务里。

**TX-T1**：验证actor/repo/session；Session锁后先按(actor,session,key)查旧Task，同摘要返回旧结果。新请求核对expectedWorklineId/expectedSessionVersion、workflow OPEN、无sync gate与活跃Task。Task冻结L，状态PENDING_DISPATCH。普通回收中可以先保存但不发旧Worker；READY且已激活才分配Attempt/command。不允许仅凭MERGED线判Session不能收消息；发布限制是另一条规则。

**TX-T2**：Dispatcher仅发送已保存信封；超时/5xx为UNKNOWN，原ID查询。迟到202不得把COMPLETED改回ACCEPTED。返回503要核对实际实例和初始化；不能伪造未受理。

**TX-T3**：取消先标固定Task.cancel_requested。未派发可原子撤销；已开始/发送结果未知时查询原SUBMIT，确认受理再送同取消意图。Worker未知attempt可404但不能因此断言历史未执行。只在可证明停止后清槽。

**TX-E1**：Session→Binding，校验事件scope/digest/连续序号→归档→Task/Attempt投影→连续游标，同事务。每个事件先查eventId，相同原字节重复幂等；当前终态必须同时匹配activeTaskId/currentAttemptId/workline/epoch才清槽。旧历史仍可更新旧Task的历史事实，但不得改变当前指针。

### 5.2 归档与平台副作用

**TX-A1**：事务外下载并验证固定RECOVERY/PROGRESS，保存对象。Session/Workline/Binding锁内插archive（同Q/export去重）；只有RECOVERY能更新该Workline.latest_recovery_archive_id，且不可被较早epoch/sequence回退。准备sync实例的日志可私有归档，但不能发布成当前工作已切换。ACK只在包、引用对象、截止N的连续事件和快照就绪事件已持久保存后发送。

**TX-O1**：repo→Session→Workline/Binding→Task/Attempt→Operation，先对已有ID核对摘要。新操作要求当前active Q/L/epoch、线ACTIVE、Task身份与授权匹配、无sync gate。持久PENDING返回202。schema权限是运行配置，不由payload提供。原已受理操作的查询重新检查用户/用途权限后返回原事实，不用新active线改写它。

**TX-P1**：固定PROGRESS包及operation，保存作者/parent/time/message，后续重试复用。**TX-P2**：repo→Session→Workline/Binding→Branch→Task/Attempt→Operation/Publication，重验授权和受管分支归属；CAS、CommitRecord、Workline.publishedHead、Publication/Operation结果与BRANCH_UPDATED Outbox同事务。已受理的操作可能在Task取消后完成，取消不是撤销；不得要求已完成操作返回前Task仍RUNNING。合并/sync不能越过PENDING/PROCESSING操作。

**TX-O2**：Agent创建PR复用通用PR创建事务，允许当前Task运行；固定源line/branch/S，已有OPEN PR返回原引用，不覆盖它后来编辑的描述；Operation成功与PR/Outbox同事务。它不隐式commit。

### 5.3 PR、同步和业务事件

**TX-R1/TX-R2**：完整流程见13/16。普通PR不查Sandbox。merge不取W/RECOVERY；最终核对R/S/T、权限和受管线无active Task/pending operation/sync gate，标PR与Workline MERGED，Session仍OPEN。merge的状态统一PREPARING/COMPUTING/SUCCEEDED/CONFLICT/FAILED；请求strategy固定FF_OR_SQUASH。

**TX-Y1/TX-Y2**：显式sync准备/激活，见12及[同步失败表](contracts/sync-recovery-table.md)。同一Session的sync_operation_id是持久门闩，不因HTTP超时清空；不同新任务返回409。新epoch ready之后、激活之前无模型或平台写授权；最终激活原子切Q.active_workline/current_epoch并清自己的gate。清理独立于成功事实。

**TX-D1/TX-N1**：业务事实与Outbox同事务；消费者receipt、投影及必要派生Outbox同事务，COMMIT之后ACK。DomainEvent格式和事件因果见15及contracts/business-events.md。不是把AgentEvent接进通知队列。

## 6. ZIP、Manifest和baseline的具体规则

ExportManifest新增purpose=BOOTSTRAP/RECOVERY/PROGRESS。BOOTSTRAP来自平台准备固定A或显式sync的新H/W撇；RECOVERY必须含tree/state/baseline及完整日志覆盖，才可用于恢复；PROGRESS只含冻结TREE条目及manifest（不含BASELINE/STATE条目），stateDigest为空，不能作为完整恢复包。ArchiveService和BundleValidator分别按purpose校验，不能接受缺state的RECOVERY。

baseline只在受控初始化（含显式sync的H）或确认report_progress成功后更新；PUBLISHED以本次冻结树更新，不读取后续活动树。NO_CHANGES保持等价基准。没有发布时保留dirty文件；Task结束不做隐式提交。

包中exports与临时ZIP不递归打包。日志按完整截止N/字节offset复制。普通文件原始字节、CRLF、路径大小写、Unicode不被normalize。TREE digest排序与编码沿用第15节；stateDigest仅用于BOOTSTRAP/RECOVERY的STATE+BASELINE集合。

导入先在临时目录校验中央目录类型、路径、重复entry、实际解压限额和每个hash；禁止符号链接/设备文件/权限升级；校验成功后才切换。已跟踪文件不能被ignore规则误删。代码Diff只用于展示，不能替代提交字节。

### 6.1 恢复与晚到发布结果

正常回收先核对所有pending平台操作，日志/工作树/baseline为同一边界，RECOVERY.confirmedPublishedHead与Server一致。ACK_CHECKPOINT只确认恢复包，不推进仓库HEAD。

崩溃恢复遇到更旧包与更晚平台发布时，按operationId核对结果；必须有对应文件树和明确Context覆盖才继续。不能只修改head字段配上旧文件；无法组合可信状态返回RECOVERY_BASE_DIVERGED，保留历史，不偷偷覆盖最新分支。详见08第8节。

## 7. 公共API与私有协议不混用

全部协作端点统一在16；PR比较使用`GET /api/repos/{repoId}/pulls/{prId}/compare`，元数据/draft使用`PATCH .../{prId}`。合并请求为`mergeId,prVersion,sourceHead,targetHead,strategy,message`，strategy=FF_OR_SQUASH；不同于旧expectedRevision/method=AUTO格式。

公共Task：`POST /api/repos/{repoId}/agent/sessions/{sessionId}/tasks`，header为Idempotency-Key，body只含message、expectedWorklineId、expectedSessionVersion。私有Task才是完整AgentCommand。public与private Schema分别为public-task.schema.json和command.schema.json。

公共steer/cancel/retry与查询仍在具体Task下。变更预览统一`POST .../sessions/{sessionId}/change-preview`（202含commandId），随后`GET .../change-preview/{commandId}`取固定结果；若使用可信已回收RECOVERY可直接200返回预览，不新建Worker。运行中精确预览返回BUSY。同步是`POST .../sync`及`GET .../sync/{syncId}`，不新增Worker命令类型。

私有PREVIEW_CHANGES的taskId/attemptId固定null；预览Q/L/epoch来自信封。所有public查询都重新验证actor/repo/session/pr归属，不能直接暴露私有WorkerHealth/credential。

## 8. 完成SQL与协议后如何验收

先运行离线contract编译与JSON fixture校验；然后在MySQL副本执行新migration，验证旧历史不变、唯一约束、UPDATE影响行数及回滚；至少用两个真实数据库连接测TX-T1和TX-R2并发。不能用单线程Mock Mapper证明锁和外键正确。

这里已经决定表、字段、职责和事务顺序；尚未把“这些DDL在你的最新库上执行成功”当作事实。没有Docker/MySQL服务的文档生成环境无法提供该证据，02给出本机验收步骤，07明确记录这个区别。

## 11. 通用Task与工具授权（替代旧任务分类）

Submit包含message、expectedPublishedHead、deadlineAt、runtimeConfigDigest、worklineStatus；Core不使用TaskInput或mode。公共Task正文不接受mode/allowedTools/capabilities。RuntimeConfig.allowedTools来自平台在Binding中冻结的受信配置；排序后不可变、拒绝重复/未知名、空列表表示无工具。它进入runtimeConfigDigest；原命令重发不改变配置摘要。definitions与execute共享同一受限工具Map。模型意图不授予权限，平台操作入口仍重新鉴权。

Jackson显式开启FAIL_ON_UNKNOWN_PROPERTIES、FAIL_ON_TRAILING_TOKENS和重复键检测；关闭default typing。不要将“拒绝未知字段”写成关闭FAIL_ON_UNKNOWN_PROPERTIES。sealed仅限制Java实现集合，不会自动证明CommandType与Payload成对匹配；解析和构造边界都应验证。

旧Review/专属QA执行入口按02步骤17停止受理，保留最小历史读取。不要创建TaskMode、专属Review报告工具或兼容执行适配器。普通自然语言审阅/问答仍由同一个Agent处理。

已执行过旧草案migration时必须另写增量迁移并保留旧记录解释能力；本包schema仅为未执行的目标DDL，不能修改Flyway已应用文件。旧Task.mode字段不回填成另一种权限事实。

## 12. 样例类型和施工先后

RuntimeConfig、ControlTypes、ControlRows的完整字段已随reference提供；contracts/sql-field-map.md逐列对应DDL。ToolRuntime确定为普通Map类，在步骤 3就创建以供脚本模型测试；不是步骤 4才出现的接口。步骤 6先建立TaskFinalizer接口，再写Inbox，真实LocalTaskFinalizer与独立SessionSealer在步骤 8装配。假Finalizer只在test源码，Main缺正式Finalizer时不允许对外READY。

接口引用可在同一步集体创建后编译；不是要求先写一个尚无依赖的空实现。如果编译报某个body中使用的辅助类型不存在，先查04“嵌套类型”和reference；不得另起同名职责层。未由外部协议引用的纯helper可作为类内私有方法，文档不要求每个helper一文件。

## 13. 仓库发布与归档的补充裁决

一Task可有多次progress，每次是不同operation和独立immutable export。重复同operation必须返回同结果；不明结果时不生成新意图。当前树恢复为最初A，但远端在B，仍应由下一次report_progress生成以B为父的新提交，不能因相对初始A无差异就跳过。

RECOVERY覆盖全部原始记录与未发布代码；PROGRESS不覆盖会话历史。只保存摘要或某次Commit都不足以承诺完整恢复。

ControlTypes内运行token不得进入命令正文、manifest或普通日志。WorkerConfig增加platformEndpoint和platformToken，平台从受控配置/Session范围注入。模型和平台能力令牌用途分开；网络与凭据边界仍是基础要求，不因取消任务级结算而弱化。

## 14. 初始化与HTTP读取不能向后依赖封存实现

步骤 6先创建WorkerResources接口，HTTP类只调用receiveBootstrap/initialize/export/previewJson；步骤 8由LocalWorkerResources使用BundleCodec/ExportStore实现。这样可以先独立测试HTTP受理，而不将一个空的生产ExportStore写出来冒充完成。TaskFinalizer同样是先声明、后注入生产实现。两个接口的完整签名在reference。

开发中允许先建立直接互相引用的一小组类型，再立即编译并观察对应行为，不必等待整个步骤的全部类完成。依赖后续能力时只在test注入已有接口的替身；所有生产依赖必须在最终WorkerAssembly装配时闭合。

SQL方法和对应锁/更新条件见[Mapper施工表](contracts/mapper-contracts.md)，SQL字段见[逐列字典](contracts/sql-field-map.md)。这两份不是额外的产品阶段，而是05的文件级展开。

关键类构造器、方法和嵌套结果记录见[component-methods.md](contracts/component-methods.md)，与reference共同约束实现。

## 15. 字节格式最终补充

所有digest条目排序以UTF-8无符号字节词典序为准，不使用受语言/locale影响的默认排序。TREE用于托管源码内容摘要，写pathLength:uint32_be、pathBytes、size:uint64_be、sha256:32bytes。STATE和BASELINE共同进入stateDigest，额外在每条前面写kind字节（STATE=1、BASELINE=2），最后写executable字节（0或1）。长度/size必须在限额内，不允许负值。manifest最终由确定性JSON编码；ZIP外层sha绑定manifest全部字段，所以不允许替换permission或scope。

现有GNOV只记录path→blob，不具备原生Git可执行位/符号链接模式。封存/恢复可以保存普通可执行权限元数据，但发布不能宣称GNOV因chmod单独生成了原生Git模式变化。首次bootstrap没有模式证据时使用普通文件权限；执行无可执行位脚本用`bash ./mvnw`等明确解释器，不能因为Linux目录存在就假定拥有完整Git工作副本。

## 16. 受管分支与历史、恢复上下文

通用ManagedBranchPolicy声明在repository，AgentManagedBranchPolicy实现在线路控制模块。所有分支写入口先查真实branchId→workline归属，不能只看可空PR来源字段或分支名前缀。普通push拒绝写受管源；merge目标不得为受管分支。merge资格只查DB，不要求checkpoint。

新epoch从sequence=1追加，eventId仍为Q:epoch:sequence；Workline在信封里校验。旧epoch原日志与结果objects按原路径/原字节只读放入state/history，不能写成新事件。RECOVERY的throughSequence仅指当前epoch，历史旧epoch的完整覆盖写入state/history-index.json并受stateDigest保护。resultId稳定，读取先校验属于Session的已保留历史scope。

同线恢复重建活动Context到已保存覆盖。跨线sync复制原始历史和结果对象以便回查，但活动Context只带显式长期用户约束、未完成目标和基线切换说明；旧工具输出不伪装为新代码已验证。结构化来源保存在state/context-selection.json，列出sourceArchiveId、旧scope、当前workline与selected group IDs；所有group必须在history-index覆盖中。

新Worker初始化只发WORKER_READY，表示prepared可运行。平台激活事务是切换事实的权威来源。首个授权SUBMIT到达新Worker时，使用bootstrap中已固定的syncId/前后线信息追加一次WORKLINE_SWITCHED（重启按日志去重）；它是模型环境事实，不是冒充用户指示。准备实例如果未被激活就销毁，不生成成功切换事件。

文件锁、进程登记、install.json属于实例控制信息，不从旧归档直接激活为新实例控制权。安装先staging验证、后打开日志，详见09。命名卷不同时挂两个写实例；旧实例未知时不继续自动接管。

跨线Context文件及首次记录的精确规则见[Context交接合同](contracts/context-handover.md)。

**合并事实怎样进模型：** Server在构造每次私有SUBMIT时，从已锁定Workline冻结`worklineStatus`（ACTIVE/MERGED/SOURCE_MISSING），持久在命令信封中；Worker将它渲染为当前execution的HARNESS_FEEDBACK(kind=RUNTIME_CONTEXT)，耐久记录后由Context单独注入，不增加Core业务字段，也不改写USER正文。它不是TaskMode，不决定自然语言意图，也不授予工具权限；公开Task不能传入它。这样merge不重载沙箱也能让下一Task知道旧线已合并。若执行时平台状态后来变化，外部发布仍以Server当前授权为准，不凭此提示消息放行。

## 17. 私有查询/回执精确合同

CommandReceipt使用status=ACCEPTED/REJECTED、requestDigest、Q/L/epoch、task/attempt、acceptedSequence、duplicate、code/message；不使用另一个accepted布尔量+executionStatus形状。acceptedSequence是Worker日志位置，初始化没有日志可为null，安装回执在control/install.json核对。examples/accepted.json与receipt.schema.json同字段。

WorkerHealth有Q/L/epoch；TaskView增加可空runnerEpoch，PENDING且尚未分配attempt时为null，其余来自固定attempt；answer沿两个原始事件ID，不以latest assistant猜。平台操作Result固定operationId/state/outcome与结果引用，安装baseline前再根据已保存Request检查Q/L/epoch，Result本身不是新的授权。

这些为私有查询类型。公开页面由Server白名单投影，只展示需要的Task/代码线业务信息，不原样公开WorkerHealth、令牌或宿主地址。额外Schema是本包可复跑验证手段，不要求生产增加另一套JSON处理框架。
