# GitNova：验收矩阵与资料依据

## 1. 如何记录验收

所有用例初始状态都是**未执行**。本文没有运行新系统，不提供虚假的通过标记。每次验收记录：代码提交/工作树摘要、环境与镜像、测试命令、结果、证据路径和剩余问题。

单元测试验证自己的代码逻辑；容器集成测试验证Linux/网络/SDK语义；真实模型实验验证整体任务行为。三种证据不能互相替代。一次真实任务成功不证明取消、恢复或重复投递已正确。

建议结果记录格式：

```text
用例ID：
代码基线：
环境/镜像：
执行命令：
预期结果：
实际结果：
状态：未执行 / 通过 / 失败 / 受阻
证据位置：
```

## 10. 阅读时用到的术语

| 词 | 在本文中的具体含义 |
|---|---|
| Control Plane / 控制面 | 平台负责“谁能做、哪个环境做、用户看到什么、成果发布到哪” |
| Worker | 沙箱里长期运行的Java Agent程序，不是RabbitMQ消费者 |
| Handler | 接到一个HTTP请求后解析、校验并返回的短程序，不在里面等待整个Agent任务 |
| 受理 / Accepted | 已可靠接收这个请求；不代表执行成功 |
| 幂等 | 同一个逻辑请求重发，不会启动第二次任务或制造第二个不同结果 |
| Epoch | 一个Session执行环境的粗粒度代数；不是每次编辑的文件版本号 |
| Projection / 投影 | 根据已经发生的事件更新出来的页面查询状态，不再负责遥控每个工具 |
| Cursor / 游标 | 已读到哪里，用于断连以后从正确位置继续 |
| Readiness / 就绪 | 不仅进程活着，而且文件、状态和模型连接配置已具备接任务条件 |
| Seal / 封存 | 暂停新写入，在明确边界保存一个不再变化的工作状态 |
| Manifest / 清单 | 包中有哪些文件、多少字节、什么摘要及属于哪次Task，不是逐文件数据库状态机 |
| CAS | 只有Branch仍指向我预计的旧HEAD时才更新；冲突不强制覆盖 |
| Squash merge | 合并后的树保存为一个以目标当前HEAD为父的新提交；不创建双父Merge Commit |
| Backpressure / 背压 | 消费方跟不上时限制积压或断开慢连接，而不是无限占内存或堵住Agent |

本次文档自检的实际执行证据见07及audit/self-check.json；上表120项是完整产品验收，不与离线探针混为通过。
