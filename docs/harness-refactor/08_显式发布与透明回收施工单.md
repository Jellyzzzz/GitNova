# 最新逻辑自检与改动施工单

本文件落实用户最新确认的产品行为。它是同一重构目标的修改，不增加产品版本，也不把必须实现的发布能力留到以后。下面新增的接口、字段和状态是本次设计决定，不冒充当前GitNova已有代码。

## 1. 自检结论：可以采用，但先修正五个易出错点

**空闲不是“长时间没有用户消息”。** Agent可能仍在思考、运行测试或创建PR；没有新消息仍必须保留执行环境。心跳/SSE不算业务活动，不能导致容器永不回收。

**保存会话不等于提交仓库。** RECOVERY包保存代码、上下文、历史结果，后台回收前必须完成；PROGRESS包只为一次显式report_progress发布提供确定代码树，不能拿它当完整Agent恢复点。

**HTTP超时不等于没有Commit。** 平台受理外部副作用后，用同一operationId追踪；未知时阻止新发布和PR，不用新ID猜测重做。取消也不回滚已经确认的远端成果。

**显式发布不是取消工具框架。** 本地shell/read/edit仍在Worker内；只有真实仓库副作用走平台代理。这是有意的外部能力边界，不是恢复旧Workspace RPC。

**没有自动提交兜底。** Agent不调用report_progress就不会生成Commit；自然STOP仍可以交付回答。用户明确要求“提交/开PR”时，通过指令和验收确认工具调用确实发生；若遗漏显示实际未发布事实，不伪造成功，也不偷偷在STOP后补提交。readiness、休眠、恢复不是聊天消息。

## 2. 用户看到什么

重新打开页面只加载原有对话、实际Commit/PR与Diff；不显示环境休眠或恢复提示。继续发送时走普通消息等待状态。环境启动失败才展示“本次任务未能开始，请重试”等业务错误；不能无限等待。用户浏览历史不会唤醒Sandbox。

后台物理回收不改Session.status/workflow_state为CLOSED/MERGED，不插入“工作已完成”。PR已经合并属于真实业务事实，可正常展示原PR状态；后续不向已合并工作线发布；Session可继续发消息，W不变，显式sync才选择新H/新线，不把这种约束与空闲回收混为一谈。

开发Mac＋Windows需要两机服务都运行，这是开发机房问题，不成为产品UI/公共DTO中的主机字段。

## 3. 三条顺序（禁止重新合并）

```text
A. 自然结束
有效MODEL_RESPONSE → ANSWER_DELIVERED
→ 本地工具/子进程安全收尾、log.force → TASK_FINISHED → Worker IDLE
→ Server按原事件关联保存回答、释放activeTaskId

B. 显式发布
report_progress → durable operationId → freeze(PROGRESS)
→ POST平台operation → 查询同id直到确定结论
→ PUBLISHED/NO_CHANGES时更新对应baseline → 返回ToolResult → Agent继续

C. 透明回收
真正IDLE超时 → 后台领取回收权 → CHECKPOINT_SESSION
→ 保存RECOVERY包及全部引用/连续事件 → ACK_CHECKPOINT
→ STOP_WORKER → 销毁确认 → 以后新消息触发内部恢复
```

A不依赖B，C不能代替B。B发生在Task内的任意里程碑，可以执行多次。

## 4. 接线与调用方向

Server→Worker：沿用HTTP commands和SSE，负责启动/控制Task和后台checkpoint。

Worker→Server新增两类外部能力：

```text
POST /internal/agent/sessions/{sessionId}/operations/report-progress
POST /internal/agent/sessions/{sessionId}/operations/create-pull-request
GET  /internal/agent/sessions/{sessionId}/operations/{operationId}
```

使用与控制令牌不同用途的Session/Workline/epoch作用域能力令牌。Server从已鉴权Task/Session取得actor、从Workline取得repo/工作分支，核对当前epoch和当前attempt，模型不传这些权限字段。平台受理202与真正成功分开。已受理操作的GET在环境替换后仍可由新授权epoch或Server内部恢复流程查询，不允许旧实例借旧token发起新修改。

Server接收后持久存储operation请求，短响应202；处理程序在事务外通过既有AgentWorkerClient.downloadExport拉取固定包。Worker执行线程可等候结果，但Worker HTTP服务仍独立服务下载和取消。不要在接收POST的事务里等待下载，也不要拿本地文件锁等整段网络。

operationId在请求发送前写入Worker日志并绑定toolCallId。网络重发复用同id。operationId和commandId、eventId是不同身份；不要用模型生成的标题当去重键。

## 5. report_progress方法体怎样写

1. 校验受信RuntimeConfig.allowedTools确实授予report_progress；模型任务文字不授予权限，平台入口仍核对Session/actor/repo。
2. 查询本地pending operation；有UNKNOWN则先核对。不能从未知结果上继续生成另一次发布。
3. 分配并持久保存operationId、modelCallId/toolCallId、消息与当前工作线确认HEAD。
4. 以串行工具执行点为边界；停止/核对可能写树的后台进程。局部冻结只等**其他**写者，不能等待当前report_progress自身结束。
5. SessionSealer.sealProgress固定文件集合，生成purpose=PROGRESS的ZIP，treeDigest绑定路径/原始字节；此包不含可恢复Agent state。完成后释放文件锁。
6. PlatformOperationClient.postReport发送manifest摘要、exportId、expectedHead和message；HTTP响应只作受理。
7. 以相同operationId有限轮询/重连。服务端GET返回PENDING/PROCESSING时继续等；超出本次等待预算返回UNKNOWN，并保存pending id。禁止把它写成FAILED后再自动新建。
8. PUBLISHED：记录完整结果，原子安装本次snapshot的baseline；NO_CHANGES：确认当前baseline与已核验的树相等，HEAD不变。不对活动树重新拍一次照当作已发布基准。
9. FAILED/REJECTED/CONFLICT：返回真实错误，不改HEAD；永久失败不后台无限重试。用户/Agent修改后可以发新的明确操作，但不是为了掩盖未知结果。
10. TOOL_RESULT仍带稳定原始来源。成功返回至少status、operationId、branch、commit、treeDigest；失败仍能查看本地未发布代码。

平台提交顺序：插operation(完整固定请求摘要) → 验证PROGRESS包并归档 → 唯一publication(与operationId关联) → 固定timestamp/message/parent → 写对象 → 短事务更新Branch CAS、CommitRecord、Workline.publishedHead、publication结果、operation结果与BRANCH_UPDATED Outbox。对象写入不在事务内；同id重复处理候选SHA必须相同。

## 6. create_pull_request方法体怎样写

在Worker本地安全边界核对当前树等于confirmed baseline，没有未决发布。否则返回UNPUBLISHED_CHANGES/PROGRESS_UNCONFIRMED，绝不隐式提交。生成独立operationId，调用平台；sourceBranch与默认targetBranch由Workline绑定决定。

平台校验预期sourceHead尚未变、权限和PR范围；按现有同源/目标OPEN唯一关系创建PR或返回已有PR。将operation SUCCEEDED与新PR/已有PR引用放同一事务；重试返回原结果，不覆盖别人后改的PR内容。Dirty检查是Worker防误发布语义，不是平台授权依据。

PR可以在RUNNING的Task中创建，因此create的事务不能沿用“必须没有activeTask”的merge校验；只有merge仍要求活动Task、未决平台操作结束且没有sync gate。PR不包含本地尚未发布变化。后续report_progress更新源分支，PR跟随分支，而不是每次开新PR。

## 7. Task结束和空闲回收的准确关系

TaskFinalizer.finish仅收尾本地执行并写终态，**不负责生成ZIP、访问Server或发布**。确认无法停掉的子进程仍要BLOCKED并请求基础设施终止，不能为了摆脱等待而宣称IDLE。Worker本地可以完成回答，但Server故障时后续模型代理调用可能不可达，不承诺离线无限执行。

后台checkpoint独立于Task：IDLE且没有pending operation后先拒绝新写入，固定工作树、baseline、Context摘要、原始结果、完整日志截止N。平台耐久保存RECOVERY包后，核对SSE连续归档至少到N及快照事件自身，再ACK_CHECKPOINT，Worker PARKED、STOP_WORKER、销毁。失败时续期/保留，不能先删。

新Task与回收竞态：平台使用同Session锁。若回收已经开始，持久受理Task并预留activeTaskId，不向QUIESCING Worker投递；等待原回收完成，然后创建新epoch恢复，在就绪后创建attempt/command。不能让GET历史触发恢复，不能用两个用户客户端各建一个Worker。

如果平台已保存Task但还没有可用epoch，currentAttemptId保持null。Task业务状态PENDING_DISPATCH；环境就绪后一个短事务分配attempt并保存SUBMIT，取消先到则ABORT受理意图，不启动模型。正文与幂等键在准备过程中保持不变。

## 8. 不明副作用与恢复

没有pending operation才允许普通idle回收。异常崩溃后，先根据本地与平台operation记录核对远端结果，再允许新发布。旧epoch的新写请求拒绝；已经持久受理的操作由平台按固定身份完成或明确失败，不因重新建Worker而换ID。

RECOVERY快照里的confirmedHead必须与恢复基准一致。如果平台存在更晚的成功发布而快照更旧，不能只改head字段、保留旧文件并静默继续。先使用有对应文件树的发布包恢复代码并明确重置/截断当前上下文到可证明的覆盖，或返回RECOVERY_BASE_DIVERGED阻止自动续跑；历史仍能查看。常规透明回收在无未决操作的静止点完成，正常路径不应触发这个错误。

取消正在进行的report_progress：取消可中止等待，但平台可能已经提交。保留operationId，后台核对后归档真实结果；取消不是undo。不能因为取消而发布另一份代码或创建补偿Commit。

### 8.1 未决操作的后台核对与下一条Task

HttpPlatformCapabilities增加reconcilePending()。WorkerAssembly维护一个有界、低频的核对任务；它只GET原operationId，不创建新操作。正在运行时将已确认结果排到下个本地工具安全边界安装baseline；IDLE时取得同一短锁安装。网络请求不持该锁，停止Worker时先终止核对请求，保留pending身份。

SUBMIT.expectedPublishedHead通常必须与确认基准一致；但存在已知pending远端发布时，不得简单把请求中的新HEAD覆盖本地baseline。先核对原操作；仍UNKNOWN可让已受理Task仅开展本地工作，拒绝新的report_progress/create_pull_request，直到基准协调完成。真实缺失/冲突与正常未发布改动分开，用户不需要点击skip解除Task。

## 10. 已有文件的具体切换

WorkerHealth删除任务级WAITING_SETTLEMENT；TaskView删单条publication/settlement字段，改为progresses列表和可空unpublishedChanges。未知dirty状态返回null，不默认false。TaskFinalizer不再有acknowledge；SessionSealer独立checkpoint/ack/stop方法供后台Worker命令使用。

EventProjector在匹配当前attempt的TASK_FINISHED事务内清activeTaskId。CHECKPOINT_STORED只更新归档元数据，不清某个后来新受理Task的槽。生命周期仍用binding控制，Session身份与历史不受回收影响。

ArchiveService收包先校验purpose。RECOVERY可更新对应Workline.latest_recovery_archive_id；PROGRESS只用于有显式operation的发布，不能自动触发Commit，更不能替代RECOVERY包。一个Task可以出现多个export和多个publication；所有“按task取唯一待发布包”逻辑都删除。

前端只展示真实消息、工具进展和已确认分支/PR结果；隐藏基础设施事件，不隐藏实际失败。去掉“等待发布才能下一条”与skip按钮。平台公共GET绝不原样透出WorkerHealth、私网URL或模型凭据。

## 13. 与PR和显式同步的边界

PR merge不触发本文件checkpoint链，不检查本地W；只处理远端S并结束原Workline发布资格，Session保留。显式sync才使用MAINTENANCE checkpoint保存旧W/B/历史；三种草稿政策和新实例激活见12。不能把普通idle回收恢复成main同步。

所有请求、PROGRESS/RECOVERY包、事件与结果核对固定Q/L/epoch；完整签名在唯一reference。跨线旧操作查询只返回其原结果，不允许安装到新线baseline。sync开始前本地pending必须核对并安装到对应旧baseline，才能封存可信W/B。
