# GitNova｜统一施工手册

**唯一开发根目录：`docs/harness-refactor/`。** 本包已将Agent 00—10与协作后端11—20真正合并；reference、contracts、examples、目标DDL、验收只有一套当前定义。19是集成检查与变更记录，不是用于覆盖旧正文的补丁。

## 1. 本轮产品规则

Session是连续会话；Workline是一次基线/工作分支；Binding是实例。merge只改变远端与旧工作线的发布资格，不关闭Session，不检查或覆盖本地草稿。真正更换代码基线通过显式sync：REQUIRE_CLEAN、CARRY_CHANGES、DISCARD_CHANGES。普通空闲恢复回到原工作线，不自动更新main。

CommandType保持8种，线上schemaVersion=2。所有私有执行身份固定sessionId/worklineId/runnerEpoch；public Task只提交message与用户已看到的工作线/会话版本，不能传工具权限。report_progress是唯一Agent Commit入口；PR创建、自然回答、checkpoint彼此独立。

## 2. 你现在从哪里写

**交付目标是完成整套已约定的Harness重构，不是最小版、演示版或MVP。** 分阶段只决定先实现什么、何时验证，不减少功能、异常处理或验收范围。完整交付包括：Core执行与模型网关、本地工具及进程管理、日志与结果存储、跨执行Context、Worker命令/取消/事件协议、Sandbox与平台接线、回答展示、显式发布、约定范围内的恢复、旧执行链退役及端到端验收。通用PR、同步与协作后端保留在整体产品计划中，按已有依赖顺序继续完成，不因当前先写Harness而删减。

某条正常路径跑通只表示该项实现取得进展。该模块的失败分支、资源关闭、并发边界和恢复验证仍须完成，不能统一改称“后续完善”；尚未完成的项目必须明确列出。

截至本次文档调整，生产目录已具备模块骨架、AgentCommand与ProtocolJson；Core/Worker尚未实现。已写协议保留，但不继续把完成全部协议类型作为进入Core的门槛。现在从02的“当前实际施工顺序”和步骤3开始；不先写社交功能，也不执行目标DDL。

执行路线：**基线与模块 → 步骤3 Core执行链 → 步骤2/4/5本地存储、工具、Context及真实模型 → 步骤6—8 Worker协议与生命周期 → 步骤9—12沙箱/平台接线 → 回答展示、显式发布与恢复 → 旧执行链退役及完整验收。** 编号保留作职责索引，不代表必须先写完全部步骤2才能开始步骤3。各阶段完成标准见02和03，不能把第一条循环当作Core或整体重构已完成。

不要把文件名数字当唯一依赖：12的同步必须等13的三方合并器与Agent安装器可用；15的Outbox表和事务写入端口要在PR落库前可用，MQ消费者可在之后接入。同一产品的施工顺序不是分版本交付。

### 当前先完成Harness，不把协作后端当成前置

当前先实现**可脱离平台运行的Core，再接Worker**。Task正文始终保留原文；Worker为本次执行绑定Writer、Control和获授工具，再把原文或ModelTypes.Message(USER)交给Core。不新增TaskInput，Core不接平台Task/Attempt、不解析AgentCommand、不查COMMAND_ACCEPTED来取得输入。文件读取/搜索通过shell调用cat/sed/rg是实现方式的选择，不是省略文件能力；必须实际完成路径处理、输出限制、来源记录和错误反馈。专用read_file按稳定分页、行号或独立读权限的需要选用，不以增加一个同名Java类作为能力完成标准。完整实施路线见02；输入边界见05第2.5节。未接通的发布/PR能力不加入生产allowedTools，其真实接线仍是约定交付内容，不用Fake冒充成功。

每步先读02新增的“行为与数据流”，再按该段“动手顺序”打开需要的文件。05集中说明字段来源、静态校验与运行时校验；reference只给精确类型。你应能从当前步骤回答：入口是什么、每个输入谁赋值、输出谁消费、哪一步产生副作用、失败后留下什么。

不要一次复制全部模板，也不要等当前步骤每个未来类型都齐了才编译。按一条调用链的直接依赖集合编译、运行、补失败分支，再继续本步；完整放行条件不减少。可先写业务代码再补测试，但写代码前至少明确一个正常输入和一个失败输入的预期结果。查API、讨论取舍是正常学习；基本字段和接线若仍需靠聊天补齐，应修正文档，而不是让开发者猜。

## 5. 安全导入

1. 解压本包到临时目录，先运行 `python3 scripts/self_check.py`（在包根）。它只检查本包，不修改项目或数据库。
2. 在真实仓库先运行git status，明确备份当前文档与新写代码；不要无选择地git add全部目录。
3. 运行 `python3 <包根>/scripts/import_docs.py <仓库根>` 查看dry-run；确认目标仅是docs/harness-refactor后，传`--apply`。旧目录在仓库外生成有时间戳的备份，新目录从完整包复制，失败会尝试恢复；绝不merge两棵半旧文档树。
4. 仅审查文档diff并提交。**reference中的Java是签名参考，不会自动复制到src；SQL不执行；不自动切分支或git commit。** 你已经写的协议类型手工按19核对。
