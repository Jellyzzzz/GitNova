## 本次设备安排与两条可分别推进的工作线

**默认双机开发布局是本文的部署选择，不是软件架构变化：Mac 编写代码并调试 GitNova Server；Windows 32G 机器承载 WSL2、Docker Desktop 的 Linux Engine、OpenSandbox 和 Agent Sandbox。** Windows 按用户提供的 Intel/x86-64 信息使用 `linux/amd64`；先用06的命令核实。双机不意味着两个业务Server，各设备浏览器必须连接同一个平台地址。

| 工作线 | 现在可以做什么 | 何时必须汇合 |
|---|---|---|
| Java手写线 | 步骤0冻结真实worktree；步骤1—8按顺序编写协议、Core、Worker、初始化与封存 | 步骤9把真实Worker放进已验证的Windows环境 |
| 环境准备线 | 现在即可按06安装Windows执行宿主、启动OpenSandbox，用随包独立探针验证Mac→Sandbox与Sandbox→Mac | 不能替代步骤9的真实Worker、身份、卷、模型代理和连续Task验收 |

不必等Agent写完才发现跨机路由不通，也不必等Windows全部配置好才开始纯Java契约/单元测试。基础设施探针不调用真实模型、不读取生产仓库、不要求MySQL、AgentCore或生产Worker已经实现。它使用专用测试Sandbox与测试卷，不是新增的产品版本。

**Mac在默认布局中还承载Server与Model Proxy：关浏览器不会取消任务，但Mac睡眠、断网或关掉Server会切断控制/模型入口。** 需要“Mac合盖后Windows继续完整运行”时，按06将同一个Server、数据库连接与模型代理也部署到Windows运行端；不是另建一份用户Session，也不是只启动Windows的Docker就自动实现。执行中的会话不做无准备的跨部署热迁移。

## 第一小时应该做的事

先将本文件夹放到GitNova仓库的 `docs/harness-refactor/`，保持目录结构，不把reference源码自动覆盖到生产源码。

在仓库根执行：

```bash
python3 docs/harness-refactor/scripts/inventory_current.py . \
  --output docs/harness-refactor/audit/local-source-inventory.json
```

检查未映射文件、本地自然STOP实现、最新Flyway编号和真实前端入口。旧源码地图固定到316112a；用户给出的自然STOP新行为已写成迁移契约，但未提交worktree没有被远程工具读到。因此步骤 0是实际基线对齐，不是让你重新设计架构。

随后执行文档自检（需要JDK21；JSON Schema检查需要Python jsonschema）：

```bash
python3 docs/harness-refactor/scripts/self_check.py
python3 docs/harness-refactor/scripts/check_dual_host_docs.py
```

这个检查编译的是随包接口参考和独立探针，不是尚未手写的整个产品。探针使用本机loopback临时端口和临时目录，不连接你的模型账户，不访问项目数据库。Linux进程探针在Windows的WSL2/Linux环境执行；不要为此在内存不足的Mac再启动Docker。Mac上的纯Java与通信检查可以先执行，涉及Linux的检查不能伪标通过。

## 构建与文件放置

`deploy/agent-parent.pom.xml` → `agent-runtime/pom.xml`；其余三个POM分别放到同名模块。Server根pom仍然是现有应用，不改成聚合父工程。Server只依赖protocol和所需基础设施SDK，不依赖agent-core/worker。

`reference/`中的31个Java文件提供明确字段和接口，其中少量纯本地辅助类给出参考实现。它们不是可交付的成品Agent，也不含编译通过就假装工作的空业务方法。缺失的业务body按02手写；不得把test FakeFinalizer或ProbeWorker打进正式发布。

`schema/agent_control.sql`是需要审查后应用的新DDL。先在库副本运行；使用install_migration.py只创建新的Flyway文件，不修改旧migration，不直接连接数据库。

`probes/opensandbox/`有一个真实SDK接线探针；其API已按固定tag核对，但当前环境未下载SDK编译、未运行Docker。具体命令和检查项在06。双机地址与环境检查现在就可以提前做，生产接线仍按步骤9验收。

## 如何使用“阶段性完成”

每个步骤的通过只表示该步骤可接到下一步，不是宣布一个缩水产品已交付。步骤 6的HTTP可以用假Engine测试，步骤 9的环境可以用独立探针测试；直到Context、本地工具、封存、发布、PR、恢复和旧路径退役均完成，才到最终交付。

## 本包的边界

本包完成的是架构/施工层补全与静态、隔离探针自检。真实GitNova实现、OpenSandbox代理/卷/销毁、MySQL迁移、原实验回归均需按文档实际执行；不能拿本包的PASS替代这些验收。工期不以文档页数估计，遇到实测失败按明确错误分层定位，不靠继续堆新组件解决。

施工顺序已根据依赖自检修正：**步骤8先完成Worker初始化/封存，再在步骤9接OpenSandbox，步骤10接平台Session，步骤11接任务/事件/归档**。不会在需要初始化时才发现关键实现还留在后面。
