# 13｜PR与代码讨论：从输入到事务的施工单

## 1. 不从表开始，先画四个对象

PR是“希望把源分支已发布的变更合入目标”的请求，不是沙箱状态。给定共同祖先O、源S、目标T，审查Diff是O→S，合并候选是merge(O,T,S)。Sandbox的W不作为通用PR输入。

`pull_request`保存业务身份；`pull_request_revision`保存不可变源版本；`pull_request_comment`保存讨论及固定代码锚点；`pull_request_merge`保存一次用户合并意图和确定结果。命名仍用当前Spring/MyBatis风格，字段说明在16，逐列类型以schema/target.sql.reference及其生成字段表为准。

## 2. 施工卡 P1：树读取与纯Diff

**复用**：CommitObject.mapping、GitObjectCodec、ObjectStorage。`service/repository/CommitTreeService.java`已有则补方法，没有则按旧02步骤10先建。不能把GitNova对象直接丢给JGit Repository假装是标准.git。

**新文件**：`service/pullrequest/CommitCompareService.java`，辅助数据作为该类record或 `PullRequestTypes` 嵌套类型。

**输入**：repoId和两个确定Commit，或O/S/T三个确定Commit；不是动态branchName。**输出**：文件路径、ADD/DELETE/MODIFY、old/new blob、二进制标记、受限文本片段、truncated及明确继续读取位置。

**第一步思考**：同一路径hash相同意味着这次无内容变化；path只在一侧分别是新增/删除。先把两棵mapping的path并集分成四种情况，写成测试表，再实现循环。不要一开始就写文本行diff。

**实现**：读取并验证固定Commit→验证仓库归属/可达性规则→mapping按规范化路径排序→逐path分类→按需读取变动blob→文本产生行diff、二进制只元数据。缓存键含repoId/O/S/T和算法版本，不含“main”作为唯一key。响应大小和每文件读取上限有配置；大文件不是假装空差异。

祖先沿单父链找：把S的祖先身份放集合，再从T向父走，首个相交为O；visited防循环、最大深度防坏对象、没有祖先明确UNRELATED_HISTORIES。不默认拿Session.baseCommit代替O。

**测试**：target独有文件不出现在O→S里作为删除；UTF-8/CRLF/无末尾换行；二进制；大文件；路径非法；没有共同祖先。**查**：GN1/GN2/GN3；`merge base three dot comparison`；JGit `DiffAlgorithm/RawText`，见17。

## 3. 施工卡 P2：创建PR

**文件**：`entity/pullrequest/PullRequestRows.java`（POJO集合）、`mapper/pullrequest/PullRequestMapper.java`、`service/pullrequest/PullRequestService.java`、`controller/PullRequestController.java`。PR行不放ControlRows，Server DTO不进入agent-protocol。

**请求**：sourceBranchId、targetBranchId、title、body、draft、requestKey；author从认证取得。**输出**：PR id、仓库内number、当前版本及固定S/T。允许无差异Draft，非Draft无差异返回NO_CHANGES；merge从来不能把空差异当有新代码。

**思考**：请求键解决同一次点击重试；活动分支对唯一约束解决两个人用不同键同时创建。两者不是一把钥匙。先写这两个测试再建业务体。

**处理顺序**：参数和当前权限初检→短事务锁repository→按(actor,repo,requestKey)查原请求摘要→核对source/target存在且不是同一分支、非受管target→锁两分支固定S/T→校验Draft规则→分配仓库内number→插PR与首revision→同事务写PR_OPENED Outbox→提交。O和Diff昂贵时事务外先算，以事务内HEAD不变为前提，否则返回409刷新；不持锁读取整仓库。

活动唯一性：推荐 `(repo_id,source_branch_id,target_branch_id,open_slot)` 唯一索引，OPEN含Draft时open_slot=1，其他状态NULL。用使用目标SQL已规定的生成列，不在实现时另选手工open_slot方案。PR编号用repo_counter中同repo行锁自增，不能MAX(number)+1无锁。

重复键命中：同请求返回原PR；不同请求但同活动分支对，返回PR_ALREADY_OPEN及有权看到的existingId。数据库异常不是“已经存在”，不要catch所有异常返回成功。

**查源码**：OneDev `PullRequestResource.createPullRequest`→`DefaultPullRequestService.open/findOpen`。只借校验和持久化责任，不搬Issue/审批/CI。**测试**：不同用户并发创建、同键不同正文、非法目标、撤权、无差异Draft、删除后重建同名分支不混为旧branchId。

## 4. 施工卡 P3：源版本与当前详情

**重要区分**：PR.version用于标题/状态等并发编辑；source revision记录代码证据。target前进并不等于source有人新增代码，两种变化不能混成“revision++”。

采用有限异步投影：BRANCH_UPDATED事件携带稳定branchId、before/after、repoSequence。`PullRequestRevisionProjector`只给事件发生时已创建、且事件序号不晚于该PR合并截止点的来源PR建立版本记录。CLOSED期间仍可记录源变化供重开后查阅；已MERGED后的新源提交不追加到旧PR。创建序号和merged_repo_sequence用于固定范围。唯一 `(pr_id,source_branch_id,repo_sequence)`；重复消费不重复增加。晚到旧事件不把currentSource指针退回去，不按消费时读取的当前HEAD伪造历史。

**当前权威读**：detail/compare直接读repository里source/target当前HEAD。revision消费者暂停时仍能正确展示当前S/T，返回`historyProjectionPending=true`，不偷偷在GET创建新PR业务记录。diff的viewToken绑定(prId,prVersion,O,S,T)；行评论自己保存确定提交锚点，不依赖“最新revision行一定已经投影”。

历史revision保存sourceHead、targetHeadSeen、comparisonBase（可待计算）、sourceSequence；它不是merge授权。计算base缺对象明确标失败可补算，不用当前T冒充历史target。事件本身携带最初source更新的时间和版本；目标在事件时的HEAD若未采集，targetHeadSeen可空，不能造一个当时不存在的值。

**第一项测试**：暂时停止投影，source已从B推到C，详情显示C、merge只接受C，历史列表允许说明索引待更新。再倒序投递B/C事件，最终历史不丢、当前读不倒退。

**查**：OneDev `DefaultPullRequestUpdateService.checkUpdate`；Gitea `PullRequestSynchronized`；`idempotent projection out of order event aggregate sequence`。

## 5. 施工卡 P4：普通讨论、固定版本行评论

**请求**：body、requestKey；普通讨论anchor为空。行评论额外携带viewToken/O/S/path/side/lineStart/lineEnd；replyTo可空但只允许回复同PR已有评论。`resolved`作用于线程根；不做无限嵌套树。

**输入验证**：重新检查PR读取/评论权限；普通评论当前有读权限的登录用户可发；正文上限；Markdown输出必须净化，不直接信任HTML；author不能由payload指定。行锚点必须实际出现在对应确定Diff的允许范围；LEFT对应O，RIGHT对应S，不用当前文件行号替代。

**逻辑**：解析→读确定Diff核验锚点（事务外）→短事务重新核对资源存在、权限、requestKey→插评论→写PR_COMMENTED事件（仅新评论/回复）→提交。源HEAD后来变化，旧评论仍指向旧S并显示过时标记，不自动搬到新行。一般讨论不因代码变化过时。

**修改/删除**：作者可改自己内容，仓库owner可删除违规内容；带commentVersion条件更新。删除改为tombstone以保留回复结构，读取不显示旧正文。通知主体只保存commentId，读取时查当前可见内容，避免删除后仍泄漏正文。resolve只作者或仓库写者可做；代码新版本不继承“已审查通过”，本次没有正式approval对象。

**测试**：未知path/越界行/伪造author拒绝；重试仅一条；跨PR reply拒绝；源更新后旧锚点不挪；HTML脚本不能执行；删除父评论回复仍可读。

**查**：`review comment commit_id side line original_line`；`Markdown HTML sanitization OWASP`；不认识库时沿项目现有前端渲染器先查安全配置，别新引两套。

## 6. 施工卡 P5：三方树合并器

文件 `service/pullrequest/ThreeWayMergeService.java`。输入三个不可变Tree：base、ours、theirs；输出完整候选Tree或Conflict列表。它不访问数据库、不更新分支、不创建Sandbox；只读内容可按blobId从不可变存储按需取，单元测试注入假读取器。唯一Tree/MergeCandidate签名在contracts/component-methods.md第4节。PR调用ours=T/theirs=S，同步调用ours=H/theirs=W。

先逐path处理，缺文件用显式ABSENT值，不用空字符串代表：

| 条件 | 选择 |
|---|---|
| ours == theirs | 该内容（都不存在则删除） |
| ours == base | theirs，包括新增/删除 |
| theirs == base | ours |
| 两边均不同于base | 进入文本三方合并或冲突 |

双改文本：以保留原始字节为前提尝试JGit MergeAlgorithm；检测NUL/非法UTF-8、混合换行等不能可靠往返的输入，返回冲突，不悄悄变编码。新增/新增不同内容、删除/修改、二进制双改明确冲突。当前没有rename检测，按旧路径删除+新路径新增处理；不能据此声称智能重命名合并。

输出Tree需要检查目录/文件前缀冲突，例如一边添加 `a` 文件，另一边添加 `a/b`；必须冲突，不生成不可物化树。控制每文件大小、总路径数和合并耗时。普通文本不同区域修改应自动合并；冲突只生成临时可查看证据，不写目标branch。

**第一次实验**：三个小文本，base两行，ours改第一行，theirs改第二行，得到同时保留的候选。再做两边改同一行的反例。随后加文件级并集分类、字节限制，再接业务。

**查**：JGit `MergeAlgorithm.merge(RawTextComparator.DEFAULT, base, ours, theirs)`、`MergeResult.containsConflicts`、`MergeFormatter`；先用当前Server JDK兼容的固定版本在小测试里验证真实签名，不猜SDK。包版本锁定是H0工作，不要求升级整个Spring。

## 7. 施工卡 P6：合并意图、固定候选和短事务

入口 `PullRequestApplicationService.merge` 统一普通/受管来源；`PullRequestService`处理通用PR事务，Agent来源的业务资格由上层协调检查，不能让公开入口绕过。

**请求**：mergeId（或Idempotency-Key映射）、prVersion、sourceHead S、targetHead T、strategy=FF_OR_SQUASH、message。**输入事实**是用户实际看过的版本。**结果**是确定mergedCommit M或明确冲突；不能以HTTP超时推导失败。

**阶段一，持久意图**：短事务锁repository→关联Session→Workline/Binding（仅受管来源）→PR→分支(id升序)，查原mergeId/摘要，核对PR OPEN且非Draft、权限、source/target是S/T、无受管target；受管来源无活跃Task/未决操作时允许准备，不检查W。写PREPARING及固定R/S/T/时间/作者/提交说明；释放锁。

**阶段二，候选**：事务外读O/T/S。若T是S祖先，快进到S；若S已被T包含或最终目标Tree不变，返回NO_CHANGES不伪造新提交；否则三方合并并生成单父parent=T的squash候选M。重试使用阶段一固定元数据，因此候选SHA可重现。对象先写安全存储；本次关闭在线对象GC，DB未提交的候选不能被并行清理。停写离线清理必须遍历进行中意图及历史根。

**阶段三，提交**：重新锁相同顺序，核对原意图/权限/R/status/S/T；再次核对受管Session没有新Task/未决操作。CAS target→S或M、CommitRecord、PR MERGED与mergedFromHead/mergedCommit、merge结果、PR_MERGED/BRANCH_UPDATED Outbox，同一MySQL事务提交。Agent来源只把Workline发布资格标为MERGED，Session仍OPEN；不发STOP、不换W、不等checkpoint。

准备后Task抢先进入可让最终检查返回409，避免锁住整个模型任务。也可以应用层短期merge gate阻止新Task，但本包选择**最终重检并冲突返回**，不新增长时间维护租约。已经接受的平台发布同理先核对到确定结果，不复用mergeId自动吸收新S。

**HTTP丢失**：GET mergeId或重发原请求；SUCCEEDED返回同M。不重新取main、不再次生成时间、不再次调用模型写message。若原请求终态FAILED，修正后用新mergeId表达新意图。

**查源码**：Gitea `recordMergeIntent/hasPullRequestCommitBeenMerged/doMergeAndPush`；OneDev `merge/checkMergePreview/updateRef(expectedOld)`。本项目DB与文件系统不在同一事务，原子性声明仅覆盖MySQL中分支可见性及业务结果。

**测试**：source/target准备后改变；两次merge；撤权；对象保存后DB回滚；事务提交后响应丢失；有草稿W但无活跃任务可合并且W不变；普通PR在Sandbox全关时可merge。

## 8. 施工卡 P7：状态修改与删除

PR状态OPEN/CLOSED/MERGED；draft是OPEN上的独立布尔。Ready不代表审核通过；close不删分支或Sandbox；reopen核对两分支存在、活动分支对唯一、PR未MERGED，必要时更新当前比较信息；已MERGED不能重开。

close事务同时保存当时的source/target HEAD；源版本投影尚未追平也不能漏掉这个历史证据。分支仍在时允许显示当前比较；分支已删时CLOSED详情使用closed_source_head/closed_target_head，MERGED详情使用merged_*，不再查询同名新分支。comparisonBase可由固定两个HEAD按需计算。

`PATCH title/body/draft`、close/reopen带prVersion与requestKey；评论修改/删除/resolve同样带key和commentVersion。它们通过pull_request_mutation保存回执，避免关闭成功后已被重开、旧关闭请求重发又把它关闭。先查同actor/pr/key的固定摘要与已保存结果；命中返回原结果，不重复改状态/发事件。新请求的状态更新和mutation结果、Outbox处于同一事务；影响行数为0回滚并409。mutation不是新的执行调度器，仅是一条已经完成的用户写操作回执；错误请求不伪造成功回执。状态变化写业务事件；普通标题编辑不必触发全员通知，明确在15白名单中取舍。

源分支OPEN PR默认禁止删除；要求显式close之后再删。MERGED/CLOSED的PR必须保存确定提交引用，仓库GC不能删除这些历史引用；分支名同名重建是新branchId，不能让旧PR自动指向新分支。PR/Revision/Workline保留被删分支的旧ID作为历史引用，不用ON DELETE SET NULL抹去异步事件匹配条件；即使关闭后的旧BRANCH_UPDATED稍后才到，仍能按原身份入历史。目标删除同样不得使OPEN PR悬空，默认先关闭相关PR；批量处理需单独显式入口，普通删除只返回受影响PR摘要。

## 9. 施工卡 P8：页面与API联调

列表、详情、文件列表、Diff、讨论、Draft/Ready、关闭/重开、merge都是通用仓库页面，不放在Agent专属页面目录作为唯一入口。Agent回答中只是链接到相同PR页。

前端拿详情返回的R/S/T/viewToken发写请求；409保留输入并提示刷新，不能自动用更新的S/T再次merge。合并确认文字说明只合并远端已发布代码；未发布草稿不会被覆盖，也不会自动包含。合并后留在PR详情或原Session，代码续作入口发12的显式sync。

Codex可写组件，但你用浏览器网络记录验证：只有一次业务写；刷新不重做；私有PR不能通过改URL读取；Diff大文件有截断提示；旧评论版本来源清楚。

## 11. P3投影的派生事件与P6最终检查

`PR_SOURCE_UPDATED`有且只有一个产生位置：PullRequestRevisionProjector在成功插入源版本的同一事务写派生Outbox。`eventId`用固定命名空间和原eventId+prId+类型确定，`causationEventId`指向原BRANCH_UPDATED，`scopeKey=pr:<id>:source`、`scopeSequence=原repoSequence`；接收人计算仍使用原事件occurredAt。它不获取repository计数锁，不伪造消费时间的HEAD。投影事务锁receipt→PR即可，之后不反向获取repository/Session；若遇到PR并发写，等待或回滚重试。

source更新可能在读取候选后发生，因此无论历史投影是否追平，最终merge都从Branch当前行锁再次确认S/T；不能拿PR.currentRevision缓存证明源没变。关闭/合并时固定当次HEAD和repoSequence，延迟事件按序号归属，source同名重建的新branchId永不进入旧PR。

受管PR在准备阶段只做资格初检，不持有贯穿候选计算的Session维护租约。最终事务必须再次检查activeTaskId、sync_operation_id、旧线未决平台操作和Workline ACTIVE。其间新Task获准运行，最终merge返回BUSY/409是正常竞争结果，不取消用户任务强行完成merge。无论从页面、Agent能力或内部调用，都使用相同PullRequestApplicationService/ManagedBranchPolicy入口。

评论和状态写入幂等：创建评论按requestKey固定；修改/删除评论带commentVersion。close/reopen/draft等使用pull_request_mutation回执，不因一次旧close请求重试把后来重开的PR又关掉。mutation收到重复时先检查actor/摘要，返回原结果，不再执行当前状态转换。
