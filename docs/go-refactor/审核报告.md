## 会影响重构的发现

### A1：Agent 完整循环尚未形成，必须计入开发成本

证据：[Loop](/Users/zhaoguodong/code/GitNova/agent-runtime/agent-core-ts/src/agent/loop.ts:87) 的批量执行方法仍在编辑；[Session](/Users/zhaoguodong/code/GitNova/agent-runtime/agent-core-ts/src/agent/session.ts:99) 只有私有生命周期方法，尚无 public prompt/run 接线；[CLI](/Users/zhaoguodong/code/GitNova/agent-runtime/agent-core-ts/src/cli.ts:69) 调用一次 Gateway 后执行工具，并未把结果交回下一次模型。

审核时 `tsc -p` 返回 TS1472（Loop 中未完成的 try）。这是当前 WIP 状态，不是对用户最终实现的缺陷结论。即使语法恢复，仍需要运行入口、循环终止、历史、取消与上限的功能验收。方案为此单列 16 小时。

### A2：旧 Agent HTTP、Worker、数据库表不能合并称为“已有 Agent 后端”

证据：[README](/Users/zhaoguodong/code/GitNova/README.md:10) 明确旧执行链退役；[页面](/Users/zhaoguodong/code/GitNova/src/main/resources/static/index.html:69) 显示 Agent 不可用；`agent-runtime/agent-worker/src` 下无 Java 生产文件，但 [POM](/Users/zhaoguodong/code/GitNova/agent-runtime/agent-worker/pom.xml:6) 仍声明 `AgentWorkerMain`。

Session/Task/Run/Workspace/Step/Outbox 实体和 Mapper 在，没有对应活跃生产 Service。新 Go 接线是实质工作，不是换掉 Spring 启动类。

### A3：标准 Git 替换改变权威存储与事务边界

证据：[CommitObject](/Users/zhaoguodong/code/GitNova/src/main/java/com/gitnova/gitobject/CommitObject.java:9)、[GNOV 编码](/Users/zhaoguodong/code/GitNova/src/main/java/com/gitnova/gitobject/CanonicalGitObjectCodec.java:33)、[TransferService](/Users/zhaoguodong/code/GitNova/src/main/java/com/gitnova/service/TransferService.java:88)、[旧存储目录](/Users/zhaoguodong/code/GitNova/src/main/java/com/gitnova/storage/ObjectPathResolver.java:21)。

旧对象不能直接移动进标准 `.git/objects`。用户确认只有测试数据，所以不需要转换历史。新方案只让 Git 持有 Ref；PR 操作要处理“Git 成功、SQL 失败”的恢复，不能把 `@Transactional + branchMapper` 逐句改写成 Go 事务。

### A4：授权缓存与主页可见性不能照搬

证据：[RepositoryAccessService](/Users/zhaoguodong/code/GitNova/src/main/java/com/gitnova/service/RepositoryAccessService.java:22) 的成员 TTL 为 5 分钟，私有读取接受缓存；[列表 SQL](/Users/zhaoguodong/code/GitNova/src/main/java/com/gitnova/mapper/RepoMemberMapper.java:14) 只按成员查询且不分页；当前所有 `/api/**` 默认要求登录。

目前没有成员管理 API，不能声称已在真实撤权链路上复现泄漏。但若直接继承这种缓存到新增成员/私有主页业务，就不能保证立即撤权。新方案使用 SQL 当前 ACL 过滤后分页，viewer 与主页 owner 分离；公开读取使用可选认证。

### A5：仓库创建/删除与原生目录生命周期需要补齐

证据：[RepoService](/Users/zhaoguodong/code/GitNova/src/main/java/com/gitnova/service/RepoService.java:33) 仅建元数据和 owner；删除仅删成员与 repository。旧 `agent_session` 外键可能阻止有关联会话的删除；旧 branch/commit_record 没有随删除清理。

新实现需要 CREATING→READY/ERROR 和软删除。对象目录初始化不能被当成数据库事务里的可回滚操作。旧测试只证明授权调用顺序，不证明带实际关联数据的删除正确。

### A6：认证 WIP 和测试契约不同；不把这些失败当成必须修完 Java 才能开 Go

证据：[JwtUtil](/Users/zhaoguodong/code/GitNova/src/main/java/com/gitnova/util/JwtUtil.java:32) 已改为 sub=userId；[拦截器](/Users/zhaoguodong/code/GitNova/src/main/java/com/gitnova/interceptor/JwtInterceptor.java:56) 调用 `verifyAndGetUserId`。但 [旧测试](/Users/zhaoguodong/code/GitNova/src/test/java/com/gitnova/interceptor/JwtInterceptorTest.java:32) mock `parseToken` 并期待用户名；Workbench 的认证 mock 同样未适配。

原树 87 项 Java 单测有 2 失败；同 HEAD 的干净 Go 树 87/87 通过，说明当前基线与 WIP 应分开描述。Go 从明确后的身份契约开始写测试即可。

### A7：HTTP 错误与输入约束需要统一

证据：[AuthService](/Users/zhaoguodong/code/GitNova/src/main/java/com/gitnova/service/AuthService.java:45) 返回 `ApiResponse.error`，Controller 通常仍为 HTTP 200；密码上限按字符设为 100，而 BCrypt 的输入边界需按字节处理；并发注册/创建的唯一冲突未专门映射。[通用异常处理](/Users/zhaoguodong/code/GitNova/src/main/java/com/gitnova/config/GlobalExceptionHandler.java:91) 将内部异常 message 拼给客户端。

新 Go Handler 返回正确 HTTP 状态、稳定错误码、公开错误信息；唯一约束作为最终防线。这里迁移规则，不逐项修理即将退役的 Java 实现。

### A8：当前 Bash 是本地工具，不能直接当隔离执行器

证据：[Bash](/Users/zhaoguodong/code/GitNova/agent-runtime/agent-core-ts/src/tools/bash.ts:63) 传整个 `process.env`，工具直接启动本机 Bash；[OutputCollector](/Users/zhaoguodong/code/GitNova/agent-runtime/agent-core-ts/src/tools/output-collector.ts:43) 截断显示后继续将完整输出落临时文件，尚无总磁盘上限。

云端接线前将工具绑定到独立容器，并限制环境、挂载、执行时间、输出总量。模型凭据留在可信 Host。取消必须回收容器内实际执行，不能只杀死宿主的 `docker exec` 客户端后宣称停止。

### A9：旧评测结果与当前产品链不是同一份实现

证据：[旧 live client](/Users/zhaoguodong/code/GitNova/evaluation/context-large-output/live_client.py:117) 仍调用已移除的 Agent Session 路径；其他 runner 使用 Java JAR/Gitlet CLI。前端测试将 API 全部 mock，因此通过也不能证明新后端贯通。

保留任务样例、验收器和原始结果；为新链路重写驱动后再测。简历不把历史 Java 指标写成 Go/TS 指标。

### A10：Go 标准 CGI Handler 不是无条件可用的 Git 网关

本地 Go `net/http/cgi/host.go:118` 直接拒绝 chunked 请求；226 行直接构建 `exec.Cmd`，并非 `CommandContext`。标准 Git 客户端的网络请求大小与传输形式必须纳入验收。

方案采用参考 Gitea 的固定 Smart HTTP 适配，把协议流交给 Git 原生 upload-pack/receive-pack；测试取消、gzip、流式上传与 MIME，避免围绕标准 CGI 的限制重新堆补丁。这里仅完成源码核查，未实现或验证新的 Go HTTP 网关。

## 结论对排期的影响

1. 原生 Git 可以替代当前自研底层，但用户/权限/HTTP/数据库/前端适配仍需重写。
2. TS Gateway 和工具是可用资产，完整 Agent 是待完成工作；不能把整月排成 Go CRUD 后最后一天接 Agent。
3. 没有历史数据迁移需求，直接使用独立数据库与裸仓库根，可以省掉双写和对象转换项目。
4. 旧文档规模远大于当前活跃系统，不把它们全部搬成 Go。本月只围绕能够证明后端开发能力的实际链路分配 120 小时。
5. 用户仍在手写的 TS 文件应先完成再按选定路径提交到 Go 分支；此次材料没有覆盖这些代码。
