按本次 MODEL_CALL_STARTED 中记录的 fixedTokens=1,956，代码实际计算为：

```text
inputLimit    = 32,000 - 1,024 - 2,048 = 28,928
dynamicBudget = 28,928 - 1,956         = 26,972
useRatio      = (estimatedInputTokens - 1,956) / 26,972

80% 摘要触发：estimatedInputTokens >= 23,534
90% 后续处理：estimatedInputTokens >= 26,231
```

阈值依赖当前请求的估算，不是 Run 累计消耗，也不是简单的 32,000 × 80%。
固定内容变化时这些数值也会变化。不开摘要的 A/B 不执行 80% 分支，但仍执行 28,928 的输入上限检查。
本轮没有触发摘要或更强压缩；不把配置存在等同于相关处理已执行。

## 轨迹与质量观察

### A：重复读取导致的成本放大

先读取 CSV 第 1–80 行，随后连续 6 次请求同一文件第 80–161 行。
返回均为 SUCCESS，range/totalLines 正常，没有工具错误；这些重复内容持续进入上下文。
最终 applyPatch 修复两个 Policy，第二次运行公开测试全部通过；随后输入上限阻止继续调用模型。
本轮只记录行为，未加去重或 no-progress 处理，不替换这个失败样本。

### B：外置生效，仍有原文回读

两次 runCommand 的输出各外置一次。模型分两次读取首次日志的 Artifact，随后修复、测试、检查 diff 并完成。
尽管回读有成本，这条执行轨迹最终仍处在预算内，没有摘要调用。

### C：摘要配置开启，但完整任务未达到阈值

只有 9 次模型调用，已发送请求估算峰值 20,708、动态占比 69.52%，低于 80%。
因此没有 CONTEXT_SUMMARY_RESULT/CREATED，也没有摘要费用。
不能把 C 相比 A 的差异解释为摘要算法改善：两者实际都没有摘要，执行路径却不同。

### D：同样未触发摘要

两次外置、两次 Artifact 回读，另调用一次 searchText，最后正常结束。
折扣使用 BigDecimal + HALF_UP，运费按折后小计计算；不同于其他样本的整数公式，但独立测试通过。
动态占比峰值只有 54.71%，摘要没有触发。

报告措辞仍有一个证据边界：D 用 searchText 搜索 Workspace 中的 `FAIL`，命中 README 和测试源码。
这不能验证 stdout 是否有 FAIL 行，因为命令日志不在搜索范围内。真实 stdout 确实无失败行、exitCode=0，
但“已用文本搜索确认日志”不是有效的证据归因，不能因为 finishTask 通过就认为自然语言说明全部严格。

## 结论限制与下一步

这次不能再沿用“仅摘要最省”的排序：B 的样本消耗最低，但 C/D 没有运行摘要，差异主要混合了执行轨迹变化。
也不能直接对比 18k 与 32k 并把差异都归给窗口，因为摘要阈值同时从 60% 改为 80%。
temperature=0 不意味着此次实验能控制供应商内部路由、缓存或得到完全相同的工具选择。

若继续验证摘要，需要固定策略后使用自然更长、会达到 80% 的真实任务；若测稳定成本，应对相同配置重复采样。
不通过强制调用摘要、插入填充文本、只保留成功 Run 来制造效果。
下一项直接暴露的优化候选是相同读取的重复注入/no-progress，但它应单独实验，不能混进本轮。

原有 Workspace generation 持久化缺口仍在：工具观察已为 1，数据库行仍为 0；本轮没有修复或验证重启恢复。
本报告不证明跨 Task 记忆、长期摘要质量或供应商 1M 窗口下的效果。
