# 场景 2：真实 HTTP / DeepSeek / Docker 四组对照

## 结论

四组都真正执行了：HTTP 创建 Task → MySQL/Outbox → RabbitMQ → Worker → Runtime → DeepSeek → Docker。
四份最终代码都通过 160 个公开用例和 2,125 个独立用例，且仅修改两个允许的 Policy 文件。
但只有 C 组完整走到 `finishTask → FINISH_SUCCEEDED`；“代码正确”不能和“Run 完整结束”混为一谈。

本轮不支持“同时开摘要与外置一定更省”的结论。B 的全量回读抵消了外置收益，D 又遇到未能分类的网关异常。
这是每组一次的探索性实验，不是统计显著结论；尤其不能拿提前停止的组与完整完成的组直接计算节费率。

- 仓库：repoId=16，云端基准 `abb532bb1836baf48b2d2c9f9a2e43795c49098a`。
- 四个独立 Session/Workspace，创建后逐文件 SHA-256 核对同一初始文件树，generation 均为 0。
- 相同 TASK.md，SHA-256：`b54c1dc35527bda0d8c85030c1adee4e429f86e1cebce5262faa30b86538ff0b`。
- 相同工具集，含 readArtifact；definitionDigest：`f242e557f06d11bfbdcba360b8cce7c829ebd5a5834f51ffd3c9ca0c35b7d262`。
- 配置模型 deepseek-v4-flash、thinking disabled、temperature=0。未记录 Provider 响应中的实际模型版本，不能声称固定了供应商内部路由。
- 18,000 实验窗口、1,024 安全余量、2,048 输出保留；0.6/0.9 触发阈值，保留最近 2 个完整交互组。
- 最多 14 次主模型调用、35 次工具调用；4096/1024 内联/预览预算。
- 固定镜像 `sha256:2236aa4655ce559a47e1f574e8253412c384adad937d254395a1b02542a2edea`，无网络，非 root，测试构建在 /tmp。

18k 是主动设置的实验预算，不是供应商 1M 窗口失效或 API 限额。顺序为 A→B→C→D；没有随机交错、多次重复或缓存命中控制。

## 轨迹说明

### A：修复成功，但结束步骤没走完

两次 runCommand 分别返回 exitCode=1、0。applyPatch 已修复两个文件，generation=1。
第二次完整测试输出继续加入历史，下一次模型请求准备阶段超过预算，尚未执行 finishTask 就停止。

### B：外置确实生效，但模型把内容读回来了

首次测试的完整输出确实进入 Artifact，模型收到预览与引用；随后调用两次 readArtifact：
offset=0/maxBytes=4096、offset=4096/maxBytes=4096，读取同一个 Artifact。
第二次测试输出再次外置，最终仍超预算。

这里有两个可观测成本：额外模型往返，以及回读内容重新进入上下文。
此外模型工具选择本身也与 A 不同，不能把全部 25,239-token 差值严格归因于回读。
四个外置 Artifact 均核对实际落盘内容的 SHA-256 和 size；readArtifact 返回 SUCCESS。

### C：摘要让完整闭环继续，但摘要并不免费

两次摘要都被接受并发布。准备阶段估算分别为 12,521→11,360、17,615→9,450。
这些是上下文准备计量，不是供应商直接报告的“节省 token”，不同计量来源不可直接当作精确节费率。
两次摘要分别花费 2,778、11,464 tokens，合计 14,242。
最终 getWorkspaceDiff、finishTask 成功，报告正确列出了 ORD-065/069/093 的首次 expected/actual。

质量仍需核对：报告中“乘积个位 ≥5”描述 HALF_UP 条件不准确，正确应为乘积对 100 的余数 ≥50；
代码与具体订单示例正确。不能仅凭结构化终止通过就声称自然语言说明完全正确，也不能据此认定是摘要造成。

### D：摘要与回读均生效，但最终失败原因缺失

发生两次摘要，两次外置、两次 Artifact 回读，代码独立验收通过。
最后一次请求准备估计约 6,740 tokens，未触及实验输入预算；随后网关抛异常，Runtime 返回 MODEL_GATEWAY_FAILURE。
现有 catch 未记录 errorCode/providerStatusCode/providerRequestId，无法从此次已存数据判断是 HTTP 错误、网络问题还是解析问题。
本轮没有付费重放“直到成功”，没有替换这个失败样本，也没有重放任何已执行的写工具。

## 预跑与场景校准错误

最初日志 14,636 bytes，我只检查了 Docker 64 KiB 捕获上限，漏掉 Gateway 的 8 KiB 二次限制。
最初 A/B 的实际 stdout 都被截到 8,192 bytes；B 没有触发外置，不能算有效外置消融。
这两次保留在 `live/`，消耗分别 50,520、55,218，共 **105,738 tokens**，不混入正式四组表格。

修正只改测试仓日志格式，保留相同160条订单、两个缺陷、同一用户任务及原生产限额。
校准后 stdout=7,265 bytes、完整结果估计4,742 tokens、预览733 tokens；
正式四组首次/最终测试 stdout 分别为7,265/7,238 bytes，truncated 均为 false。

正式四组已观测消耗 **279,656**；含两次预跑为 **385,394 tokens**，另有 D 失败调用的未知消耗。
缓存计费细分未保存，不能把这个合计直接当作人民币账单。

## 本轮发现的后续事项（未混入实验中修复）

1. 先补网关失败的安全诊断/持久化事件：至少错误分类、HTTP 状态、requestId、是否可重试；禁止记录 API key 或原始敏感响应。
2. 外置要优化按需回读：当前读完整日志会重新膨胀上下文。下一轮可以比较保留失败摘要、定向提取及范围读取，不宜先调低门槛后宣称获益。
3. Gateway 截断与 Artifact 的关系必须讲清：当前 Artifact 只能保存 Gateway 已交付的内容，不能找回此前丢掉的尾部。
4. 四个 Workspace 的数据库 generation 仍为0，工具结果中的 generationAfter 已为1。该持久化缺口需单独修复；本轮使用四个新 Session，未验证重启后继续同一 Workspace 的语义。
5. 当前只是每组一次、小实验预算下的任务测试；不证明1M真实窗口下的净节费、跨Task记忆、长任务恢复或长期压缩质量。
