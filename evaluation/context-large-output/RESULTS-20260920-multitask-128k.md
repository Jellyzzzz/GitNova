**12/12 Run 达到 COMPLETED / FINISH_SUCCEEDED；102 次主模型调用，0 次摘要尝试，累计 3,115,435 tokens。**
主调用均返回 TOOL_CALLS，均取得 usage，没有记录到主调用 LENGTH/TIMEOUT。
这证明本场景在 128k 下能够完成跨 Task 的执行和代码验证，不代表每句交付说明都正确，亦不代表摘要准确性已经验证。

```text
最大输入 = 128,000 - 4,096 - 1,024 = 122,880
固定 System/Tools 估算 = 1,956
动态预算 = 122,880 - 1,956 = 120,924
80% 触发对应总输入估算 ≈ 1,956 + 120,924 × 0.8 = 98,695
90% 触发对应总输入估算 ≈ 110,788
```

实际最高 Provider 单次输入为 74,225，本地最高估算为 74,195，未到摘要触发条件。
因此没有强行触发摘要；本批不能评价 128k 下的摘要准确性、摘要失败恢复或强压缩算法。

## 不应被 COMPLETED 掩盖的质量问题

1. **A 的证据查找错误。** Task 3 用 64 个零组成的占位 artifactId 调用 readArtifact，得到 ARTIFACT_NOT_FOUND。之后交付说明用这次错误推断原始记录不可回读；这不是有效证明。A 原始完整 ToolResult 仍在 Session 历史中。它后来用旧代码逻辑重算出正确订单数字，但「重现」与「读到原执行记录」不是同一证据来源。
2. **C 的时间/来源表述不严谨。** Task 3 在 /tmp 重现 BASE 测试，数字与原失败一致，却将新重现输出称作「最初失败日志」。本批没有摘要，不能把该问题归咎于有损摘要。
3. **完成证据仍需纠偏。** A 一次、C Task 2 一次、D Task 2 一次未声明最新成功验证命令；C Task 3 在重现失败测试后还需重新运行当前版本成功测试。Harness 拒绝后均完成纠偏。
4. **B/D 历史检索更直接。** Task 3 均成功 readArtifact，引用的代表订单 expected/actual 和初始 160/153/7 统计正确。但最终文字将 Artifact ID 缩写成 `…`，不是直接可调用的完整引用；工具执行时使用的是完整合法 ID。

这些是人工核对的代表性问题，不是覆盖所有自由文本陈述的完整语义评分。代码正确性、执行完成度、证据引用质量应分别报告。
