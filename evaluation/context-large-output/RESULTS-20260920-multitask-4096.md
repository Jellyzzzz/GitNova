# 60 秒读取超时、4096 输出额度及新摘要提示词：四组多 Task 真测

## 结论

2026-09-20，再次通过真实客户端注册/登录/建仓库/CLI push → HTTP Session/Task → MySQL/Outbox/RabbitMQ → Worker/Runtime → DeepSeek → Docker 执行。
四组各使用全新 Session/Workspace，每组连续三条 Task，组内不重启服务、不重置代码/历史、不人工纠正摘要，不将失败样本重跑成成功。

**完成数从上一批的 4/12 提升为 7/12；C（仅摘要）完成了全部三条 Task。**
83 次主模型调用均返回 TOOL_CALLS，没有已记录的主调用 LENGTH 或 TIMEOUT。
但 D 的 5 次摘要中有 1 次被本地校验拒绝，只记录了 `FAILED_IllegalStateException`，具体 response/usage 未保存；不能据此宣布所有摘要调用都无截断，或将其费用计为零。

这是同场景重测，不是 timeout/output 两因素的独立因果实验：C/D 同时换了 Pi 风格摘要提示词，供应商响应和工具路线也存在差异。
结论应为“当前组合配置改善了本批完成度”，而非“已找到最优阈值”或“摘要准确性已解决”。

输出额度来自同一个总窗口，扩大输出同时缩小输入额度：

```text
输入硬上限 = 32,000 - 1,024 - 4,096 = 26,880
固定 System/Tools 估算 = 1,956
动态输入预算 = 26,880 - 1,956 = 24,924
80% 触发对应总输入估算约 = 1,956 + 24,924 × 0.8 = 21,896
90% 触发对应总输入估算约 = 24,388
```

上一批输入上限为 28,928，80% 对应约 23,534。本批更早遇到摘要/输入限制并不矛盾。
compact 配置仍只控制紧急摘要/失败边界，**没有新增独立强压缩算法**。

### 失败没有导致每轮无限重试

D Task 3 的 sequence=160：输入估算 22,633，摘要失败，记录 `FAILED_IllegalStateException`，未发布坏摘要。
主流程继续使用原上下文；后续输入估算达到 24,952，紧急摘要尝试成功降至 7,498（sequence=173/174），继续主循环。

失败记录缺少具体校验原因、finishReason 和 usage。ContextSummarizer 对空 response、工具调用、非 STOP、空正文都可能抛 IllegalStateException，因此**现有证据不能把这一次精确归类为 LENGTH**。
这是新的可观测性缺口，应先补充失败元信息保留，再决定是否调整摘要输出额度；本批未中途修代码或掩盖样本。

## 摘要质量仍有边界

对 8 份已发布摘要做有限核查：被保留的完整 64 位引用/digest 和 callId 均能在此前原始 Steps 中找到，没有发现凭空生成的完整标识。
这只能证明标识存在，**不能证明引用归属、每句语义和信息保留都正确**。

明确反例：C sequence=86 的摘要同一句将测试数量写作“12 个 expectQuote”，随后又写“13 个 quote 检查＋4 个非法输入检查”；实际是 13＋4=17。
它还把上一 Task 的 sequence=70 测试称为“本轮”已执行，而当前审核 Task 起于 sequence=82。历史验证并不等价于当前 Task 已验证。
Runtime 没有把该摘要当完成依据，C 后续真实运行了当前测试并正常完成；但这仍是摘要的时间归属错误。

本轮不加入 Run 最终状态投影，不改变前面确认的范围。数据层测试通过和 Controller/Runtime 完成，并不构成“摘要无损”的证明。
